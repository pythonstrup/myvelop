여러 사람이 같은 표를 열어 두고 각자 셀을 고치는 웹 앱을 만든다고 하자. 쇼핑몰 운영자들이 함께 쓰는 상품 표다. 한 행은 상품 하나이고, 열은 상품명, 가격, 재고, 판매 상태, 태그, 상품 설명 여섯 필드다. 운영자는 셀을 눌러 값을 고치고 저장한다. 관리자 화면에서는 이 표가 아래처럼 보인다고 하자.

<ProductTableDiagram />

A가 베이직 린넨 셔츠의 가격을 고치는 동안 B가 같은 상품의 설명을 고친다. 둘 다 저장을 누르면 두 수정이 모두 남아야 한다. 그런데 구현에 따라 한 사람의 수정이 아무 오류 없이 사라진다.

그렇다면 어디까지를 충돌로 봐야 하고, 충돌이 나면 어떻게 다뤄야 할까?

동시 편집을 다루는 방법은 여러 가지다. 마지막 저장을 그대로 두는 방법부터 편집 잠금, 버전 비교, 자동 병합, CRDT까지 있다. 어느 하나가 늘 정답은 아니다. 충돌이 얼마나 자주 나는지, 수정이 사라지면 얼마나 아픈지, 오프라인 편집이 필요한지, 구현과 운영에 얼마나 들일 수 있는지에 따라 알맞은 방법이 달라진다. 이 글은 방법마다 무엇을 얻고 무엇을 내주는지 따져 보고, 요구사항에 맞게 고르는 기준을 정리한다.

## 잃어버린 수정

예시 앱은 많이 쓰는 구성대로 관계형 DB에 데이터를 두고 SQL로 읽고 쓴다고 하자. 다른 저장소를 써도 원리는 같다.

가장 단순한 구현부터 보자. 화면은 행을 통째로 읽어 오고, 사용자가 셀을 고치면 행 전체를 서버로 보내 덮어쓴다.

```ts
// 화면: 고친 셀을 반영한 행 전체를 보낸다
await fetch(`/products/${product.id}`, {
  method: "PUT",
  body: JSON.stringify({ ...product, [field]: value }),
});
```

여름 할인을 맞아 A는 가격을 39,000원에서 29,000원으로 내리고, 그사이 B는 상품 설명에 세탁 방법을 덧붙인다고 하자. 두 사람이 거의 동시에 이 행을 고치면 어떻게 될까?

<pre class="mermaid">{`sequenceDiagram

    accDescr: A와 B가 같은 상품 행을 읽는다. A가 가격을 29,000원으로 내려 저장한 뒤, B가 상품 설명을 고쳐 저장하면서 가격이 39,000원인 옛 행을 통째로 보내 A의 수정을 덮어쓴다.
    participant A
    participant S as 서버
    participant B
    A->>S: 행 읽기
    S-->>A: 가격 39,000원, 설명 원래대로
    B->>S: 행 읽기

    B->>S: 설명에 세탁 방법 추가 (행 전체)

B의 화면은 A가 저장하기 전의 행을 들고 있었다. 그래서 B가 설명만 고쳤는데도 서버에는 이런 쓰기가 도착한다.

```sql
-- B의 저장: 설명만 고쳤지만 화면이 들고 있던 행 전체가 실려 간다
UPDATE products
SET name = '베이직 린넨 셔츠', price = 39000, stock = 120, status = '판매 중',
    tags = ARRAY['여름', '신상'], description = '통기성 좋은 린넨 100% 셔츠. 찬물 손세탁 권장'
WHERE id = 1;
```

옛 가격 39,000원이 함께 실려 가 A가 내린 29,000원을 덮었다. 서버도 화면도 오류를 내지 않았고, A는 할인 가격이 사라진 줄 모른다. 할인 행사는 시작됐는데 상품은 여전히 정가로 팔린다. 이런 현상을 <strong>잃어버린 수정(lost update)</strong>이라고 부른다.

덮어쓰는 칸에는 재고도 들어 있다. B가 행을 읽은 뒤 주문이 세 건 들어와 재고가 117로 줄었다면, B의 저장은 재고까지 읽어 둔 120으로 되돌린다. 이미 팔린 세 개가 재고에 다시 잡히는 것이다.

### 재고 차감과 다른 점

같은 쇼핑몰에서 주문이 재고를 깎을 때도 잃어버린 수정이 생긴다. [UPDATE 한 줄로 끝내는 동시성 문제](/ko/blog/concurrency-single-update)에서 다룬 문제다. 그때는 요청 하나가 재고를 읽고 쓰는 사이가 몇 밀리초였다. 그래서 `UPDATE` 한 줄로 읽기와 쓰기를 붙이거나 [비관적 락](/ko/blog/pessimistic-lock-like-feature)으로 그 사이를 막으면 됐다.

사람의 편집은 다르다. 화면을 여는 순간 값을 읽고, 몇 초에서 몇 분이 지나서야 저장한다. 그 시간 내내 트랜잭션이나 락을 쥐고 있을 수는 없다. 누군가 셀을 연 채 점심을 먹으러 가면, 그동안 다른 사람은 그 행을 아무도 고치지 못한다.

그래서 읽기와 쓰기 사이에 끼어든 변경을 <strong>저장하는 순간에</strong> 알아내야 한다.

### 실시간 화면의 한계

꼭 저장하는 순간이어야 할까? 앞의 표처럼 다른 사람의 변경을 실시간으로 보여 주면, A가 가격을 내리자마자 B의 화면에도 29,000원이 떠서 덮어쓸 일이 없을 것 같다.

하지만 화면에 보이는 값이 서버의 최신 값이라는 보장은 없다. B의 화면은 이런 때 서버보다 뒤처진다.

<ScreenLagDiagram />

그래서 실시간 표시는 충돌을 줄여 줄 뿐 막지는 못한다. 뒤에서 다룰 OT와 CRDT도 모든 화면이 결국 같아지는 것을 보장할 뿐, 매 순간 같다고 보장하지는 않는다. 데이터를 지키는 일은 화면이 아니라 서버가 맡아야 하고, 저장하는 순간의 확인은 실시간 화면을 붙여도 빠질 수 없다. 다음 절에서 이 문제를 다루는 방법들을 살펴본다.

## 동시 편집을 다루는 단순한 방법

먼저 비교적 단순한 네 가지를 살펴보자. Last-Write-Wins, 편집 잠금, 버전 비교, 자동 병합이다. 넷 모두 사용자가 고친 내용을 저장 한 번에 묶어 보낸다는 공통점이 있다. 글자 하나하나를 실시간으로 합치는 OT와 CRDT는 뒤에서 따로 자세히 다룬다.

방법마다 무엇을 얻고 무엇을 내주는지, 실제 제품은 어떻게 하는지 차례로 본다. 제품의 동작은 각 제품의 공식 문서와 엔지니어링 블로그에서 확인한 것만 옮겼다.

### Last-Write-Wins

가장 단순한 방법은 아무것도 하지 않는 것이다. 나중에 도착한 저장이 앞의 저장을 덮는다. 마지막 쓰기가 이긴다는 뜻으로 Last-Write-Wins, 줄여서 LWW라고 부른다. 앞에서 본 구현이 바로 이 방식이다.

생각보다 많은 제품이 이 방식을 쓰되, 덮는 단위를 행이 아니라 셀로 좁힌다. Smartsheet는 같은 셀을 거의 동시에 고치면 마지막으로 저장된 값을 보여 주고, 앞선 값은 셀 기록에서만 볼 수 있다고 안내한다. Baserow도 문서에 마지막 저장이 이기는 방식을 쓴다고 적어 두었다.

셀 단위로 덮으면 앞의 사고처럼 서로 다른 칸을 고친 경우는 부딪히지 않고, 같은 칸을 고친 경우에만 앞 사람의 값이 사라진다. 이 차이는 뒤에서 비교 단위를 다룰 때 자세히 본다.

A가 가격을 29,000원으로 내린 직후, 할인 소식을 모르는 B가 같은 칸에 35,000원을 넣었다고 하자. 두 사람 모두 저장했다는 알림을 받지만, 남는 값은 마지막에 저장한 B의 35,000원이다.

<CellHistoryDiagram />

얻는 것은 단순함이다. 서버는 받은 값을 쓰기만 하면 되고, 사용자는 확인창을 보지 않는다. 내주는 것은 같은 칸의 앞선 수정이다. 값이 사라져도 아무도 알아채지 못한다. 그래서 이 방식을 쓰는 제품은 변경 기록을 함께 남겨 나중에라도 되살릴 수 있게 한다.

같은 칸을 동시에 고치는 일이 드물고, 덮여도 기록에서 되살리면 되는 데이터라면 이 방식으로 충분하다.

<strong>구현할 곳</strong> — 화면은 HTTP `PATCH`로 바꾼 칸만 보내고, 서버는 그 칸만 `UPDATE`한다. Document DB라면 문서를 통째로 바꾸는 대신 필요한 필드만 고치는 갱신 연산을 쓴다.

### 편집 잠금

누군가 고치는 동안 다른 사람이 아예 고치지 못하게 막는 방법이다. 행을 여는 순간 잠그고, 저장하거나 화면을 나가면 푼다.

서버는 상품마다 누가 언제까지 잠금을 쥐었는지 기록해 둔다. 만료 시간을 5분으로 두고, 편집 화면이 입력이 있는 동안 1분마다 잠금을 연장한다고 하자. 잠금은 이런 순서로 걸리고 풀린다.

<pre class="mermaid">{`sequenceDiagram
    accTitle: 편집 잠금이 걸리고 풀리는 순서
    accDescr: A가 상품을 열면 서버가 A에게 5분짜리 잠금을 준다. 같은 상품을 연 B는 A가 편집 중이라 읽기만 할 수 있다. A의 화면은 입력이 있는 동안 1분마다 잠금을 연장한다. A가 저장하면 서버가 값을 저장하고 잠금을 푼다. A가 자리를 비우거나 창을 닫으면 연장이 끊겨 5분 뒤 잠금이 만료된다. 어느 쪽이든 그 뒤에 B가 다시 열면 B가 잠금을 얻어 편집할 수 있다.
    participant A
    participant S as 서버
    participant B
    A->>S: 상품 열기
    Note over S: 잠금 없음, A에게 잠금 (5분)
    S-->>A: 편집 가능
    B->>S: 같은 상품 열기
    Note over S: A가 잠금 중
    S-->>B: 읽기만 가능 (A님이 편집 중)
    loop 입력하는 동안 1분마다
        A->>S: 잠금 연장
    end
    alt A가 저장한다
        A->>S: 저장
        Note over S: 값을 저장하고 잠금 해제
    else A가 자리를 비우거나 창을 닫는다
        Note over S: 연장이 끊겨 5분 뒤 잠금 만료
    end
    B->>S: 다시 열기
    Note over S: 잠금 없음, B에게 잠금
    S-->>B: 편집 가능`}</pre>

충돌이 처음부터 생기지 않는다는 것이 장점이다. 대신 앞에서 본 문제가 그대로 돌아온다. 잠근 사람이 화면을 열어 둔 채 자리를 비우면 아무도 그 행을 고치지 못한다. 그래서 잠금에는 만료 시간이 꼭 필요한데, 만료가 너무 짧으면 고치는 도중에 잠금이 풀린다. 브라우저가 닫히거나 연결이 끊긴 경우도 따로 처리해야 한다.

막지 않고 알리기만 하는 부드러운 잠금도 있다. Shopify 관리자는 다른 직원이 이미 편집 중인 상품을 열면 경고를 띄우지만, 무시하고 계속 편집할 수 있게 둔다. 충돌을 줄이는 효과는 있어도 막지는 못하므로 다른 방법과 함께 쓴다.

예시의 상품 표에 부드러운 잠금을 붙이면, A가 고치고 있는 상품을 B가 열 때 이런 경고가 뜬다.

<EditLockDiagram />

한 번 고치는 데 오래 걸리고, 동시에 고치면 되돌리기 어려운 데이터라면 편집 잠금이 맞다. 긴 계약서처럼 한 사람이 끝까지 맡아 고치는 문서가 그렇다.

<strong>구현할 곳</strong> — 누가 언제까지 잠금을 쥐었는지 적어 둘 저장소면 어디서든 만들 수 있다. 관계형 DB라면 상품 id를 기본 키로 하는 잠금 테이블을 두고, 잠금이 없거나 만료됐을 때만 쓰는 문장 하나로 잠금을 얻는다.

```sql
-- A가 상품 1의 잠금을 얻는다. 행이 돌아오면 성공, 돌아오지 않으면 다른 사람이 쥐고 있다
INSERT INTO edit_locks (product_id, holder, expires_at)
VALUES (1, 'A', now() + interval '5 minutes')
ON CONFLICT (product_id) DO UPDATE
SET holder = excluded.holder, expires_at = excluded.expires_at
WHERE edit_locks.expires_at < now() OR edit_locks.holder = 'A'
RETURNING holder;
```

두 사람이 동시에 열어도 기본 키가 겹치므로 한 사람만 잠금을 얻는다. 연장은 같은 문장을 다시 보내고, 해제는 `holder`가 나인 행만 지운다. 함께 알아 둘 것은 이렇다.

- <strong>키값 저장소</strong> — Redis라면 `SET lock:product:1 A NX PX 300000` 한 줄로 키가 없을 때만 잠금을 만들고, 5분 뒤 저절로 지워지게 한다.
- <strong>편집 중 표시</strong> — 누가 어디를 보고 있는지는 WebSocket이나 SSE로 나눈다.
- <strong>쓰지 않을 것</strong> — DB의 `SELECT … FOR UPDATE`나 PostgreSQL의 advisory lock은 트랜잭션이나 DB 연결이 끝나면 풀린다. 요청마다 연결을 바꿔 쓰는 웹 서버에서는 사람이 편집하는 몇 분 동안 쥐고 있기 어렵다.

### 버전 비교

저장할 때 내가 읽은 뒤로 아무도 바꾸지 않았는지 확인하고, 바뀌었으면 저장을 거절하는 방법이다. 낙관적 락이라고도 부른다. 충돌이 드물다고 낙관하고 일단 편집하게 둔 뒤, 저장하는 순간에만 검사한다는 뜻이다.

행마다 버전 번호를 두고, 저장할 때 읽어 둔 버전을 조건에 넣는다. A가 읽은 행의 버전이 7이었다고 하자.

```sql
UPDATE products
SET price = 29000, version = version + 1
WHERE id = 1 AND version = 7;
```

그사이 누가 저장했다면 버전이 8로 올라가 있어서 이 문장은 행을 하나도 고치지 않는다. 서버는 고친 행 수가 0인 것을 보고 충돌로 판정한다. 버전 번호 대신 마지막 수정 시각인 `updated_at`을 비교해도 원리는 같다.

A가 먼저 저장하고 B가 뒤따르면 이런 순서가 된다.

Salesforce가 이 방식을 쓴다. 편집을 시작한 뒤 레코드가 바뀌었으면 저장을 거절하고, 입력한 내용을 적어 둔 뒤 레코드를 다시 불러와 입력하라고 안내한다. 다른 사용자가 바꾼 경우뿐 아니라, 같은 사용자의 다른 창이나 백그라운드 작업이 바꾼 경우에도 똑같이 거절한다.

얻는 것은 수정이 조용히 사라지지 않는다는 보장이다. 잠금처럼 남을 기다리게 하지도 않는다. 내주는 것은 사용자의 수고다. 거절당한 사람은 입력을 다시 해야 한다. 버전이 행 단위라면 남이 다른 칸만 고쳐도 거절되는데, 이 오탐을 줄이는 방법은 뒤에서 다룬다.

A가 가격을 바꿔 버전이 올라간 뒤 B가 설명만 고쳐 저장하면, 행 단위 버전 비교는 B에게 아래 창을 띄운다.

<VersionRejectDiagram />

충돌이 드물고 덮어쓰면 안 되는 데이터라면 버전 비교가 맞다. 업무용 화면 대부분이 여기에 속한다.

<strong>구현할 곳</strong> — HTTP에는 이 방식을 위한 표준이 있다. RFC 9110에 따라 서버는 응답의 `ETag`로 버전을 알려 주고, 클라이언트는 저장할 때 `If-Match`에 그 값을 싣는다. 버전이 다르면 서버는 `412 Precondition Failed`를 돌려준다. ORM도 지원해서 JPA는 `@Version` 필드, Rails는 `lock_version` 칸을 두면 위 SQL을 대신 만든다. DynamoDB의 조건부 쓰기와 Kubernetes의 `resourceVersion`도 같은 원리다.

### 자동 병합

버전 비교로 충돌을 찾은 뒤, 바로 거절하지 않고 합칠 수 있는지 한 번 더 보는 방법이다. 내가 읽은 값, 서버의 최신 값, 내가 보낸 값 셋을 비교해서 서로 다른 곳을 고쳤으면 둘 다 살린다. 세 값을 쓰기 때문에 3-way 병합이라고 부르고, Git이 브랜치를 합칠 때도 같은 원리를 쓴다. Git에서는 이 셋을 base, theirs, ours라고 부른다.

위키백과가 쓰는 MediaWiki가 좋은 예다. 편집을 시작한 뒤 문서가 바뀌었어도 서로 다른 줄을 고쳤으면 자동으로 합친다. 같은 줄을 건드렸을 때만 편집 충돌 화면을 띄우고, 최신 문서와 내 변경을 함께 보여 줘 사용자가 직접 합치게 한다.

앞의 버전 비교와 같은 상황에서 자동 병합은 B를 거절하지 않는다. 두 사람이 고친 칸이 다르니 둘 다 살려 저장한다.

<AutoMergeDiagram />

얻는 것은 거절이 크게 줄어든다는 점이다. 진짜로 같은 곳을 고친 경우에만 사용자에게 묻는다. 내주는 것은 구현의 복잡도다. 무엇을 다른 곳으로 볼지 데이터 종류마다 정해야 한다. 숫자 칸은 합칠 방법이 없고, 태그 같은 목록은 항목 단위로, 긴 글은 줄 단위로 합칠 수 있다. 판정 규칙이 틀리면 엉뚱한 값이 조용히 만들어진다.

여러 사람이 같은 레코드를 자주 함께 고치고, 거절이 잦으면 일이 막히는 경우라면 자동 병합을 검토할 만하다. 판정 방법과 목록을 합치는 계산은 뒤에서 차례로 다룬다.

<strong>구현할 곳</strong> — 클라이언트가 저장 요청에 내가 읽은 값을 함께 보낸다. 서버는 `SELECT … FOR UPDATE`로 행을 잠깐 잠근 채 세 값을 비교하고 쓴다. 긴 글은 diff3 계열 라이브러리로 줄 단위 병합을 할 수 있다.

네 방법 가운데 무엇을 고르든 먼저 정해야 할 것이 있다. 충돌을 무엇의 단위로 비교할지다.

## 비교 단위 — 행과 칸

같은 상황이라도 무엇을 단위로 비교하느냐에 따라 결과가 달라진다. 앞의 예에서 A는 가격을, B는 설명을 고쳤다. 행 단위로 비교하면 B의 저장은 거절되고, 칸 단위로 비교하면 둘 다 저장된다. B가 서버에 보내는 요청부터 다르다.

<CompareUnitDiagram />

### 행 단위

앞의 버전 비교가 행 단위다. 행마다 버전을 하나 두고, 어느 칸이 바뀌든 버전을 올린다. 비교할 값이 하나뿐이라 구현이 단순하고, `ETag`나 ORM의 버전 필드를 그대로 쓸 수 있다. 앞에서 본 Salesforce도 레코드 단위로 비교한다.

세 사람이 같은 행의 서로 다른 칸을 차례로 고치면 이렇게 된다.

<RowVersionDiagram />

대신 실제로는 겹치지 않은 저장까지 거절한다. 칸이 많고 함께 고치는 사람이 많을수록 이런 오탐이 늘어난다. 한 사람이 폼 하나를 맡아 고치는 화면이면 문제가 되지 않지만, 여러 사람이 같은 표를 고치는 화면이면 거절이 잦아진다.

### 칸 단위

화면은 바꾼 칸만 보내고, 그 칸을 읽었을 때의 값을 함께 보낸다. 서버는 그 칸의 최신 값이 읽은 값과 같을 때만 쓴다. 버전 번호가 하던 일을 칸의 값이 대신하는 셈이다.

앞의 세 사람에 A보다 늦게 가격을 고친 D를 더해 칸 단위로 비교하면 이렇게 된다.

<CellValueDiagram />

B의 저장을 SQL로 쓰면 이렇다.

```sql
-- B의 저장: 설명이 B가 읽은 값 그대로일 때만 고친다
UPDATE products
SET description = '통기성 좋은 린넨 100% 셔츠. 찬물 손세탁 권장'
WHERE id = 1 AND description = '통기성 좋은 린넨 100% 셔츠';
```

A가 바꾼 가격은 조건에 없으므로 B의 저장은 통과하고, A의 가격도 그대로 남는다. 여러 칸을 함께 고쳤다면 칸마다 조건을 `AND`로 붙인다. 값이 비어 있을 수 있는 칸은 `=` 대신 `IS NOT DISTINCT FROM`으로 비교한다. SQL에서 `NULL = NULL`은 참이 아니라 `NULL`이기 때문이다.

### 함께 바뀌어야 하는 칸

칸 단위에도 함정이 있다. 서로 묶인 칸을 따로 비교하면, 두 저장이 각각은 맞아도 합친 결과가 틀릴 수 있다.

베이직 린넨 셔츠를 촬영 때문에 잠시 품절로 내려 두었고, 재고는 3개라고 하자. A는 창고를 확인해 보니 실제 재고가 없어서 재고를 0으로 고친다. 같은 때 B는 촬영이 끝났으니 재고 3개를 보고 판매 상태를 판매 중으로 연다. 두 사람이 고친 칸이 다르니 칸 단위 비교는 둘 다 통과시키고, 상품 표에는 이런 행이 남는다.

<LinkedCellsDiagram />

주문이 들어와도 보낼 물건이 없다. 막는 방법은 세 가지이고, 어디에서 막느냐에 따라 얻는 것과 내주는 것이 다르다.

| 방법 | 막는 범위 | 얻는 것 | 내주는 것 |
| --- | --- | --- | --- |
| 묶어서 비교 | 이 화면의 저장 | 어느 값을 남길지 사용자가 고른다 | 함께 있어도 되는 수정까지 충돌로 잡는다 |
| 서버 코드로 검사 | 이 코드를 거치는 쓰기 | 알아듣기 쉬운 오류, 예약 판매 같은 예외 | 배치 작업이나 직접 실행한 SQL은 못 막는다 |
| DB 제약 | 모든 쓰기 | 어느 경로로 쓰든 막는다 | 한 행 안의 규칙만 걸 수 있고, 바꾸려면 마이그레이션이 필요하다 |

<strong>묶어서 비교</strong>하면 재고와 판매 상태를 한 칸처럼 판정해 B의 저장을 충돌로 잡는다. 대신 A가 재고를 채우는 사이 B가 판매를 연 것처럼, 함께 있어도 되는 수정까지 B에게 묻는다.

<strong>서버 코드로 검사</strong>하면 쓰기 직전에 합쳐질 행이 규칙을 지키는지 본다. 이미 잠근 행을 쓰므로 조회가 늘지 않고, "재고가 0이라 판매를 열 수 없습니다" 같은 오류나 예약 판매 같은 예외를 넣기 쉽다.

<strong>DB 제약</strong>은 이렇게 건다.

```sql
-- 판매 중이면 재고가 있어야 한다. 기존 행은 두 번째 문장에서 검사한다
ALTER TABLE products ADD CONSTRAINT on_sale_needs_stock
  CHECK (status <> '판매 중' OR stock > 0) NOT VALID;
ALTER TABLE products VALIDATE CONSTRAINT on_sale_needs_stock;
```

`CHECK`는 쓰는 행 하나만 보고 식을 계산할 뿐, 다른 행을 읽거나 잠그지 않는다. PostgreSQL 17에 32개 연결로 동시에 `UPDATE`를 보내 재 보면 이렇다.

<CheckBenchDiagram />

제약 유무로는 차이가 없다. 처리량을 떨어뜨린 것은 같은 행에 몰린 쓰기다.

부담은 처음 걸 때 생긴다. 기존 행을 검사하는 동안 테이블이 잠기므로, `NOT VALID`로 먼저 걸고 `VALIDATE CONSTRAINT`로 나중에 검사한다. 제약을 어긴 쓰기는 DB 오류로 돌아오니, 화면에 보일 문장으로 바꾸는 일은 서버 코드가 맡는다.

셋은 섞어 쓸 수 있다. 오류와 예외는 서버 코드가 맡고, 어떤 경로로도 깨지면 안 되는 규칙은 DB 제약으로 한 번 더 막는 식이다.

고르는 기준은 화면의 모양이다. 한 사람이 폼 하나를 끝까지 고쳐 한 번에 저장하는 화면이면 행 단위로 충분하다. 여러 사람이 한 표에서 서로 다른 칸을 고치는 화면이면 칸 단위가 맞고, 묶인 칸은 위의 방법으로 따로 지킨다.

칸 단위로 비교하기로 했다면 남은 질문이 하나 있다. 읽은 값과 최신 값이 다르면 늘 충돌로 봐야 할까?

## 진짜 충돌 가려내기

읽은 값과 최신 값이 다르다는 것은 그사이 누군가 그 칸을 바꿨다는 뜻이다. 내 수정과 부딪혔다는 뜻은 아니다. A와 B가 같은 할인 공지를 보고 둘 다 가격을 29,000원으로 내렸다고 하자. A가 먼저 저장하면 B가 읽은 39,000원과 최신 값 29,000원이 달라서, 앞의 칸 단위 비교는 B의 저장을 거절한다. 하지만 B가 저장하려는 값이 이미 최신 값이므로 거절할 이유가 없다.

그래서 칸마다 세 값을 본다. 화면이 그 칸에 보여 준 <strong>읽은 값</strong>, 서버의 <strong>최신 값</strong>, 내가 저장하려는 <strong>보낸 값</strong>이다. 가격 칸 하나로 경우를 나누면 이렇다.

<ThreeValueDiagram />

색이 같은 칩은 같은 값이다. 진짜 충돌은 마지막 줄 하나뿐이다. 세 값이 모두 다를 때, 곧 남도 바꾸고 나도 바꿨는데 서로 다른 값으로 바꿨을 때만 사용자에게 물으면 된다.

```ts
type Verdict = "write" | "keep" | "same" | "conflict";

// 칸 하나를 판정한다. eq는 칸 종류마다 정한 "같다"의 기준이다
function judge<T>(seen: T, current: T, mine: T, eq: (a: T, b: T) => boolean): Verdict {
  if (eq(current, seen)) return "write"; // 아무도 안 바꿨다
  if (eq(mine, seen)) return "keep"; // 나는 이 칸을 안 바꿨다
  if (eq(current, mine)) return "same"; // 둘이 같은 값으로 바꿨다
  return "conflict"; // 서로 다르게 바꿨다
}
```

두 번째 줄이 있어서 화면이 행 전체를 보내도 안전하다. 처음에 본 잃어버린 수정에서 B가 함께 실어 보낸 옛 가격 39,000원은 B가 읽은 값과 같다. 그러니 서버는 그 칸을 건너뛰고, A가 내린 29,000원이 남는다.

서버는 행을 잠깐 잠근 채 칸마다 판정하고, 충돌이 없을 때만 쓴다.

```ts
// 서버: SELECT … FOR UPDATE로 행을 잠근 트랜잭션 안에서 판정하고 쓴다
const current = await lockRow(productId);
const writes: Record<string, unknown> = {};
const conflicts: string[] = [];
for (const [field, mine] of Object.entries(changes)) {
  const verdict = judge(seen[field], current[field], mine, eqFor(field));
  if (verdict === "write") writes[field] = mine;
  if (verdict === "conflict") conflicts.push(field);
}
if (conflicts.length > 0) throw new ConflictError(conflicts, current);
await updateRow(productId, writes);
```

이 예시는 충돌이 하나라도 있으면 아무것도 쓰지 않고, 충돌한 칸과 최신 값을 돌려준다. 일부 칸만 저장하면 사용자가 무엇이 저장됐는지 헷갈리기 때문이다. 충돌을 알리는 화면은 뒤에서 다룬다.

### 같다의 기준

판정은 "같다"를 어떻게 정하느냐에 달렸다. 같은 값을 다르다고 보면 충돌이 아닌데 사용자에게 묻고, 다른 값을 같다고 보면 수정이 사라진다. 그래서 칸 종류마다 기준을 정해 둔다.

| 칸 | 같다고 보는 기준 |
| --- | --- |
| 가격, 재고 | 숫자로 바꿔 비교한다. `29000`과 `"29000"`은 같다 |
| 태그 | 순서가 의미 없다면 집합으로 비교한다. `["여름", "신상"]`과 `["신상", "여름"]`은 같다 |
| 상품 설명 | 저장할 때와 같은 방식으로 다듬은 뒤 비교한다 |
| 빈 값 | 저장할 때 `null`, 빈 문자열, 빈 목록을 하나로 맞춘다면 비교할 때도 같게 본다 |

핵심은 저장할 때와 비교할 때 같은 규칙을 쓰는 것이다. 저장할 때는 앞뒤 공백을 지우는데 비교할 때는 그대로 두면, 아무도 안 바꾼 칸이 바뀐 것으로 보인다.

읽은 값은 화면이 그 칸에 보여 준 값이다. 실시간으로 새 값을 받아 화면을 바꿨다면 읽은 값도 함께 바꾼다. 사용자가 보고 고친 값이 그 값이기 때문이다.

세 값으로 판정하면 사용자에게 물을 일은 진짜로 부딪힌 칸만 남는다. 그중 가격 같은 숫자나 글은 둘 중 하나를 고를 수밖에 없다. 태그 같은 목록은 다르다. 항목 단위로 보면 두 사람의 수정을 모두 살릴 수 있다.

## 목록 값 병합

베이직 린넨 셔츠의 태그가 여름, 신상 두 개라고 하자. 할인이 시작되어 A는 세일을 더하고, 같은 때 B는 출시한 지 한 달이 지나 신상을 뺀다. A가 먼저 저장하면 B가 읽은 값은 여름·신상, 최신 값은 여름·신상·세일, B가 보낸 값은 여름이다. 세 값이 모두 다르니 앞의 판정은 충돌로 본다. 하지만 두 사람이 건드린 태그는 서로 다르다.

그래서 목록은 항목 단위로 본다. 태그마다 읽은 값, 최신 값, 보낸 값에 그 태그가 있는지를 놓고 앞의 세 값 판정을 한다.

<TagMergeDiagram />

신상은 B가 뺐으니 B의 값을 따라 빠지고, 세일은 B가 건드리지 않았으니 최신 값을 따라 남는다. 항목마다 값은 있다와 없다 둘뿐이라 세 값이 모두 다를 수 없다. 그래서 충돌이 생기지 않는다.

코드로는 내가 빼고 더한 항목만 최신 값에 반영하면 같은 결과가 나온다.

```ts
// 태그 칸: 내가 빼고 더한 항목만 최신 값에 반영한다
function mergeTags(seen: string[], current: string[], mine: string[]): string[] {
  const removed = seen.filter((t) => !mine.includes(t));
  const added = mine.filter((t) => !seen.includes(t));
  const kept = current.filter((t) => !removed.includes(t));
  return [...kept, ...added.filter((t) => !kept.includes(t))];
}
```

앞의 서버 반복문에서 태그 칸은 `judge` 대신 이 함수의 결과를 쓴다. 두 사람이 같은 태그를 더해도 한 번만 들어가고, 같은 태그를 함께 빼도 문제없다.

드문 경우가 하나 남는다. 같은 태그를 한 사람은 빼고 다른 사람은 다시 더하면, 나중에 저장한 쪽이 남는다. 이것까지 가리려면 항목을 더할 때마다 고유한 표시를 붙이고, 뺄 때는 내가 본 표시만 지워야 한다. 뒤에서 다룰 CRDT가 이렇게 한다.

얻는 것은 목록 칸에서 사용자에게 묻는 일이 사라진다는 점이다. 내주는 것은 세 가지다.

<strong>저장한 값과 남는 값이 다르다.</strong> B는 여름만 남기려고 저장했지만 여름·세일이 남는다. 서버는 합친 결과를 응답으로 돌려주고, 화면은 그 값으로 칸을 다시 그려야 한다. 그러지 않으면 B의 화면에는 세일이 빠진 목록이 남는다.

<MergedResultDiagram />

<strong>합친 결과가 규칙을 어길 수 있다.</strong> 태그를 5개까지만 달 수 있다면, 4개 달린 상품에 두 사람이 하나씩 더해 6개가 될 수 있다. 각 저장은 규칙을 지켰는데 합친 결과가 어긴 것이다. 앞의 함께 바뀌어야 하는 칸처럼 합친 결과로 규칙을 다시 검사한다.

<MergedRuleDiagram />

<strong>순서는 지키지 못한다.</strong> 이 방법은 목록을 집합으로 본다. 대표 이미지 순서처럼 순서에 뜻이 있으면, 두 사람이 같은 자리에 끼워 넣거나 같은 항목을 다른 자리로 옮길 때 어느 쪽을 따를지 정할 수 없다. 이런 목록은 목록 전체를 값 하나로 판정해 충돌로 묻는 편이 단순하다. 순서까지 합쳐야 한다면 CRDT 같은 순서 있는 자료 구조가 필요하다.

<ListOrderDiagram />

<strong>구현할 곳</strong> — 태그를 상품마다 한 행씩 따로 저장하면 병합을 DB가 맡는다. 상품 번호와 태그를 묶어 기본 키로 두고, 화면은 목록 대신 더한 태그와 뺀 태그를 보낸다.

```sql
-- A의 저장: 세일을 더한다. 이미 있으면 아무 일도 하지 않는다
INSERT INTO product_tags (product_id, tag) VALUES (1, '세일')
ON CONFLICT DO NOTHING;

-- B의 저장: 신상을 뺀다
DELETE FROM product_tags WHERE product_id = 1 AND tag = '신상';
```

값 대신 바꾼 내용, 곧 연산을 보내는 셈이다. 이 생각을 글자 하나하나까지 밀고 가면 뒤에서 다룰 OT와 CRDT가 된다.

세 값 판정과 목록 병합을 거치면, 사용자에게 물을 일은 같은 칸을 서로 다르게 고친 경우만 남는다. 그때 무엇을 보여 주고 어떻게 고르게 할지가 다음 질문이다.
