## 들어가며

알림톡, 이메일, 푸시처럼 사용자에게 메시지를 보내는 기능은 어느 서비스에나 있다. 처음에는 필요한 곳에서 외부 API를 바로 호출하면 그만이다. 그런데 발송하는 곳이 늘어나면 금세 한계에 부딪힌다.

-   <strong>여러 곳에서 같은 외부 API를 호출한다.</strong> API 서버, 어드민, 배치까지 발송 경로가 흩어진다.
-   <strong>외부 API에는 rate limit이 있다.</strong> "5초당 100건" 같은 제약을 어디선가 지켜야 한다.
-   <strong>바로 보내지 않는 알림이 많다.</strong> "인증 후 D+1에 안내", "결제 실패 시 3일 뒤 재안내"처럼 시점이 정해진 발송이 필요하다. 어드민이 특정 사용자에게 특정 시점으로 거는 일회성 예약처럼, 도메인 모델의 상태값으로는 표현하기 어려운 것도 있다.
-   <strong>대량 발송은 언제나 일부가 실패한다.</strong> 어떤 메시지가 실패했고 무엇을 다시 보내야 하는지 추적할 수 있어야 한다.

이 문제들은 하나씩 따로 풀 수 있다. 발송 모듈을 하나로 모으고, 함수 안에 rate limit을 두고, 스케줄러로 시점 분기를 만들고, 발송 이력 테이블에 실패를 기록하면 된다. 어려운 것은 네 가지를 한 시스템 안에서 동시에 풀어야 할 때다. API 서버와 워커 여러 대가 함께 도는 분산 환경이라면 넷이 서로 어긋나지 않아야 한다.

이 시리즈는 그런 알림 서버를 설계하며 만난 갈림길을 다룬다. 갈림길마다 어떤 후보가 있었는지, 각 후보가 무엇을 얻고 무엇을 내주는지를 따진다. 1편에서는 그 출발점으로, 발송을 어디에 맡길지를 네 가지 질문으로 나눠 본다.

1. 발송을 요청한 쪽이 결과를 기다려야 하는가
2. 요청한 쪽이 누가 처리할지 아는가
3. 대기 중인 작업의 상태를 어디에 둘 것인가
4. 예약 발송을 어떻게 표현할 것인가

답부터 말하면 Redis 기반 작업 큐인 BullMQ를 골랐다. 다만 이 글은 BullMQ를 소개하지 않는다. 질문마다 다른 후보를 골랐다면 무엇이 달라졌을지를 따진다. BullMQ 자체의 구조와 기능은 [BullMQ란](/ko/blog/bullmq-notification-part-1-what-is-bullmq) 글에 따로 정리했다.
