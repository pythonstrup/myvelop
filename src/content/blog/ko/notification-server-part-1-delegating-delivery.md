## 들어가며

회원가입을 마치면 환영 알림톡을 보내는 서비스를 하나 만든다고 해보자. 처음에는 가입 API 안에서 외부 메시징 API를 한 번 호출하면 끝난다.

요구사항은 금방 눈덩이처럼 불어난다. 결제가 실패하면 3일 뒤에 다시 안내해야 하고, 어드민에서는 특정 사용자에게 원하는 시각으로 예약을 걸고 싶어 한다. 밤마다 도는 배치는 가입자 전원에게 공지를 보낸다. 그러면 발송 코드가 API 서버, 어드민, 배치에 하나씩 생긴다.

이때부터 문제가 드러난다. 외부 API에 "5초당 100건" 같은 한도가 있다고 하자. 세 곳이 이 한도를 나눠 써야 하는데, 서로의 호출량을 아는 곳은 없다. 3일 뒤 재안내를 보내려면 누군가 그 시각을 기억하고 있어야 한다. 배치로 보낸 공지 가운데 일부가 실패하면, 누구에게 다시 보내야 하는지 알아내기도 어렵다.

이쯤 되면 발송을 한곳에 모아 별도 서버로 떼어 내자는 이야기가 나온다. 이 시리즈는 알림 서버를 만들면서 마주하게 될 트레이드오프에 대해서 다룬다. 발송을 무엇에 맡길지, 외부 API의 한도를 어디서 지킬지, 보낸 기록을 어디에 쌓고 어떻게 읽을지, 대량 발송을 묶어 보낼 때 무엇이 엇갈리는지가 차례로 나온다. 결정마다 후보를 나란히 놓고, 각 후보가 무엇을 얻고 무엇을 내주는지를 따진다. 지금 발송 서버를 떼어 내려는 참이라면, 결정하기 전에 짚어 볼 목록으로 읽어도 좋다.

1편은 그 첫 트레이드오프인 "발송을 어디에 맡길 것인가"를 다룬다. 이 질문은 다시 네 가지로 나뉜다.

1. 발송을 요청한 쪽이 결과를 기다려야 하는가
2. 요청한 쪽이 누가 처리할지 아는가
3. 대기 중인 작업의 상태를 어디에 둘 것인가
4. 예약 발송을 어떻게 표현할 것인가
