## 기본 설정의 한계

EC2를 띄우면 콘솔은 VPC와 서브넷을 고르라고 한다. 무엇인지 몰라도 기본값을 누르고 넘어가면 서버는 잘 뜬다.

문제는 그 위에 무언가를 얹을 때 드러난다. EKS에서는 Pod마다 서브넷 IP를 하나씩 가져간다. 서브넷을 작게 잘라 두면 CPU와 메모리가 남아도 Pod가 IP를 받지 못한다. 프라이빗 서브넷의 노드는 NAT 게이트웨이를 거쳐 밖으로 나가는데, 다른 길을 만들어 두지 않았다면 NAT가 멈추는 순간 새 Pod는 이미지를 받지 못한다. 처음 VPC를 만들 때 정한 주소 범위는 나중에 고칠 수도 없다.

## VPC

### VPC란

VPC(Virtual Private Cloud)는 리전 안에서 내 몫으로 떼어 받은 가상 네트워크다. 다른 계정의 네트워크와는 논리적으로 격리되어 있고 리전 안의 모든 가용 영역에 걸친다.

> <strong>리전과 가용 영역이란?</strong>  
> 리전은 서울(`ap-northeast-2`)처럼 AWS 데이터센터가 모인 지역이다. 가용 영역은 그 리전 안에서 전원과 네트워크를 따로 쓰는 데이터센터 묶음이다. 서울 리전에는 a부터 d까지 네 곳이 있다.

VPC를 만들 때는 IPv4 주소 범위부터 정한다. 범위는 CIDR로 적고 크기는 `/16`에서 `/28` 사이로 고를 수 있다.

### CIDR 읽는 법

`10.0.0.0/16`에서 `/` 뒤의 숫자는 앞에서부터 고정하는 비트 수다. IPv4 주소는 32비트이므로 `/16`이면 앞 16비트는 `10.0`으로 고정되고, 나머지 16비트로 주소를 만든다. 만들 수 있는 주소는 2¹⁶, 곧 65,536개다.

| CIDR | 고정하는 비트 | 주소 수 |
| --- | --- | --- |
| `/16` | 16 | 2¹⁶ = 65,536 |
| `/19` | 19 | 2¹³ = 8,192 |
| `/20` | 20 | 2¹² = 4,096 |
| `/24` | 24 | 2⁸ = 256 |

헷갈리기 쉬운 것은 방향이다. `/` 뒤의 숫자가 클수록 고정하는 부분이 길어지니 범위는 작아진다. `/19`는 2¹⁹개가 아니라 2¹³개다. 고정하는 비트가 하나 늘 때마다 주소 수는 절반이 된다.

### 주소 범위 추가

VPC의 범위는 만든 뒤에 키우거나 줄일 수 없다. 모자라면 범위를 하나 더 붙여야 한다.

그런데 붙일 수 있는 범위도 처음 범위에 따라 정해져 있다. 처음 범위를 `192.168.0.0/16`으로 잡았다면 다른 사설 대역인 `10.0.0.0/8`이나 `172.16.0.0/12`는 붙일 수 없다. `100.64.0.0/10` 대역이나 공인 대역만 붙일 수 있다.

> <strong>100.64.0.0/10이란?</strong>  
> 통신사가 내부용으로 쓰라고 떼어 둔 공유 주소 공간(RFC 6598)이다. 인터넷에서 라우팅되지 않는 주소라 VPC 안에서 사설 주소처럼 쓸 수 있다.

IP가 넉넉해도 범위는 모자랄 수 있다. 서브넷마다 IP가 수천 개씩 남아 있어도, VPC 범위를 서브넷으로 빈틈없이 나눠 버렸다면 새 서브넷을 만들 자리가 없다. 처음 VPC를 나눌 때 범위의 일부를 비워 두는 편이 낫다.

## 서브넷

### 서브넷과 가용 영역

서브넷은 VPC 범위의 일부를 잘라 낸 것이다. 서브넷 하나는 반드시 가용 영역 하나에만 속하고 여러 영역에 걸칠 수 없다. 그래서 가용 영역 두 곳에 서버를 나눠 두려면 서브넷도 최소 두 개가 필요하다.

`10.0.0.0/16` VPC를 예로 들어 나눠 보자.

| 서브넷 | 가용 영역 | 용도 |
| --- | --- | --- |
| `10.0.0.0/24` | a | 퍼블릭 |
| `10.0.1.0/24` | b | 퍼블릭 |
| `10.0.10.0/24` | a | 프라이빗 |
| `10.0.11.0/24` | b | 프라이빗 |

### AWS 예약 주소

서브넷의 주소를 전부 쓸 수 있는 것은 아니다. 일반 네트워크에서도 범위의 첫 주소(네트워크 주소)와 마지막 주소(브로드캐스트 주소)는 기기에 주지 않는다. AWS는 여기에 세 개를 더 가져간다. `10.0.0.0/24`라면 이렇다.

| 주소 | 용도 |
| --- | --- |
| `10.0.0.0` | 네트워크 주소 |
| `10.0.0.1` | VPC 라우터 |
| `10.0.0.2` | DNS 서버 |
| `10.0.0.3` | AWS가 나중에 쓰려고 남겨 둔 주소 |
| `10.0.0.255` | 브로드캐스트 주소. VPC는 브로드캐스트를 지원하지 않지만 주소는 막아 둔다 |

그렇다면 `/19` 서브넷에는 Pod를 몇 개 띄울 수 있을까? 8,192개에서 다섯 개를 빼면 8,187개다.

하지만 Pod가 이 IP를 전부 받지는 못한다. 노드 자신도 IP를 쓰고, 같은 서브넷에 꽂힌 로드 밸런서와 NAT 게이트웨이도 IP를 쓴다. 노드가 Pod를 빨리 띄우려고 미리 잡아 두는 IP도 있다. 무엇이 IP를 쓰는지는 뒤의 ENI 절에서 다시 본다.

### 퍼블릭 서브넷과 프라이빗 서브넷

서브넷 이름에 public이나 private을 붙이는 경우가 많지만, 이름이 서브넷의 성격을 정하지는 않는다. 퍼블릭과 프라이빗을 가르는 것은 <strong>라우팅</strong>이다. 인터넷 게이트웨이로 가는 경로가 있으면 퍼블릭 서브넷이고, 없으면 프라이빗 서브넷이다.

퍼블릭 서브넷에 있다고 바로 인터넷에 나갈 수 있는 것도 아니다. 인스턴스에 공인 IP가 있어야 한다. 서브넷에는 새 인스턴스에 공인 IP를 자동으로 줄지 정하는 설정이 따로 있다. 이 설정이 꺼진 퍼블릭 서브넷에 띄운 인스턴스는 공인 IP를 직접 붙여 주지 않는 한 밖으로 나가지 못한다.

인터넷과 직접 통신해야 하는 자원은 퍼블릭 서브넷에, 나머지는 프라이빗 서브넷에 둔다. 프라이빗 서브넷에는 인터넷 게이트웨이로 가는 경로가 없어서 보안 그룹을 실수로 전체 공개해도 인터넷에서 직접 들어올 수 없다.

| 퍼블릭 서브넷 | 프라이빗 서브넷 |
| --- | --- |
| 인터넷과 직접 통신하는 자원을 둔다 | 인터넷에서 직접 접속하면 안 되는 자원을 둔다 |
| 인터넷용 로드 밸런서, NAT 게이트웨이를 주로 둔다 | EKS 노드, 앱 서버, DB를 주로 둔다 |
| 공인 IP가 있고 보안 그룹이 허용하면 인터넷에서 직접 접속할 수 있다 | 인터넷에서 직접 접속할 수 없다 |

사용자 요청은 퍼블릭 서브넷의 로드 밸런서가 받아 프라이빗 서브넷의 앱으로 넘긴다.

## 라우팅 테이블

### 서브넷과 라우팅 테이블

서브넷에는 라우팅 테이블이 하나씩 붙는다. 서브넷을 떠나는 패킷은 이 표를 보고 어디로 갈지 정한다. 표의 한 줄은 "이 주소 범위로 가는 패킷은 여기로 보내라"는 뜻이다.

프라이빗 서브넷의 라우팅 테이블은 보통 이렇게 생겼다.

| 목적지 | 대상 |
| --- | --- |
| `10.0.0.0/16` | `local` |
| `0.0.0.0/0` | `nat-0a1b2c3d` |

첫 줄은 VPC 안으로 가는 패킷의 길이다. 모든 라우팅 테이블에 자동으로 들어가는 줄이라 VPC 안끼리는 따로 설정하지 않아도 통한다. 둘째 줄의 `0.0.0.0/0`은 모든 주소를 뜻한다. 첫 줄에 걸리지 않은 나머지는 전부 NAT 게이트웨이로 보낸다.

퍼블릭 서브넷의 표는 마지막 줄 하나만 다르다. 대상이 NAT 게이트웨이가 아니라 인터넷 게이트웨이(`igw-…`)다. 퍼블릭과 프라이빗을 가르는 것이 바로 이 한 줄이다.

### 경로 선택 규칙

`10.0.5.10`으로 가는 패킷은 두 줄에 모두 걸린다. `0.0.0.0/0`은 모든 주소를 품으니 당연히 걸리고, `10.0.0.0/16`에도 걸린다. 이럴 때는 <strong>범위가 가장 좁은 줄</strong>을 따른다. `/16`이 `/0`보다 좁으니 이 패킷은 `local`로 간다.

<LongestPrefixDemo client:visible />

그래서 `0.0.0.0/0`은 나머지를 모두 받는 줄이 된다. 다른 어느 줄에도 걸리지 않은 패킷이 이 줄로 간다. 이 규칙은 뒤의 VPC 엔드포인트에서 다시 쓰인다.

## 인터넷 게이트웨이와 NAT 게이트웨이

### 두 게이트웨이의 차이

둘 다 VPC 밖으로 나가는 출구지만 방향이 다르다.

- <strong>인터넷 게이트웨이</strong> — VPC와 인터넷을 양방향으로 잇는다. 공인 IP가 있는 인스턴스는 이 문으로 나갈 수 있고, 밖에서도 이 문을 지나 그 인스턴스로 들어올 수 있다.
- <strong>NAT 게이트웨이</strong> — 프라이빗 서브넷의 자원이 밖으로 나가게만 해 준다. 밖에서 먼저 들어오는 연결은 받지 않는다. NAT 게이트웨이 자신은 퍼블릭 서브넷에 두고 Elastic IP를 붙인다.

프라이빗 서브넷의 서버가 외부 API를 부르면 패킷은 표를 두 번 거친다. 프라이빗 서브넷의 표가 패킷을 NAT 게이트웨이로 보내고, NAT 게이트웨이가 있는 퍼블릭 서브넷의 표가 다시 인터넷 게이트웨이로 보낸다.

### 출발 주소 변환

프라이빗 서브넷의 노드에서 도는 Pod가 바깥 회사의 API를 부른다고 하자. 상대 서버의 로그에는 어떤 IP가 찍힐까?

Pod IP도 노드 IP도 아니다. <strong>NAT 게이트웨이의 공인 IP</strong>가 찍힌다. 출발 주소가 나가는 길에 두 번 바뀌기 때문이다.

#### 1\. Pod를 떠날 때

Pod IP가 `10.0.10.25`라고 하자. 패킷은 이 주소를 출발 주소로 달고 Pod를 떠난다.

#### 2\. 노드를 떠날 때

목적지가 VPC 범위 밖이면 VPC CNI가 출발 주소를 노드의 주 IP로 바꾼다. EKS의 기본 동작이다. 노드 IP가 `10.0.10.7`이라면 출발 주소는 이제 `10.0.10.7`이다. 목적지가 VPC 안이면 바꾸지 않고 Pod IP 그대로 보낸다.

#### 3\. NAT 게이트웨이를 떠날 때

NAT 게이트웨이가 출발 주소를 자기 공인 IP로 바꿔 인터넷으로 내보낸다. 공인 IP가 `203.0.113.10`이라면 상대 서버가 보는 출발 주소는 `203.0.113.10`이다. 응답은 이 주소로 돌아오고, NAT 게이트웨이와 노드가 바꿨던 주소를 거꾸로 되돌려 Pod까지 전달한다.

<SnatDemo client:visible />

그래서 바깥 회사가 IP로 허용 목록을 관리한다면 알려 줘야 할 주소는 NAT 게이트웨이의 공인 IP다. NAT 게이트웨이가 여러 개라면 노드가 어느 서브넷에 있느냐에 따라 나가는 IP가 달라지므로 전부 알려 줘야 한다.

### NAT 게이트웨이와 가용 영역 장애

NAT 게이트웨이는 만들 때 고른 가용 영역 하나에 속한다. 여러 가용 영역의 서브넷이 NAT 하나를 같이 쓰다가 NAT가 있는 영역에 장애가 나면 어떻게 될까? 다른 영역의 서버도 인터넷에 나가지 못한다. AWS 문서도 가용 영역마다 NAT를 하나씩 두고 같은 영역의 NAT를 쓰도록 라우팅하라고 권한다.

<NatZoneDemo client:visible />

EKS에서는 피해가 인터넷에서 그치지 않는다. 클러스터의 API 서버 엔드포인트를 공개로만 열어 두었다면 프라이빗 서브넷의 노드도 NAT를 거쳐 API 서버에 닿는다. NAT가 멈추면 노드와 컨트롤 플레인의 연결까지 함께 끊긴다.

NAT를 몇 개 둘지는 안정성과 비용 사이에서 정할 문제다. NAT 게이트웨이에는 시간당 요금이 붙으니, 가용 영역마다 두면 그만큼 비용이 늘어난다.

## VPC 엔드포인트

### 컨테이너 이미지를 받는 경로

새 Pod가 뜨면 노드는 ECR에서 컨테이너 이미지를 받는다. 이때 노드는 두 곳에 들른다. ECR에서 이미지의 목록(manifest)을 받고 실제 층(layer) 파일은 S3에서 받는다. 이미지 용량의 대부분은 층 파일이다.

ECR도 S3도 VPC 밖에 있는 서비스라 주소가 VPC 범위에 들지 않는다. 그러면 라우팅 테이블에서 걸리는 줄은 `0.0.0.0/0` 하나뿐이고 이미지는 NAT 게이트웨이를 거쳐 들어온다. 이미지 크기만큼의 트래픽이 NAT를 지나고, NAT가 멈추면 새 Pod는 이미지를 받지 못한다.

### 엔드포인트의 종류

VPC 엔드포인트는 NAT를 거치지 않고 AWS 서비스에 바로 닿는 길이다. 게이트웨이 엔드포인트와 인터페이스 엔드포인트, 두 종류가 있다.

| 구분 | 게이트웨이 | 인터페이스 |
| --- | --- | --- |
| 지원 서비스 | ❌ <strong>S3, DynamoDB만</strong> | ✅ ECR 등 대부분의 서비스 |
| 연결 방식 | ✅ 라우팅 테이블에 줄 하나 추가 | 서브넷에 꽂은 ENI의 사설 IP |
| 요금 | ✅ 추가 요금 없음 | ❌ <strong>시간당 요금과 데이터 처리 요금</strong> |
| IP 소모 | ✅ 없음 | ❌ 서브넷 IP 사용 |

### 게이트웨이 엔드포인트의 동작 방식

게이트웨이 엔드포인트가 더하는 줄은 S3의 주소 목록만 가리킨다. 모든 주소를 가리키는 `0.0.0.0/0`보다 좁으니, 앞에서 본 규칙대로 S3로 가는 패킷은 이 줄을 따른다. NAT로 가는 줄을 지우지 않아도 S3 트래픽만 지름길로 빠진다.

<ImagePullDemo client:visible />

S3 게이트웨이 엔드포인트 하나만 붙여도 이미지 용량의 대부분인 층 파일은 NAT를 지나지 않는다. 목록까지 NAT 밖으로 빼려면 ECR용 인터페이스 엔드포인트(`ecr.api`, `ecr.dkr`)를 더한다.

### NAT와 엔드포인트의 요금 차이

같은 이미지라도 어느 길로 받느냐에 따라 요금이 다르다. 2026년 11월 서울 리전 기준으로 이렇다.

| 길 | 시간당 요금 | GB당 처리 요금 |
| --- | --- | --- |
| NAT 게이트웨이 | $0.059 | $0.059 |
| 게이트웨이 엔드포인트 | 없음 | 없음 |
| 인터페이스 엔드포인트 | $0.013 (가용 영역마다) | $0.01 |

층 파일을 한 달에 1,000GB 받는다고 하자. NAT 게이트웨이로 받으면 처리 요금만 $59가 붙고, S3 게이트웨이 엔드포인트로 받으면 $0이다.

다만 인터페이스 엔드포인트는 쓰지 않아도 시간당 요금이 나간다. `ecr.api`와 `ecr.dkr`을 가용 영역 두 곳에 두면 한 달(730시간)에 약 $38이다. 층 파일이 S3로 빠지고 나면 ECR로 오는 것은 작은 목록뿐이라, 처리 요금을 아껴 이 값을 메우기는 어렵다. 요금만 보면 S3 게이트웨이 엔드포인트가 먼저이고, ECR 인터페이스 엔드포인트는 NAT가 멈춰도 이미지를 받으려고 더하는 쪽이다.

외부 요청이 남아 있으면 NAT 게이트웨이도 남는다. 엔드포인트로 줄어드는 것은 NAT의 시간당 요금이 아니라 처리 요금이다. 인터넷으로 나가는 데이터에는 전송 요금이 따로 붙는다.

## 보안 그룹

### 보안 그룹의 동작 방식

보안 그룹은 ENI에 붙는 방화벽이다. 허용 규칙만 있고 규칙에 없는 트래픽은 막는다.

노드의 보안 그룹에 "443 포트로 들어오는 것 허용" 규칙만 있고 나가는 규칙은 하나도 없다고 하자. 들어온 요청에 대한 응답은 나갈 수 있을까? 나간다. 보안 그룹은 <strong>들여보낸 연결을 기억하고</strong>, 그 연결의 응답은 나가는 규칙과 상관없이 통과시킨다.

덕분에 규칙은 연결을 시작하는 방향으로만 쓰면 된다. 들어오는 요청을 허용했다면 응답이 나갈 길까지 따로 열 필요는 없다.

> <strong>네트워크 ACL이란?</strong>  
> 서브넷 단위로 트래픽을 거르는 또 다른 방화벽이다. 연결을 기억하지 않아서 응답이 나갈 길도 규칙으로 열어야 한다. 기본값이 모두 허용이라 손대지 않는 경우가 많다.

### 다른 보안 그룹 참조

규칙의 출발지에는 IP 대신 다른 보안 그룹을 적을 수 있다. DB 보안 그룹에 "노드 보안 그룹에서 오는 5432 포트 허용" 한 줄을 두었다고 하자. 노드가 늘어나거나 새 노드로 바뀌어 IP가 달라져도, 그 노드에 같은 보안 그룹이 붙어 있는 한 규칙을 고칠 필요가 없다.

EKS의 클러스터 보안 그룹이 이 방식을 쓴다. 이 그룹에는 자기 자신에서 오는 트래픽을 모두 허용하는 규칙이 기본으로 들어 있다. EKS는 이 그룹을 컨트롤 플레인의 ENI와 관리형 노드 그룹의 노드에 함께 붙이므로, 둘은 별도 규칙 없이 서로 통한다.

## ENI

### ENI란

ENI(Elastic Network Interface)는 VPC 안의 가상 네트워크 카드다. 서버에 꽂는 랜카드를 소프트웨어로 만든 것이다. 카드 한 장마다 이런 것이 정해진다.

| 항목 | 설명 |
| --- | --- |
| 서브넷 | 한 장은 서브넷 하나에 속한다. 그래서 가용 영역도 한 곳에 묶인다 |
| IP | 주 사설 IP 하나와 보조 IP 여러 개 |
| 보안 그룹 | 카드 단위로 붙는다 |
| MAC 주소 | 카드마다 하나 |

ENI는 같은 가용 영역의 인스턴스에 붙였다 뗄 수 있다. 다만 인스턴스를 만들 때 생기는 기본 카드(eth0)는 떼지 못한다.

### 인스턴스 종류별 ENI 한도

인스턴스 종류마다 꽂을 수 있는 ENI 장수와 한 장에 붙일 수 있는 IP 수가 정해져 있다.

```bash
aws ec2 describe-instance-types --instance-types m7i.xlarge m8i.xlarge \
  --query 'InstanceTypes[].[InstanceType,NetworkInfo.MaximumNetworkInterfaces,NetworkInfo.Ipv4AddressesPerInterface]' \
  --output text
```

```text
m8i.xlarge	4	30
m7i.xlarge	4	15
```

둘 다 vCPU 4개에 메모리 16GiB인데, 한 장에 붙일 수 있는 IP 수는 두 배 차이가 난다. EKS에서는 이 값이 노드 하나에 띄울 수 있는 Pod 수를 정한다. 계산법은 다음 글에서 다룬다.

### ENI를 쓰는 자원

VPC 안에서 IP를 쓰는 것은 전부 ENI로 서브넷에 꽂혀 있다. 로드 밸런서도, NAT 게이트웨이도, Lambda도, 인터페이스 엔드포인트도 그렇다. VPC의 ENI를 종류별로 뽑아 보면 VPC 안에 무엇이 들어 있는지 한눈에 보인다.

```bash
aws ec2 describe-network-interfaces \
  --filters Name=vpc-id,Values=<vpc-id> \
  --query 'NetworkInterfaces[].[InterfaceType,Description]' \
  --output text
```

종류와 설명을 보면 누구의 카드인지 알 수 있다.

| 종류 | 설명 | 누구의 카드인가 |
| --- | --- | --- |
| `interface` | `ELB app/…` | ALB |
| `network_load_balancer` | `ELB net/…` | NLB |
| `nat_gateway` | `Interface for NAT Gateway …` | NAT 게이트웨이 |
| `vpc_endpoint` | `VPC Endpoint Interface …` | 인터페이스 엔드포인트 |
| `lambda` | `AWS Lambda VPC ENI…` | VPC에 붙인 Lambda |
| `interface` | `aws-K8S-i-…` | VPC CNI가 노드에 더 꽂은 카드 |
| `interface` | `Amazon EKS <클러스터 이름>` | EKS 컨트롤 플레인 |

서브넷 IP가 모자랄 때도 이 목록부터 본다. Pod 말고 누가 IP를 쓰고 있는지가 여기서 드러난다.

### EKS의 ENI 사용처

표의 마지막 두 줄이 EKS의 카드다.

- <strong>컨트롤 플레인 ENI</strong> — EKS의 API 서버는 AWS가 관리하는 다른 계정에서 돈다. 그 API 서버가 노드의 kubelet에 닿을 수 있도록 EKS가 내 서브넷에 이 카드를 꽂아 둔다. `kubectl exec`와 `kubectl logs`가 이 카드를 지난다.
- <strong>VPC CNI의 ENI</strong> — VPC CNI는 노드에 카드를 더 꽂고 그 보조 IP를 Pod에 하나씩 나눠 준다. Pod가 VPC 안에서 진짜 IP를 갖는 것은 이 때문이다.

<CniEniDemo client:visible />

실제로 VPC CNI는 Pod가 뜨기 전에 카드와 IP를 미리 잡아 둔다. 앞의 서브넷 절에서 노드가 미리 잡아 둔다고 한 IP가 바로 이것이다.

이 두 카드가 어떻게 쓰이는지는 다음 글에서 자세히 본다.

## 마치며

VPC는 주소 범위이고 서브넷은 그 범위를 가용 영역마다 자른 칸이다. 패킷은 서브넷에 붙은 라우팅 테이블을 보고 길을 정하며 가장 좁은 줄을 따른다. 밖으로 나가는 출구는 인터넷 게이트웨이와 NAT 게이트웨이이고, AWS 서비스로 가는 지름길은 VPC 엔드포인트다. 보안 그룹은 ENI마다 붙어 들여보낸 연결을 기억한다. VPC 안에서 IP를 쓰는 것은 모두 ENI로 서브넷에 꽂혀 있다.
