## 들어가며

회원가입을 마치면 환영 알림톡을 보내는 서비스를 하나 만든다고 해보자. 처음에는 가입 API 안에서 외부 메시징 API를 한 번 호출하면 끝난다.

요구사항은 금방 눈덩이처럼 불어난다. 결제가 실패하면 3일 뒤에 다시 안내해야 하고, 어드민에서는 특정 사용자에게 원하는 시각으로 예약을 걸고 싶어 한다. 밤마다 도는 배치는 가입자 전원에게 공지를 보낸다. 그러면 발송 코드가 API 서버, 어드민, 배치에 하나씩 생긴다.

이때부터 문제가 드러난다. 외부 API에 "5초당 100건" 같은 한도가 있다고 하자. 세 곳이 이 한도를 나눠 써야 하는데 서로의 호출량을 아는 곳은 없다. 3일 뒤 재안내를 보내려면 누군가 그 시각을 기억하고 있어야 한다. 배치로 보낸 공지 가운데 일부가 실패하면 누구에게 다시 보내야 하는지 알아내기도 어렵다.

세 곳이 각자 한도 안에서 보낸 양이 외부 API 앞에서 합쳐지면 이렇게 된다.

<ScatteredLimitDemo client:visible />

이쯤 되면 발송을 한곳에 모아 별도 서버로 떼어 내자는 이야기가 나온다. 이 시리즈는 알림 서버를 만들면서 마주하게 될 트레이드오프에 대해서 다룬다. 발송을 무엇에 맡길지, 외부 API의 한도를 어디서 지킬지, 보낸 기록을 어디에 쌓고 어떻게 읽을지, 대량 발송을 묶어 보낼 때 무엇이 엇갈리는지가 차례로 나온다. 결정마다 후보를 나란히 놓고, 각 후보가 무엇을 얻고 무엇을 내주는지를 따진다. 지금 발송 서버를 떼어 내려는 참이라면 결정하기 전에 짚어 볼 목록으로 읽어도 좋다.

1편은 그 첫 트레이드오프인 "발송을 어디에 맡길 것인가"를 다룬다. 이 질문은 다시 세 가지로 나뉜다.

1. 발송 요청을 어떻게 넘길 것인가
2. 큐를 무엇으로 만들 것인가
3. 예약 발송을 어떻게 표현할 것인가

## 발송 요청을 어떻게 넘길 것인가

API 서버, 어드민, 배치가 각자 외부 API를 부르던 코드를 한곳으로 모으려 한다. 방법은 넷이다. 코드를 모으는 공유 모듈, 실행을 모으는 발송 서버, 요청을 쌓아 두는 트랜잭셔널 아웃박스와 메시지 큐다. 넷을 같은 기준으로 견줘 보자.

-   요청한 쪽의 응답이 발송을 기다리는가
-   외부 API가 느려지거나 멈추면 요청한 쪽도 영향을 받는가
-   발송 요청이 사라질 틈이 있는가
-   외부 API의 한도를 어디서 지키는가
-   새로 운영해야 하는 것은 무엇인가

### 1. 공유 모듈로 코드를 모은다

서비스가 모놀리식이고, 서버도 한 대만 떠 있다면 이때는 발송 코드를 모듈 하나로 모으기만 해도 괜찮을 것이다. 템플릿 매핑, 전화번호 정규화, 외부 API 호출이 한곳에 모이고 새로 운영할 것도 없다. 서버가 한 대뿐이니 모듈 안의 카운터만으로 한도도 지킬 수 있다.

5초 동안 보낼 알림이 120건이라고 해 보자. 카운터가 100건에서 멈추고 남은 20건은 다음 5초로 미룬다.

<ModuleCounterDiagram scene={1} />

문제는 서버가 늘어날 때다. 서버를 여러 대로 늘리거나 배치를 다른 프로세스로 떼어 내면 같은 모듈이 여러 곳에서 따로 돈다. 코드는 모였어도 실행은 흩어지고, 각자 자기 카운터만 보므로 합치면 한도를 넘는다.

예를 들면 API 서버, 어드민, 배치가 같은 발송 모듈을 각자 품고 5초 동안 40건, 20건, 60건을 보낸다고 하자. 셋 다 자기 카운터로는 한도 안이지만 외부 API에는 합쳐서 120건이 들어가 20건이 거절된다.

<ModuleCounterDiagram scene={2} />

카운터를 Redis 같은 공유 저장소로 빼면 해결되지만, 그걸 구현했다면 거의 큐를 만들어서 사용하는 거나 다름없다.

세 서버가 보내기 전에 Redis의 카운터를 함께 확인하므로 외부 API에는 5초에 100건만 간다.

<ModuleCounterDiagram scene={3} />

부르는 방식에 따라 약점도 갈린다. 동기로 부르면 외부 API의 지연과 장애, 한도에 걸려 기다리는 시간이 요청한 쪽 응답에 그대로 붙는다. 프로세스 안에서 비동기로 넘기면 응답은 빨라지지만, 못 보낸 요청은 메모리에 있다가 배포나 재시작 때 사라진다. 모듈을 고칠 때마다 쓰는 서비스를 모두 다시 배포해야 하는 부담도 있다.

### 2. 발송 서버를 API로 부른다

실행까지 한곳에 모으려면 발송 서버를 따로 띄우면 된다. 각 서비스가 HTTP로 발송 서버를 호출하는 방식을 살펴보자. 발송 로직을 고쳐도 발송 서버만 다시 배포하면 되고, 부르는 쪽은 HTTP만 알면 되니 언어나 프레임워크를 가리지 않는다.

외부 API를 부르는 곳이 발송 서버 하나로 줄어드니 한도를 지킬 곳도 하나로 정해진다.

앞의 예처럼 세 곳이 5초에 120건을 보내려 해도 발송 서버의 카운터가 100건에서 멈춘다.

<SendServerDiagram scene={1} />

발송 서버를 여러 대로 늘리면 요청을 나눠 줄 로드밸런서를 앞에 두게 된다. 앞의 방식을 그대로 쓰면 발송 서버마다 카운터를 따로 세게 되고, 유량 제어도 제대로 되지 않는다.

로드밸런서가 120건을 두 발송 서버에 60건씩 나눠 보낸다고 하자. 두 발송 서버 모두 자기 카운터로는 한도 안이지만 외부 API에는 합쳐서 120건이 간다.

<SendServerDiagram scene={2} />

카운터를 다시 한곳에 모으려면 모든 요청이 지나가는 로드밸런서에서 유량을 제어하면 된다. 120건이 들어오면 5초에 100건만 두 발송 서버에 50건씩 넘기고 남은 20건은 거절한다.

<SendServerDiagram scene={3} />

대신 감수할 것이 세 가지 있다.

-   <strong>재시도의 주체가 각 서비스가 된다.</strong> 넘친 요청은 쌓이지 않고 거절되므로, API 서버, 어드민, 배치가 저마다 재시도 로직을 갖춰야 한다. 최종 재시도까지 실패했을 때는 실패한 메시지 발송을 보상하기 위한 대책도 필요해진다.
-   <strong>로드밸런서는 들어온 요청 수만 센다.</strong> 발송 서버가 실패한 건을 외부 API에 다시 보내는 호출은 이 숫자에 잡히지 않는다.
-   <strong>로드밸런서도 여러 대가 되면 같은 문제가 반복된다.</strong> 노드마다 카운터를 따로 세지 않으려면 Redis 같은 공유 저장소에 카운터를 둬야 한다.

<details>
<summary>Nginx와 Envoy에서는</summary>

Nginx의 `limit_req`는 넘친 요청을 기본으로 503으로 돌려주고, `limit_req_status`로 429 같은 다른 코드로 바꿀 수 있다. `burst`를 주면 그 수만큼은 바로 거절하지 않고 늦춰서 흘려보내는데, 기본값은 0이다. 카운터는 Nginx 한 대의 공유 메모리 영역에 있고, 여러 대 사이에서 이 영역을 맞추는 `sync`는 상용 구독에서만 쓸 수 있다.

Envoy는 여러 대가 한도를 함께 지키도록 별도의 전역 rate limit 서비스를 gRPC로 부른다. 공식 참조 구현은 Go로 작성됐고 카운터를 Redis에 둔다.

</details>

이때 발송 서버가 언제 응답하느냐에 따라 두 갈래로 나뉜다.

-   <strong>발송이 끝난 뒤에 응답한다.</strong> 요청한 쪽은 결과를 바로 안다. 대신 외부 API의 지연과 장애가 요청한 쪽까지 그대로 번진다. 발송 서버가 멈추면 요청 자체가 실패하므로 다시 보낼 책임도 요청한 쪽에 남는다. 한도에 걸리면 발송 서버가 기다린 만큼 응답이 늦어지고, 429를 돌려주면 다시 보낼 시점을 요청한 쪽이 정해야 한다. 가입자 전원에게 공지를 보내는 배치라면 결국 배치가 직접 속도를 조절하게 된다.
-   <strong>받자마자 `202 Accepted`로 응답한다.</strong> 요청한 쪽은 빨라지지만 발송 서버는 받은 요청을 어딘가에 쌓아 두고 천천히 보내야 한다. 메모리에 쌓으면 재시작 때 사라지고, 저장소에 쌓으면 큐를 만드는 것이다.

가입 처리에 0.2초, 외부 API에 3초가 걸린다고 해 보자. 발송이 끝난 뒤 응답하면 가입 응답은 3.2초에, 202로 응답하면 0.2초에 돌아온다.

<ResponseTimingDemo client:visible />

발송 후에 응답하면 외부 API의 사정이 번지고, 받자마자 응답하면 쌓아 둘 곳이 필요하다. 어느 쪽이든 큐가 필요해진다.

### 3. 트랜잭셔널 아웃박스로 커밋과 함께 적는다

큐가 필요하다면 가장 가까운 곳은 이미 쓰고 있는 DB다. 가입과 같은 트랜잭션으로 발송 요청을 아웃박스 테이블에 적고, 발송 워커가 이 테이블에서 꺼내 보낸다. 가입이 커밋되면 발송 요청도 커밋되고, 롤백되면 함께 사라진다. 요청은 거절되지 않고 쌓이며 실패한 건은 워커가 다시 시도하므로, 부르는 쪽은 재시도도 실패 보상도 갖출 필요가 없다.

가입 요청 하나가 들어왔다고 해 보자. 회원 테이블과 아웃박스 테이블에 한 행씩, 한 트랜잭션으로 적힌다.

<OutboxTableDiagram scene={1} />

대신 큐의 기능을 직접 만들어야 한다. 워커 여러 대가 같은 행을 집지 않도록 `SELECT … FOR UPDATE SKIP LOCKED`로 잠그고, 재시도 간격을 관리하고, 처리한 행을 정리하고, 워커 사이에서 한도를 함께 지킬 방법도 만들어야 한다. 테이블을 주기적으로 읽는 만큼 운영 DB에 부하가 가고, 읽는 주기만큼 발송도 늦어진다.

발송 워커 두 대가 1초마다 아웃박스 테이블을 읽는다고 해 보자. 행이 어떤 상태에 있느냐에 따라 직접 만들어야 할 일이 달라진다.

<OutboxTableDiagram scene={2} />

트랜잭셔널 아웃박스는 대개 메시지 브로커와 함께 소개된다. 아웃박스 테이블에 적은 행을 별도 프로세스가 읽어 Kafka나 RabbitMQ로 옮기는 식이다. 그런데 아웃박스 테이블은 그 자체로 이미 큐다. 적은 순서대로 쌓이고, 꺼내 간 행은 처리됨으로 표시한다. 발송 워커가 이 테이블을 바로 읽을 수 있다면, 같은 일을 하는 큐를 하나 더 두고 그 사이를 옮기는 프로세스까지 운영하는 것은 오버엔지니어링이라고 생각한다.

두 구성을 나란히 그려 보면 큐 역할을 하는 것이 몇 개인지 드러난다.

<OutboxBrokerDiagram />

브로커가 값을 하는 때는 따로 있다. 서비스마다 DB가 나뉘어 있어서 받는 쪽이 아웃박스 테이블을 읽을 수 없을 때, 또는 하나의 이벤트를 여러 서비스가 구독해야 할 때다. 알림 서버 하나가 같은 DB에 적힌 발송 요청을 꺼내 가는 구조라면 둘 다 해당하지 않는다.

### 4. 메시지 큐에 넣고 바로 돌아온다

큐의 기능을 테이블 위에 직접 만들기 부담스럽다면 메시지 큐에 맡긴다. 요청한 쪽은 큐에 넣고 바로 돌아오고, 발송 워커가 꺼내 외부 API를 부른다. 아웃박스에서 직접 만들던 잠금, 재시도, 정리는 대부분의 큐가 기본으로 해 준다. 외부 API가 느려지거나 멈춰도 요청한 쪽은 영향을 받지 않고, 몰린 요청은 큐에 쌓였다가 워커가 지키는 한도에 맞춰 흘러간다.

앞의 예처럼 세 곳이 5초 동안 120건을 넣는다고 해 보자. 워커는 5초에 100건만 꺼내 보내고 남은 20건은 큐에서 기다렸다가 다음 5초에 나간다.

<QueueBufferDiagram />

대신 숙제가 생긴다.

-   <strong>결과를 바로 알 수 없다.</strong> 요청한 쪽이 아는 것은 "맡겼다"까지다. 실제로 보냈는지 확인하려면 발송 이력을 남기고 조회할 길을 따로 만들어야 한다. [3편](/ko/blog/bullmq-notification-part-3-delivery-history)과 [4편](/ko/blog/bullmq-notification-part-4-reading-history)이 이 이야기다.
-   <strong>큐를 새로 운영해야 한다.</strong> 큐가 새로운 인프라이자 새로운 장애 지점이 된다. 무엇으로 만들지는 다음 절에서 따진다.
-   <strong>같은 알림이 두 번 갈 수 있다.</strong> 외부 API는 보냈는데 응답만 끊기면 워커는 실패로 보고 다시 보낸다. 그래서 발송마다 식별 키를 두고 중복을 걸러야 한다.
-   <strong>발송 요청이 사라질 틈이 있다.</strong> 가입은 DB에 커밋됐는데 큐에 넣기 직전에 서버가 죽으면 발송 요청이 사라진다. DB와 큐에 나눠 쓰는 탓에 아웃박스가 막아 주던 틈이 다시 열린다.

커밋 직후 서버가 죽었을 때, 큐에 바로 넣은 쪽과 아웃박스에 적은 쪽에 무엇이 남는지 나란히 놓았다.

### 넘기는 방식을 고르는 기준

네 방식 가운데 어느 하나가 늘 이기지는 않는다. 서버가 몇 대인지, 요청을 한 건이라도 잃으면 안 되는지에 따라 답이 갈린다.

-   <strong>서버가 한 대뿐인 모놀리식이고 발송량이 한도에 한참 못 미친다면 공유 모듈로 충분하다.</strong> 얻는 것은 새로 운영할 것이 없다는 점이다. 내주는 것은 서버가 늘면 한도를 지킬 수 없고, 모듈을 고칠 때마다 쓰는 서비스를 모두 다시 배포해야 한다는 점이다.
-   <strong>부르는 쪽이 발송 결과를 바로 알아야 하고 재시도를 각자 맡을 수 있다면 발송 서버 API가 맞다.</strong> 얻는 것은 발송 로직과 한도가 한곳에 모이고 결과를 바로 안다는 점이다. 내주는 것은 외부 API의 지연과 장애가 부르는 쪽까지 번지고, 넘친 요청의 재시도와 실패 보상을 서비스마다 갖춰야 한다는 점이다.
-   <strong>결제 결과처럼 한 건도 잃으면 안 되는 알림이 중심이라면 아웃박스가 맞다.</strong> 얻는 것은 가입과 발송 요청이 한 트랜잭션으로 커밋되어 틈이 없다는 점이다. 내주는 것은 잠금, 재시도 간격, 정리, 워커 사이의 한도를 테이블 위에 직접 만들어야 하고, 조회 부하를 운영 DB가 받는다는 점이다.
-   <strong>서버가 여러 대이고 지연 발송, 재시도, 한도 공유가 필요하다면 메시지 큐가 가깝다.</strong> 얻는 것은 이 기능들을 큐가 기본으로 해 준다는 점이다. 내주는 것은 큐라는 새 인프라와 커밋과 적재 사이의 틈이다. 그 틈은 "보냈어야 하는데 보내지 않은 건"을 주기적으로 찾아 다시 넣는 배치로 메울 수 있다.

## 큐를 무엇으로 만들 것인가

아웃박스든 메시지 큐든 큐를 두기로 했다면 이제 무엇으로 만들지 정할 차례다. 그 전에 앞의 후보들이 왜 하나같이 큐로 모였는지부터 짚어 보자.

### 왜 큐인가

큐는 요청을 넣는 쪽과 꺼내 처리하는 쪽 사이에 놓인 대기열이다. 이 대기열 하나가 앞에서 본 문제를 네 가지로 풀어 준다.

-   <strong>몰린 요청을 받아 두고 일정한 속도로 내보낸다.</strong> 넣는 속도와 꺼내는 속도를 따로 가져갈 수 있어서 5초에 120건이 들어와도 워커는 100건씩만 꺼낸다. 외부 API의 한도를 지키면서도 넘친 요청을 거절하지 않는다.
-   <strong>요청한 쪽과 보내는 쪽을 떼어 놓는다.</strong> 요청한 쪽은 큐에 넣고 바로 돌아온다. 외부 API가 느려지거나 멈춰도 그 영향은 워커에서 멈추고 요청한 쪽까지 번지지 않는다. 발송량이 늘면 워커만 늘리면 된다.
-   <strong>실패를 큐 안에서 처리한다.</strong> 실패한 요청은 큐로 돌아가 간격을 두고 다시 시도된다. API 서버, 어드민, 배치가 저마다 재시도 로직을 갖출 필요가 없다.
-   <strong>보낼 시각을 대신 기억한다.</strong> 3일 뒤에 보낼 요청을 넣어 두면 그 시각까지 붙잡아 두었다가 내보낸다.

다만 모든 큐가 이 일을 똑같이 해 주지는 않는다. 그래서 후보를 다음 기준으로 견줘 본다.

-   3일 뒤 재안내처럼 정한 시각까지 요청을 붙잡아 둘 수 있는가
-   실패한 건을 간격을 두고 다시 시도할 수 있는가
-   인증번호처럼 급한 알림이 쌓여 있는 공지보다 먼저 나갈 수 있는가
-   워커가 여러 대여도 외부 API의 한도를 함께 지킬 수 있는가
-   서버가 죽어도 쌓인 요청이 남는가
-   새로 운영해야 하는 것은 무엇인가

후보는 다섯이다. 이미 쓰고 있는 DB, Redis 위에 만든 작업 큐, SQS 같은 관리형 큐, RabbitMQ, 그리고 Kafka다.

### 1. 이미 쓰는 DB에 쌓는다

아웃박스 절의 테이블을 그대로 큐로 쓴다. 워커가 `SKIP LOCKED`로 서로 다른 행을 집어 가고, 바라는 기능은 대부분 열 하나와 조건 하나로 만든다. 보낼 시각이 지난 행만 집으면 지연 발송이, 실패한 행의 보낼 시각을 뒤로 미루면 재시도 간격이 된다. 우선순위 열로 정렬하면 인증번호를 앞에 세울 수 있다.

지금이 10시 정각이고 발송 요청 테이블에 다섯 행이 있다고 해 보자. 워커가 쿼리 하나로 두 행을 집으면 지연 발송, 재시도 간격, 우선순위가 행마다 이렇게 갈린다.

<DbQueueTableDiagram />

가입과 같은 DB에 두면 발송 요청을 가입과 한 트랜잭션으로 넣을 수 있어 커밋과 적재 사이의 틈이 없다. 사실상 아웃박스와 같은 구조다. 새로 운영할 것도 없고 DB가 남아 있는 한 요청도 남는다.

아웃박스의 비용도 그대로 진다. 워커 사이의 한도 공유는 따로 만들고 처리한 행도 지워야 하며, 부하는 운영 DB가 받는다. 공지 1만 건을 한꺼번에 넣으면 1만 행이 들어가고, 집을 때와 끝낼 때 행마다 갱신이 일어나고, 다 보내면 1만 행을 지운다. 가입과 결제를 처리하는 DB가 이 일을 함께 떠안는다.

워커 두 대가 1초마다 테이블을 읽는다고 하고 구성을 그려 보면, 직접 만들어야 하는 부품 둘이 함께 보인다.

<QueueArchitectureDiagram kind="db" />

DB를 큐로 쓰는 것이 낯선 선택은 아니다. 이 방식을 라이브러리로 묶어 둔 것도 있다.

<details>
<summary>DB를 큐로 쓰는 라이브러리</summary>

Rails 8은 새 애플리케이션에 Solid Queue를 기본 큐로 설정한다. MySQL, PostgreSQL, SQLite 위에서 돌고, 쓸 수 있는 DB에서는 `FOR UPDATE SKIP LOCKED`로 워커끼리 행을 나눠 갖는다. 지연 실행과 우선순위를 지원하지만 자동 재시도는 없어서 Active Job의 재시도에 기댄다. 워커는 기본으로 0.1초마다 테이블을 조회한다.

Node.js에는 PostgreSQL 위에서 도는 pg-boss가 있다. 역시 `SKIP LOCKED`로 작업을 나눠 갖고, 지연 실행, 지수 백오프 재시도, 우선순위를 지원한다.

</details>

이 안이 맞는 때는 발송량이 많지 않고 운영 DB에 여유가 있을 때다.

### 2. Redis 위에 만든 작업 큐를 쓴다

BullMQ나 Sidekiq처럼 Redis를 저장소로 쓰는 작업 큐 라이브러리를 쓴다. Redis 자체는 큐가 아니지만 라이브러리가 그 자료구조 위에 큐의 기능을 얹어 둔다. 지연 실행, 간격을 두는 재시도, 우선순위가 기본으로 있고, BullMQ는 워커가 여러 대여도 한도를 함께 지키는 rate limiter까지 준다. 공유 모듈에서 카운터를 Redis로 빼면 거의 큐를 만들어 쓰는 거나 다름없다고 했는데, 그 큐를 라이브러리가 이미 만들어 둔 셈이다.

가입부터 외부 API까지 그려 보면 Redis 하나가 대기, 지연, 우선순위, 한도 카운터를 모두 맡는다.

<QueueArchitectureDiagram kind="redis" />

우선순위가 왜 필요한지는 숫자에서 드러난다. 공지 1만 건이 큐에 쌓여 있을 때 인증번호 한 건이 들어왔다고 하자. 워커가 5초에 100건씩 보내면 공지 1만 건을 다 보내는 데 500초, 8분 20초가 걸린다.

<PriorityDemo client:visible />

공지 1만 건을 넣어도 운영 DB는 그 부하를 떠안지 않는다.

Redis에 맡기면 따라오는 부담도 있다.

-   <strong>Redis를 큐에 맞게 운영해야 한다.</strong> 캐시용 설정을 그대로 쓰면 안 된다. 메모리가 찰 때 키를 지우는 설정이면 쌓인 작업이 사라지므로, BullMQ는 `maxmemory-policy`를 `noeviction`으로 두라고 권한다. 디스크에 남기는 설정도 따로 켜야 한다.
-   <strong>쌓인 요청이 메모리에 있다.</strong> 공지 1만 건을 넣으면 작업 1만 개가 Redis 메모리에 올라간다. 발송량이 늘면 메모리도 함께 늘려야 한다.
-   <strong>내구성이 DB보다 느슨하다.</strong> AOF를 켜고 기본 설정대로 1초마다 디스크에 쓰도록 두어도, 장애가 나면 마지막 1초 분량을 잃을 수 있다.
-   <strong>가입과 한 트랜잭션으로 묶을 수 없다.</strong> 앞에서 본 커밋과 적재 사이의 틈이 그대로 남는다.

<details>
<summary>BullMQ와 Sidekiq에서는</summary>

BullMQ의 rate limiter는 워커 옵션에 `limiter: { max, duration }`으로 건다. 한 큐에 워커가 10대 있어도 한도는 큐 전체에 걸린다. 우선순위는 1부터 2,097,151까지의 숫자로 주고 숫자가 작을수록 먼저 나간다. 우선순위를 붙인 작업은 넣는 비용이 O(log n)이라 일반 작업보다 무겁다.

Sidekiq은 Ruby용이다. 실패한 작업을 기본 25번, 약 20일에 걸쳐 지수 백오프로 다시 시도한다. 여러 프로세스가 Redis로 한도를 함께 지키는 rate limiting은 유료인 Sidekiq Enterprise에 들어 있다.

</details>

이 안이 맞는 때는 지연 발송, 재시도, 우선순위, 한도 공유를 직접 만들고 싶지 않고, Redis를 하나 더 운영할 여력이 있을 때다.

### 3. SQS 같은 관리형 큐를 쓴다

큐를 직접 운영하고 싶지 않다면 클라우드가 운영하는 큐를 쓴다. AWS의 SQS가 대표적이다. 띄울 서버가 없고 메시지는 여러 가용 영역에 복사돼 저장된다. Redis처럼 메모리를 늘리거나 디스크 설정을 챙길 일도 없다.

재시도는 SQS의 동작 방식에 이미 들어 있다. 워커가 메시지를 받으면 메시지는 큐에 남은 채 다른 워커에게 잠시 보이지 않는다. 이 시간을 visibility timeout이라고 하고 기본값은 30초다. 워커가 그 안에 메시지를 지우지 못하면 메시지가 다시 보이고, 다른 워커가 받아 간다. 정해 둔 횟수만큼 받고도 지워지지 않은 메시지는 dead-letter queue로 옮겨진다.

알림 서버가 바라는 것 가운데 셋은 빠진다.

-   <strong>지연은 15분까지다.</strong> 메시지마다 지연을 줄 수 있지만 최대 15분이라 3일 뒤 재안내는 SQS만으로 표현할 수 없다. AWS도 15분을 넘는 예약에는 EventBridge Scheduler를 권한다.
-   <strong>큐 안에서 우선순위를 줄 수 없다.</strong> 인증번호를 공지보다 먼저 보내려면 큐를 둘로 나누고, 워커가 급한 큐를 먼저 읽도록 직접 짜야 한다.
-   <strong>워커 사이의 한도 공유가 없다.</strong> 워커가 여러 대면 공유 모듈에서 겪던 문제가 그대로 돌아온다. 카운터를 다시 Redis 같은 곳에 둬야 한다.

3일 뒤 재안내, 인증번호 우선순위, 워커 두 대의 5초에 100건 한도를 SQS로 모두 풀어 보면 이렇게 된다.

<QueueArchitectureDiagram kind="sqs" />

<details>
<summary>SQS의 기본값과 제약</summary>

visibility timeout은 기본 30초, 최대 12시간이다. 메시지는 기본 4일, 최대 14일까지 보관된다. 지연은 큐 전체에 거는 delay queue와 메시지마다 거는 message timer 둘 다 최대 15분이다.

표준 큐는 최소 한 번 전달을 보장하므로 같은 메시지가 두 번 이상 올 수 있고, 순서도 최대한 지키려 할 뿐 보장하지 않는다. FIFO 큐는 메시지 그룹 안에서 순서를 지키고 중복 제거 ID로 같은 메시지를 걸러 준다. 대신 고처리량 모드를 켜지 않으면 API 호출이 초당 300번으로 묶이고, 10건씩 묶어 보내도 초당 3,000건이 한계다.

</details>

이 안이 맞는 때는 이미 AWS 위에서 서비스를 운영하고 있고, 큐를 직접 운영할 여력이 없을 때다. 지연, 우선순위, 한도 공유를 밖에서 채우는 비용은 따로 치러야 한다.

### 4. RabbitMQ를 쓴다

RabbitMQ는 메시지 브로커다. 보내는 쪽이 exchange에 메시지를 넣으면 라우팅 규칙에 따라 큐로 들어가고, 워커가 꺼내 처리한 뒤 ack를 보낸다. ack가 오지 않거나 워커가 거절하면 메시지는 큐로 돌아간다. 한 건을 한 워커가 처리하는 작업 큐로 쓰기에 잘 맞는다.

우선순위는 기본으로 있다. classic 큐는 선언할 때 `x-max-priority`로 우선순위 단계를 정하고, quorum 큐는 4.3부터 따로 설정하지 않아도 32단계 우선순위를 쓸 수 있다. 실패 처리도 갖췄다. quorum 큐는 같은 메시지를 기본 20번까지 다시 전달하고, 그래도 처리되지 않으면 dead-letter exchange로 보낸다.

그래도 걸리는 것이 셋 있다.

-   <strong>재시도에 간격이 없다.</strong> 거절한 메시지는 곧바로 큐로 돌아온다. 외부 API가 잠깐 멈췄을 때 같은 메시지를 연달아 다시 보내지 않으려면, TTL을 건 대기 큐와 dead-letter exchange를 엮어 간격을 직접 만들어야 한다.
-   <strong>한도 공유가 없다.</strong> prefetch로 워커가 한 번에 받아 갈 양은 정할 수 있지만, 이는 동시에 처리하는 개수를 묶을 뿐 5초에 100건 같은 속도를 지켜 주지는 않는다.
-   <strong>브로커를 운영해야 한다.</strong> 큐를 복제하려면 노드 여러 대로 클러스터를 꾸리고 그 클러스터를 지켜야 한다.

재시도 간격과 한도까지 갖춰 구성을 그려 보면 이렇다. 우선순위는 브로커가 맡고, 점선은 직접 엮는 부분이다.

<QueueArchitectureDiagram kind="rabbitmq" />

그중 재시도 대기 큐를 가까이서 보자. 외부 API가 잠깐 멈춰 실패한 발송을 30초 뒤에 다시 보내려면 대기 큐를 하나 더 두고 이렇게 엮는다.

<RabbitRetryDiagram />

지연 발송은 버전에 따라 다르다. 4.4부터는 quorum 큐가 `x-opt-delivery-time` 헤더로 지연 전달을 직접 지원한다. 그 전 버전에서는 TTL과 dead-letter exchange를 엮거나 지연 플러그인을 써야 했다.

<details>
<summary>RabbitMQ 지연 플러그인의 한계</summary>

`rabbitmq-delayed-message-exchange` 플러그인은 지연 메시지를 한 노드에만 저장한다. 그 노드를 잃거나 플러그인을 끄면 기다리던 메시지도 사라진다. 플러그인 스스로 지연 메시지가 많은 경우에는 맞지 않고 지연도 하루이틀까지를 염두에 뒀다고 밝힌다. 지금은 RabbitMQ 팀이 더 이상 관리하지 않으며 대신 quorum 큐의 지연 전달이나 TTL과 dead-letter exchange를 엮는 방식을 권한다.

</details>

이 안이 맞는 때는 알림 말고도 여러 서비스가 메시지를 주고받아 이미 브로커를 운영하고 있거나, 메시지를 여러 큐로 나눠 보내는 라우팅이 필요할 때다.

### 5. Kafka를 쓴다

Kafka는 큐라기보다 로그다. 메시지는 토픽의 파티션에 순서대로 쌓이고 읽어도 지워지지 않는다. 소비자는 파티션마다 어디까지 읽었는지를 오프셋으로 기억한다. 그래서 같은 이벤트를 여러 서비스가 각자 읽을 수 있고 필요하면 처음부터 다시 읽을 수도 있다. 아웃박스 절에서 브로커가 값을 하는 때로 꼽은 "하나의 이벤트를 여러 서비스가 구독해야 할 때"가 Kafka가 가장 잘하는 일이다.

알림 발송 같은 작업 큐로 쓰면 맞지 않는 곳이 생긴다.

-   <strong>한 건씩 실패를 처리하기 어렵다.</strong> 소비자 그룹은 오프셋으로 "여기까지 읽었다"만 남긴다. 중간의 한 건이 실패하면 그 자리에서 멈춰 재시도하거나, 재시도용 토픽을 따로 만들어 옮겨야 한다.
-   <strong>지연과 우선순위가 없다.</strong> 3일 뒤 재안내도, 인증번호가 공지를 앞지르는 것도 직접 만들어야 한다.
-   <strong>병렬성이 파티션 수에 묶인다.</strong> 한 소비자 그룹 안에서 한 파티션은 한 소비자만 읽는다. 워커를 6대로 늘려도 파티션이 4개면 4대만 일한다.
-   <strong>운영이 가장 무겁다.</strong> 브로커 여러 대로 클러스터를 꾸려야 하고 알림 발송 하나를 위해 들이기에는 크다.

Kafka 위에서 알림 발송까지 하도록 구성을 그려 보면, 작업 큐에 필요한 부품을 대부분 직접 붙여야 한다.

Kafka 4.2부터 share group이 정식 기능이 됐다. share group에서는 파티션 하나를 여러 소비자가 함께 읽고, 레코드마다 처리 결과를 알리며, 몇 번 전달됐는지를 센다. 정해 둔 횟수만큼 전달하고도 처리되지 않은 레코드는 더 보내지 않는다. 작업 큐에 한 걸음 다가섰지만 파티션 안의 순서는 보장하지 않는다. 지연 전달과 우선순위는 여전히 없다.

이 안이 맞는 때는 알림이 이미 Kafka로 흐르는 이벤트에서 시작될 때다. 그때도 Kafka는 이벤트를 받는 입구로 두고 발송 자체는 작업 큐에 맡기는 편이 낫다.

### 큐를 고르는 기준

다섯 후보 가운데서도 늘 이기는 쪽은 없다. 이미 운영하고 있는 것과 직접 만들 여력이 답을 가른다.

-   <strong>발송량이 많지 않고 운영 DB에 여유가 있다면 DB 테이블로 충분하다.</strong> 얻는 것은 새로 운영할 것이 없고 가입과 한 트랜잭션으로 묶인다는 점이다. 내주는 것은 운영 DB가 받는 조회 부하와, 직접 만들어야 하는 한도 공유와 정리 작업이다.
-   <strong>지연, 재시도, 우선순위, 한도 공유를 직접 만들고 싶지 않다면 Redis 위의 작업 큐가 가장 가깝다.</strong> 얻는 것은 네 기능이 라이브러리에 들어 있다는 점이다. 내주는 것은 Redis를 큐에 맞게 운영하는 수고, 장애 때 마지막 1초를 잃을 수 있는 내구성, 가입과 따로 커밋되는 틈이다.
-   <strong>AWS 위에서 운영하고 큐를 운영할 여력이 없다면 SQS가 낫다.</strong> 얻는 것은 띄울 서버가 없고 메시지가 여러 가용 영역에 남는다는 점이다. 내주는 것은 15분 넘는 예약, 우선순위, 한도 공유를 EventBridge Scheduler, 큐 두 개, 공유 카운터로 따로 채우는 수고다.
-   <strong>이미 RabbitMQ를 운영하고 있다면 굳이 Redis를 하나 더 들일 이유가 적다.</strong> 얻는 것은 우선순위, 재전달, dead-letter를 브로커가 맡아 준다는 점이다. 내주는 것은 직접 엮어야 하는 재시도 간격과 한도 공유, 그리고 브로커 클러스터 운영이다.
-   <strong>알림이 이미 Kafka로 흐르는 이벤트에서 시작된다면 Kafka는 입구로 두고 발송은 작업 큐에 맡긴다.</strong> 얻는 것은 같은 이벤트를 여러 서비스가 읽고 다시 읽을 수 있는 구조다. Kafka만으로 발송까지 하려면 재시도, 지연, 우선순위, 한도를 모두 직접 만들어야 한다.

## 예약 발송을 어떻게 표현할 것인가

큐를 정했다면 이제 예약이 남았다. 들어가며의 요구사항에는 바로 보내지 않는 알림이 셋 있었다.

-   결제가 실패하면 3일 뒤에 다시 안내한다. 보낼 시각이 결제 실패 시각에서 정해지고 그사이 다시 결제하면 보내지 않아야 한다.
-   어드민이 특정 사용자에게 원하는 시각으로 예약을 건다. 시각을 사람이 정하고 보내기 전에 취소하거나 바꿀 수 있어야 한다.
-   밤마다 도는 배치가 가입자 전원에게 공지를 보낸다. 같은 시각에 되풀이되고 한 번에 나가는 양이 많다.

셋 모두 보내기로 정한 때와 실제로 보내는 때 사이가 길게는 며칠이다. 그동안 사용자는 다시 결제하고, 어드민은 문구를 고치고, 서버는 여러 번 배포된다. 예약은 그 시간을 버티고, 보낼 때 아직 보내야 하는지 다시 따져야 한다.

월요일 15시에 결제가 실패해 목요일 15시로 재안내를 걸었다고 해 보자. 3일 사이에 이런 일이 일어날 수 있다.

<ScheduleGapDiagram />

그래서 후보를 다음 기준으로 견줘 본다.

-   보내기 전에 예약을 찾아 취소하거나 바꿀 수 있는가
-   그사이 조건이 바뀌면 보내지 않을 수 있는가
-   얼마나 먼 시각까지, 얼마나 정확하게 걸 수 있는가
-   배포와 재시작을 거쳐도 예약이 남는가
-   새로 운영해야 하는 것은 무엇인가

후보는 배치가 조건으로 찾는 방법, 예약 테이블, 큐의 지연 작업, 관리형 스케줄러 넷이다.

### 1. 배치가 조건으로 찾아 보낸다

예약을 어디에도 적지 않고 배치가 주기적으로 돌며 보낼 사람을 도메인 상태에서 찾는다. 3일 뒤 재안내라면 결제가 실패한 지 3일이 지났고, 아직 다시 결제하지 않았고, 재안내를 받은 적 없는 사용자를 찾아 큐에 넣는다. 보낼 시각은 결제 실패 시각과 조건 안에 들어 있다.

다시 결제한 사용자는 조건에서 저절로 빠지므로 취소 로직이 필요 없다. 문구나 조건을 바꾸면 다음 배치부터 반영된다. 적어 둔 예약이 없으니 재시작 때 사라질 것도 없고, 배치가 한 번 실패해도 다음 배치가 다시 찾는다.

다만 "재안내를 받은 적 없는" 조건을 쓰려면 보낸 기록은 남겨야 한다. 기록이 없으면 배치가 돌 때마다 또 보낸다.

배치가 매일 10시에 돈다고 해 보자. 사용자 A와 B 모두 월요일 15시에 결제가 실패했고, B만 수요일 14시에 다시 결제했다.

<BatchScanDiagram />

A가 19시간 늦은 것은 목요일 10시 배치 때 실패한 지 2일 19시간밖에 되지 않았기 때문이다.

걸리는 것은 넷이다.

-   <strong>보내는 시각이 배치 주기에 묶인다.</strong> 하루 한 번 도는 배치라면 최대 하루 늦게 나간다. 주기를 1분으로 줄이면 그만큼 자주 조회한다.
-   <strong>상태로 찾을 수 없는 예약은 담지 못한다.</strong> 어드민이 다음 주 화요일 15시로 거는 예약에는 찾을 조건이 없다. 그 시각을 어딘가에 적는 순간 다음 절의 예약 테이블이 된다.
-   <strong>조회 부하를 운영 DB가 받는다.</strong> 배치가 돌 때마다 결제 테이블을 훑는다. 가입 7일 차 안내, 장바구니 알림처럼 규칙이 늘수록 배치와 쿼리도 는다.
-   <strong>배치가 겹치면 두 번 보낸다.</strong> 배치 서버가 여러 대이거나 스케줄러가 같은 배치를 겹쳐 띄우면 같은 사용자를 둘이 찾는다. 잠금이나 보낸 기록으로 중복을 걸러야 한다.

<details>
<summary>배치를 한 번만 돌리려면</summary>

Kubernetes CronJob은 `concurrencyPolicy`로 겹치는 실행을 다룬다. 기본값 `Allow`는 겹쳐 실행하고, `Forbid`는 새 실행을 건너뛴다. 그래도 공식 문서는 Job이 두 번 만들어지거나 한 번도 만들어지지 않을 수 있다며, 여러 번 실행해도 결과가 같게 짜라고 권한다.

Spring의 `@Scheduled`처럼 애플리케이션 안의 스케줄러는 인스턴스마다 같은 작업을 돌린다. ShedLock은 DB나 Redis에 잠금을 걸어 한 곳에서만 돌게 하고, 이미 돌고 있으면 기다리지 않고 건너뛴다.

</details>

이 안이 맞는 때는 보낼 시각이 도메인 상태에서 정해지고 배치 주기만큼 늦어도 괜찮을 때다. 밤마다 나가는 공지처럼 되풀이되는 발송에도 맞다.

### 2. 예약 테이블에 보낼 시각을 적는다

받는 사람, 보낼 내용, 보낼 시각, 상태를 예약 테이블에 한 행으로 적고, 폴러가 주기적으로 때가 된 행을 큐로 옮긴다. 재안내든 어드민 예약이든 행 하나라서 배치로는 담지 못하던 어드민 예약도 담긴다.

예약이 행이라서 기준 대부분이 쉽게 풀린다. "이번 주에 나갈 예약"은 쿼리 하나이고, 취소와 시각 변경은 행을 고치는 일이다. 몇 달 뒤의 예약도 행 하나이고, DB에 있으니 재시작을 거쳐도 남는다. 결제와 같은 DB라면 아웃박스처럼 한 트랜잭션으로 적을 수 있다. 폴러가 1분마다 돈다면 오차도 1분 안이다.

지금이 목요일 15시이고 예약 테이블에 다섯 행이 있다고 해 보자. 폴러는 때가 된 행만 큐로 옮기고, 워커는 보내기 직전에 한 번 더 확인한다.

<ReservationTableDiagram />

B는 수요일에 다시 결제했지만 예약 테이블은 그 사실을 몰라 재안내를 큐로 옮겼다. 조건이 바뀐 예약을 거둘 길이 둘 있다.

-   <strong>조건이 바뀌는 곳에서 예약을 취소한다.</strong> 결제 성공을 처리하는 코드가 재안내 예약을 찾아 취소한다. 결제 경로가 늘수록 예약을 알아야 하는 코드도 늘고, 한 곳만 빠뜨려도 재안내가 나간다.
-   <strong>보내기 직전에 조건을 다시 확인한다.</strong> 워커가 외부 API를 부르기 전에 결제 상태를 다시 본다. 결제 쪽은 예약을 몰라도 되지만, 알림 종류마다 무엇을 확인할지 워커가 알아야 한다.

뒤쪽이 더 단단하다. 큐로 옮긴 직후에 어드민이 취소한 예약도 여기서 걸러진다. 문구도 같은 선택이다. 완성된 문구를 적으면 예약할 때 본 그대로 나가고, 템플릿만 가리키면 그사이 고친 문구가 나간다.

대신 챙길 것이 있다.

-   <strong>폴러를 직접 만든다.</strong> 폴러가 여러 대면 같은 행을 둘이 옮기지 않도록 `SKIP LOCKED`로 잠가야 한다. 큐를 DB 테이블로 만들 때 하던 일과 같다.
-   <strong>옮기는 순간에 틈이 있다.</strong> 큐에 넣는 일과 상태를 바꾸는 일은 한 트랜잭션으로 묶이지 않는다. 상태를 먼저 바꾸고 죽으면 예약이 사라지고, 큐에 먼저 넣고 죽으면 다음 폴링 때 한 번 더 옮긴다. 그래서 큐에 먼저 넣고 예약 id를 작업 id로 써서 중복을 거른다.
-   <strong>정확한 것은 큐에 들어가는 시각까지다.</strong> 공지 1만 건을 10시로 예약해도 5초에 100건 한도라면 마지막 건은 8분 20초 뒤에 나간다.
-   <strong>테이블이 계속 자란다.</strong> 폴러가 1분마다 조회하므로 상태와 보낼 시각에 인덱스가 필요하고, 끝난 예약은 지우거나 따로 옮겨야 한다.

폴러가 예약 r-7을 큐로 옮기다 죽었다고 해 보자. 두 일의 순서에 따라 남는 것이 갈린다.

<PollerGapDiagram />

큐를 DB 테이블로 만들었다면 예약 테이블이 곧 큐다. 워커가 보낼 시각이 지난 행만 집으니 폴러도 필요 없다.

<details>
<summary>두 번 들어온 작업을 거르는 법</summary>

BullMQ는 이미 있는 작업 id로 넣으면 무시한다. 다만 앞의 작업이 지워진 뒤에는 같은 id로 다시 들어가므로, 완료된 작업을 바로 지우도록 설정했다면 그 뒤의 중복은 걸러지지 않는다.

SQS FIFO 큐는 중복 제거 ID가 같은 메시지를 5분 동안 다시 받지 않는다. 표준 큐에는 이런 장치가 없어서 워커가 예약 id로 직접 걸러야 한다.

Java의 db-scheduler는 예약 테이블과 폴러를 묶어 둔 라이브러리다. 테이블 하나를 쓰고, 기본 10초마다 때가 된 작업을 찾으며, 인스턴스가 여러 대여도 한 실행은 한 곳만 집는다.

</details>

이 안이 맞는 때는 어드민이 예약을 보고 고쳐야 하거나 큐가 붙잡아 둘 수 없을 만큼 먼 시각까지 예약해야 할 때다.

### 3. 큐의 지연 작업으로 넣는다

큐가 지연 발송을 지원한다면 3일 뒤로 지연을 건 작업을 바로 넣는다. 예약 테이블도 폴러도 없이 시각이 되면 큐가 작업을 워커에게 넘긴다. 큐 절의 후보 가운데 3일을 붙잡아 둘 수 있는 것은 Redis 위의 작업 큐와 4.4부터의 RabbitMQ quorum 큐다. SQS는 15분까지다.

얻는 것은 단순함이다. 넣는 코드는 한 줄이고, 옮기는 단계가 없으니 옮기는 순간의 틈도 없다. 결제와 한 트랜잭션으로 묶이지 않는다는 점과 보내기 직전에 다시 확인해야 한다는 점은 앞과 같다.

걸리는 것은 예약이 큐 안에 있다는 데서 나온다. 지금이 화요일 11시이고 큐에 지연 작업 넷이 기다린다고 해 보자. 재안내는 결제 id로 작업 id를 정했고, 어드민 예약은 큐가 정해 준 id를 받았다.

<DelayedJobDiagram />

-   <strong>예약이 보낼 시각 순으로만 줄 서 있다.</strong> 사용자나 종류로 찾는 길이 없어서 "사용자 C에게 걸린 예약"을 띄우려면 작업을 모두 훑어야 한다.
-   <strong>취소하거나 바꾸려면 작업 id를 알아야 한다.</strong> 재안내처럼 결제 id로 작업 id를 정해 두면 지우거나 시각을 바꾸기 쉽다. 어드민 예약처럼 정할 규칙이 없으면 작업 id를 어딘가에 적어야 하고, 그 순간 예약 테이블이 다시 생긴다.
-   <strong>작업에 담은 데이터는 넣을 때 그대로다.</strong> 문구를 담으면 그사이 고친 문구가 들어가지 않는다. 3일 전에 넣은 작업을 그사이 배포된 새 코드가 꺼내므로, 작업 데이터의 모양을 바꿨다면 옛 모양도 읽을 수 있어야 한다. 그래서 작업에는 id만 담고 내용은 보낼 때 읽는 편이 안전하다.
-   <strong>예약이 큐의 저장소에 머문다.</strong> Redis라면 며칠 치 예약이 메모리에 쌓인다. 큐를 비우거나 다른 큐로 옮길 때 기다리던 예약도 함께 옮겨야 한다.

<details>
<summary>BullMQ와 Sidekiq의 지연 작업</summary>

BullMQ는 `delay` 옵션에 밀리초를 준다. 지연 중인 작업은 `changeDelay`로 지연을 다시 정하거나 `remove`로 지울 수 있지만, 처리 중인 작업은 지울 수 없다. 문서는 정확한 시각을 보장하지는 않지만 대부분 꽤 정확하다고 말한다.

Sidekiq은 `perform_in`이나 `perform_at`으로 예약한다. 예약된 작업은 시각 순으로 정렬된 집합에 들어가고, 기본으로 약 5초마다 확인하므로 초 단위로 정확하지는 않다. jid로 찾아 지울 수 있지만 문서는 집합을 훑어 지우는 일은 문제가 생겼을 때만 하라고 권한다. 모범 사례 문서도 기다리는 사이 데이터가 바뀌므로 작업에는 상태 대신 id를 담으라고 한다.

</details>

이 안이 맞는 때는 예약을 사람이 찾거나 고칠 일이 없고, 작업 id를 도메인의 id에서 정할 수 있을 때다. 3일 뒤 재안내처럼 시스템이 걸고 시스템이 거두는 예약이 여기에 맞다.

### 4. 관리형 스케줄러에 맡긴다

예약을 클라우드의 스케줄러에 맡긴다. AWS라면 큐 절에서 15분보다 먼 예약에 권한다던 EventBridge Scheduler다. 예약마다 한 번만 도는 일정을 만들어 두면 그 시각에 스케줄러가 발송 큐에 메시지를 넣는다.

지연 작업처럼 넣기만 하면 되고, 띄울 서버도 예약을 붙잡아 둘 저장소도 없다. 일정이 큐 밖에 있으니 큐를 비우거나 바꿔도 예약은 남는다. 일정 이름을 직접 짓기 때문에 재안내라면 결제 id로 지어 두고 그 이름으로 지우거나 바꾼다. 밤마다 나가는 공지는 cron 식 반복 일정 하나면 된다. 시각은 분 단위로 맞아서 10시로 건 일정은 10시 0분 0초에서 59초 사이에 메시지를 넣는다.

같은 예약들을 일정으로 옮기면 재안내와 어드민 예약은 한 번만 도는 일정이, 밤마다 나가는 공지는 반복 일정이 된다.

<ManagedSchedulerDiagram />

약점도 지연 작업과 닮았다.

-   <strong>찾는 길은 일정 이름뿐이다.</strong> 일정 목록은 그룹, 이름 접두어, 활성 여부로만 거를 수 있다. "사용자 C에게 걸린 예약"을 띄우려면 이름에 사용자를 넣거나 따로 적어 둬야 하고, 접두어로 찾을 수 있는 기준은 하나뿐이다.
-   <strong>바꿀 때는 일정 전체를 다시 보낸다.</strong> 일정을 수정하면 요청에 빠진 값이 기본값으로 덮인다. 시각 하나만 바꾸려 해도 일정을 먼저 읽고 나머지 값을 그대로 채워 보내야 한다.
-   <strong>담은 내용은 만들 때 그대로다.</strong> 큐에 넣을 메시지는 일정을 만들 때 정해진다. 여기서도 id만 담는 편이 안전하다.
-   <strong>끝난 일정도 한도를 차지한다.</strong> 한 번만 도는 일정은 실행된 뒤에도 남아 일정 수 한도에 잡히므로 끝나면 지워지도록 설정해 둬야 한다.
-   <strong>예약 하나가 API 호출 하나다.</strong> 결제와 한 트랜잭션으로 묶이지 않고 예약이 클라우드 계정 안에 있다. 공지처럼 한 시각에 몰리는 대량 발송은 사용자마다 일정을 만들기보다 배치를 깨우는 일정 하나를 두는 편이 낫다.

<details>
<summary>EventBridge Scheduler의 한도와 가격</summary>

한 번만 도는 일정은 `at(2026-11-26T15:00:00)`처럼 시각을 적고, 반복 일정은 `cron(0 21 * * ? *)`처럼 연도까지 여섯 칸으로 적는다. 둘 다 `Asia/Seoul` 같은 시간대를 지정할 수 있고, 정해진 시각부터 60초 안에 대상을 호출한다.

일정 수는 리전마다 기본 1,000만 개이고 늘릴 수 있다. 실행이 끝난 일회성 일정도 여기에 들어가므로 `ActionAfterCompletion`을 `DELETE`로 두라고 권한다. 대상 호출이 실패하면 지수 백오프로 최대 24시간, 185번까지 다시 시도하게 할 수 있고, 끝내 실패한 호출은 dead-letter queue로 보낼 수 있다. 일정에 담는 입력은 최대 256KB다.

가격은 매달 1,400만 번 호출까지 무료이고, 그 뒤로는 100만 번당 1달러다.

</details>

이 안이 맞는 때는 AWS 위에서 SQS로 발송 큐를 운영하고 있어 15분보다 먼 예약을 따로 맡겨야 할 때다. 일정 이름을 도메인의 id에서 지을 수 있다면 더 잘 맞는다.

### 예약을 표현하는 방식을 고르는 기준

네 방식 가운데 늘 맞는 하나는 없다. 누가 예약을 걸고 거두는지, 사람이 예약을 보고 고쳐야 하는지에 따라 고른다.

-   <strong>보낼 시각이 도메인 상태에서 정해지고 몇 시간 늦어도 괜찮다면 배치가 조건으로 찾는 편이 낫다.</strong> 얻는 것은 취소 로직도, 저장해 둘 예약도 없다는 점이다. 내주는 것은 배치 주기만큼의 오차와 운영 DB의 조회 부하이고, 상태로 표현할 수 없는 예약은 담지 못한다.
-   <strong>어드민이 예약을 보고 취소하거나 바꿔야 한다면 예약 테이블이 맞다.</strong> 얻는 것은 찾고 고치는 일이 쿼리와 행 수정이 되고, 결제와 한 트랜잭션으로 적을 수 있다는 점이다. 내주는 것은 폴러를 만들고, 옮길 때 생기는 중복을 거르고, 끝난 예약을 정리하는 수고다.
-   <strong>시스템이 걸고 시스템이 거두는 예약이고 큐가 그만큼 긴 지연을 받는다면 큐의 지연 작업으로 충분하다.</strong> 얻는 것은 따로 만들 것이 없다는 점이다. 내주는 것은 작업 id 없이는 예약을 찾을 수 없다는 점과, 며칠 치 예약이 큐의 저장소에 머문다는 점이다.
-   <strong>AWS 위에서 SQS를 쓰고 15분보다 먼 예약이 필요하다면 관리형 스케줄러가 낫다.</strong> 얻는 것은 운영할 것 없이 먼 시각의 예약을 맡길 수 있다는 점이다. 내주는 것은 일정 이름으로만 찾고, 고칠 때 일정 전체를 다시 보내야 하고, 예약이 클라우드 계정 안에 있다는 점이다.

한 서비스 안에서 섞어 쓰기도 한다. 밤마다 나가는 공지는 배치로, 어드민 예약은 예약 테이블로, 3일 뒤 재안내는 지연 작업으로 두는 식이다. 어떻게 섞든 보내기 직전의 재확인은 남는다. 예약은 미리 내린 결정이라서 보내는 순간에 그 결정이 여전히 맞는지 따져야 한다.

## 마치며

1편은 "발송을 어디에 맡길 것인가"를 세 질문으로 나눠 따졌다.

-   <strong>발송 요청을 어떻게 넘길 것인가</strong> — 서버가 늘고 요청을 잃으면 안 될수록 아웃박스와 메시지 큐 쪽으로 옮겨 가고, 어느 쪽이든 큐가 필요해진다.
-   <strong>큐를 무엇으로 만들 것인가</strong> — 이미 운영하는 것과 직접 만들 여력에 따라 답이 갈리고, 큐가 해 주지 않는 기능은 직접 만든다.
-   <strong>예약 발송을 어떻게 표현할 것인가</strong> — 사람이 예약을 보고 고쳐야 하는지, 시스템이 걸고 거두는지에 따라 고르고, 어느 쪽이든 보내기 직전에 다시 확인한다.

세 질문 모두 정답이 하나가 아니었다. 서버가 몇 대인지, 무엇을 이미 운영하는지, 무엇을 잃으면 안 되는지가 답을 바꾼다. 발송 서버를 떼어 내려는 참이라면 이 조건부터 적어 보자.

[2편](/ko/blog/bullmq-notification-part-2-rate-limit)에서는 외부 API의 한도를 어디서 지킬지 다룬다. 워커가 5초에 100건을 지켜도 외부 API는 429를 돌려줄 수 있다. 우리와 외부 API가 한도를 세는 구간의 시작이 어긋날 때, 그리고 같은 계정을 다른 곳에서도 쓸 때다.
