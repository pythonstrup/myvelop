## 들어가며

AI 에이전트를 만들다 보면 비용 문제가 먼저 걸린다. 에이전트는 일 하나를 끝내는 동안 모델을 여러 번 부르는데, 그중 깊이 따져야 하는 판단은 몇 번 되지 않는다. 나머지는 이 이력서가 요건을 채우는지, 이 글이 우리 서비스 이야기인지처럼 예/아니오나 보기 하나로 답할 수 있는 작은 판단이다.

작은 판단이니 작은 모델에 맡기면 될 것 같지만, Haiku 같은 작은 모델도 결국 LLM이라 판단 하나마다 답을 글로 써 내려간다. 하나하나는 싸도 수십 개가 쌓이면 청구서가 달라지고, 모델이 글을 다 쓸 때까지 기다리는 시간도 함께 쌓인다. 당장 큰 문제가 난 것은 아니어도 줄일 수 있는 비용이라면 줄이고 싶었다.

AI 에이전트 비용이 너무 비싼데, 더 싸게 만들 수는 없을까?

이 질문을 따라가다 TypeSafe의 Jev를 알게 되었다. Jev는 글을 쓰지 않고 판단만 하는 모델이다. 지어낸 이력서 한 장으로 같은 판단 20개를 시켜 보니 생각하는 Haiku보다 61배 빠르고 14배 쌌고, 생각을 하지 않는 Haiku와 비교해도 16배 빠르고 6배 쌌다.

이 글에서는 세 가지를 따라간다.

1. 작은 판단을 Haiku에 맡겨도 비싼 이유는 무엇인가.
2. Jev는 무엇이 다르고, 그 답은 어떻게 읽어야 하는가.
3. Jev는 언제 쓰고, 언제 쓰지 말아야 하는가.

## Haiku에 맡겨도 비싼 이유

먼저 단가를 나란히 놓아 보면 다음과 같다. 100만 토큰당 가격이고, 2026년 10월에 [TypeSafe 모델 페이지](https://docs.typesafe.ai/models)와 [Anthropic 가격표](https://platform.claude.com/docs/en/about-claude/pricing)에서 확인했다.

| 모델 | 입력 | 출력 |
| --- | --- | --- |
| Jev 1.14 | $0.042 | 무료 |
| Claude Haiku 5.5 | $0.10 | $0.50 |
| Claude Haiku 4.5 | $1.00 | $5.00 |
| Claude Sonnet 5.5 | $2.00 | $10.00 |
| Claude Opus 5.5 | $4.00 | $20.00 |

표만 보면 Haiku 5.5의 입력 단가는 Jev의 2.4배밖에 되지 않는다. 이 정도라면 그냥 Haiku를 써도 될 것 같은데, 직접 재 보니 차이는 단가가 아닌 세 군데에서 났다.

첫째는 출력이다. 생성 모델은 답을 글로 쓰고 그 글에도 값을 매기는데, Haiku 5.5의 출력 단가는 입력의 5배다. 판단 20개를 JSON으로 받으면 답만 500 토큰쯤 나오고, Haiku가 생각까지 하면 2,000 토큰쯤이 더 붙었다. Jev는 글을 쓰지 않으니 출력에 돈이 들지 않는다.

둘째는 답의 질이다. 같은 이력서로 대용량 트래픽 처리를 얼마나 깊이 다뤘는지 물었더니 Haiku는 `{"answer": "깊음", "p": 0.85}`처럼 답했다. 이 0.85는 모델이 써 넣은 글자라서, 같은 요청을 열 번 보내는 동안 0.55에서 0.85까지 오갔다. 열 번 동안 받은 확률 200개는 8개를 빼고 모두 0.05 단위로 끊어져 있었고, 그중 3분의 1이 0.6이었다. Jev도 깊음을 골랐지만 깊음 0.85, 보통 0.15처럼 보기마다 확률을 나눠 돌려줬고, 다섯 번 보내는 동안 깊음은 0.82\~0.89 안에서 움직였다. 자동으로 처리할지 사람에게 넘길지 문턱을 정하려면 이런 분포가 필요하다.

셋째는 질문끼리의 독립이다. 생성 모델에 질문 20개를 한 번에 물으면 답을 차례로 써 내려가기 때문에 앞에 쓴 답이 뒤의 답에 영향을 줄 수 있다. 판단끼리 섞이지 않게 하려면 질문마다 따로 불러야 하고, 그러면 이력서 한 장을 20번 보내게 된다. Jev는 한 요청에 묶은 질문들을 서로의 답을 보지 않게 나란히 처리한다.

결국 차이는 단가표가 아니라 답의 모양에서 나온다. 글로 답하는 모델은 쓰는 만큼 돈과 시간을 쓰고, 확률도 글자로만 준다.

## 판단이 싸지면 질문이 바뀐다

1865년 영국의 경제학자 윌리엄 스탠리 제번스는 증기기관의 효율이 좋아져 석탄 1톤으로 할 수 있는 일이 늘었는데도 석탄 소비가 줄지 않고 오히려 늘었다고 기록했다. 싸진 만큼 더 많은 곳에 쓰게 된 것이다. 이것을 제번스의 역설이라고 부른다.

TypeSafe에 투자한 Sequoia는 [투자 소개 글](https://sequoiacap.com/article/typesafe-the-jevolution)에서 이 역설을 판단에 빗댄다. 판단이 비싸면 팀은 타협한다. 전부 보지 않고 일부만 표본으로 검사하거나, 깨지기 쉬운 규칙을 짜거나, 구체적인 질문 여러 개 대신 넓은 질문 하나만 묻는다. 판단이 거의 공짜가 되면 이런 타협을 할 이유가 없어진다.

이력서를 읽는 일로 옮겨 보자. 판단이 비쌀 때는 이 사람이 몇 점인지 하나만 묻게 된다. 그런데 그 답 하나에는 요건을 채웠는지, 일을 얼마나 주도했는지, 경험이 구체적으로 적혔는지 같은 판단이 여럿 숨어 있어서, 답이 이상해도 어느 판단이 틀렸는지 알 수 없고 고칠 곳도 찾기 어렵다.

판단이 싸지면 질문을 쪼갤 수 있다. 요건마다, 우대 조건마다, 이력의 면마다 하나씩 물으면 스무 개쯤 된다. Jev로 이 스무 개를 묻는 데 $0.000116이 들었으니 만 번을 물어도 $1.16이다. 그러면 답을 하나하나 들여다보고, 문턱을 따로 조정하고, 코드로 합칠 수 있다.

그렇다면 Jev는 이런 질문을 어떻게 받고 무엇을 돌려줄까.

## Jev는 무엇이 다른가

TypeSafe는 Jev를 [System One 모델](https://docs.typesafe.ai/concepts/system-one)이라고 부른다. 이름은 카너먼의 『생각에 관한 생각』에서 왔다. 지금의 생성 모델이 천천히 따져 보는 System 2라면, 빠르게 판단하는 System 1을 따로 만들었다는 뜻이다.

### 사람이 아니라 프로그램이 읽을 답

[TypeSafe 홈페이지](https://typesafe.ai)는 채팅 모델의 한계부터 짚는다. 사람과 대화하도록 다듬은 모델은 지시를 잘 따르지만 지나치게 자신만만하고 같은 질문에 다른 답을 내기도 해서, 결국 사람이 옆에서 지켜봐야 한다는 것이다.

그래서 TypeSafe는 사람이 아니라 프로그램이 읽을 답을 내는 모델을 만들었다. 답은 대화가 아니라 정해진 모양의 판단이고, 판단마다 확신도가 붙는다. 코드처럼 믿을 수 있고, 빠르고, 같은 입력에는 같은 답을 내는 것이 목표다.

### 모델은 판단만 하고, 나머지는 코드가 맡는다

[TypeSafe 문서](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)는 Jev가 에이전트를 만드는 모델이 아니라고 분명히 밝힌다. Jev는 다음에 무엇을 할지 스스로 고르지 않는다. 규칙과 문턱, 분기와 실행은 코드가 맡고, Jev는 코드로 짤 수 없는 흐릿한 판단 하나만 채운다.

그래서 Jev를 쓸 때도 코드에서 시작한다. 평범한 흐름을 먼저 짜 두고, 글의 의미를 읽어야 하는 자리에만 Jev를 끼워 넣는다.

### Jev에게 묻는 법

질문은 세 종류가 있다.

| 종류 | 묻는 것 | 돌려주는 것 |
| --- | --- | --- |
| noul | 조건이 맞는가 | 예일 확률 하나 |
| choice | 보기 중 어느 것인가 | 고른 보기, 보기별 확률, 확신도 |
| score | 순서 있는 단계 중 어디인가 | 확률로 가중한 위치, 단계별 확률, 확신도 |

요청은 판단 재료인 `state`와 질문 묶음인 `questions`로 이루어진다. 이력서 실험에서 보낸 질문 중 세 개만 추리면 다음과 같다.

```bash
curl https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "jev-latest",
    "state": {
      "resume": "...지원자의 이력서 글...",
      "job": {
        "title": "백엔드 개발자 (결제 플랫폼)",
        "must": ["API 설계", "대용량 트래픽 처리", "데이터베이스 설계", "장애 대응"],
        "preferred": ["팀을 이끈 경험", "결제·정산 도메인 경험", "쿠버네티스 운영 경험"],
        "stack": ["Kotlin", "Spring Boot", "Kafka", "AWS"]
      }
    },
    "questions": {
      "must_db": {
        "type": "choice",
        "instructions": "필수 요건 「데이터베이스 설계」 — `resume` 에서 이 요건을 실무로 얼마나 깊이 다뤘나?",
        "criteria": {
          "얕음": "언급만 있거나 보조 역할이었다",
          "보통": "직접 맡아 운영한 경험이 있다",
          "깊음": "설계를 주도했고 결과가 구체적으로 적혀 있다"
        }
      },
      "scope": {
        "type": "score",
        "instructions": "`resume` 에서 이 사람이 주도한 일의 범위는 어디까지인가?",
        "criteria": ["혼자 맡은 기능", "팀 단위 과제", "여러 팀에 걸친 과제"]
      },
      "stack_kafka": {
        "type": "noul",
        "instructions": "`resume` 에 Kafka 를 실무에서 쓴 경험이 적혀 있는가?"
      }
    }
  }'
```

질문을 쓸 때는 네 가지를 지켰다.

- <strong>state를 칸으로 나눈다.</strong> `resume`, `job.title`처럼 이름 붙은 칸을 두면 질문마다 어디를 보고 판단하라고 짚어 줄 수 있다.
- <strong>질문 문장만 읽어도 뜻이 통하게 쓴다.</strong> `must_db` 같은 질문 이름은 코드가 답을 찾을 때 쓰는 이름이라 모델은 보지 않는다.
- <strong>보기마다 뜻을 적는다.</strong> 깊음이라는 낱말만 주면 사람과 모델의 기준이 갈리니, 보기 설명이 곧 판단 기준이 된다.
- <strong>같은 state에 대한 질문은 한 요청에 묶는다.</strong> 묶은 질문은 나란히 처리되어 왕복이 늘지 않는다. 이력서 한 장에 질문 20개를 붙여도 입력은 2,768 토큰이었다.

### 확실하면 처리하고, 애매하면 넘긴다

Jev가 돌려준 확률은 그대로 분기 조건이 된다. 문턱 하나로 예와 아니오를 가르기보다 구간을 나눠서, 확실한 답은 코드가 바로 처리하고 애매한 답은 사람이나 더 비싼 모델에게 넘긴다.

구간을 어디서 나눌지는 틀렸을 때 생기는 피해에 따라 정한다. TypeSafe의 [확신도 문서](https://docs.typesafe.ai/confidence)는 noul이라면 예 0.7, 아니오 0.3에서 시작해 자기 데이터로 조정하라고 권하고, 되돌릴 수 없는 행동은 0.9를 넘을 때만 확인 없이 실행하는 예를 든다. 뒤에서 다룰 이력서 판독기라면 항목마다 이렇게 나눠 볼 수 있다.

| 판단할 항목 | 질문 | 바로 처리하는 구간 | 이렇게 정한 이유 |
| --- | --- | --- | --- |
| 이력서에 나온 기술 스택 | 스택마다 noul | 0.7 이상이면 태그를 붙인다 | 태그 하나가 틀려도 사람이 읽으면서 고칠 수 있다 |
| 공고 직무와 관련 있는 이력서인가 | noul | 0.9 이상이면 그대로 진행하고, 0.1 이하면 관련 없음으로 따로 모은다. 그 사이는 사람이 본다 | 관련 없는 이력서로 잘못 빼면 좋은 사람을 놓친다 |
| 필수 요건을 얼마나 깊이 다뤘나 | 요건마다 choice | 확신도 0.9 이상 | 읽는 순서를 정하는 재료라 틀리면 순서가 크게 밀린다 |
| 우대 조건을 채웠나 | 조건마다 choice | 확신도 0.7 이상, 아니면 모름으로 둔다 | 조금 더해 주는 항목이라 틀려도 피해가 작다 |

틀렸을 때 되돌리기 쉬운 항목일수록 문턱을 낮추고, 놓치면 되돌리기 어려운 항목일수록 높인다. 이 숫자들도 출발점일 뿐이라 내 데이터로 다시 재야 한다.

헷갈리기 쉬운 점이 두 가지 있다. noul의 0.5는 중간쯤 맞다는 뜻이 아니라 모르겠다는 뜻이다. 그리고 Jev의 확률이 결과에 맞춰 학습됐다는 말은 예측을 여러 개 모았을 때의 이야기이지, 답 하나하나가 맞는다는 보장은 아니다.

실제로 돌아온 답을 보면 더 잘 보인다.

## Jev의 답을 읽는 법

앞의 요청에 돌아온 답에서 세 질문만 추리면 다음과 같다. 읽기 좋게 필요한 칸만 남겼다.

```json
{
  "must_db": {
    "choice": "얕음",
    "probabilities": { "얕음": 0.81, "보통": 0.17, "깊음": 0.02 },
    "confidence": 0.72
  },
  "scope": {
    "score": 0.99,
    "probabilities": { "0": 0.14, "1": 0.73, "2": 0.13 },
    "confidence": 0.59
  },
  "stack_kafka": { "noul": 0.53 }
}
```

### choice는 1순위만 믿어도 될까

`must_db`는 얕음을 골랐고 그 확률이 0.81이다. 이력서에는 데이터베이스 조회를 캐시로 옮겼다는 이야기 정도만 있고 설계를 맡았다는 내용은 없으니 맞는 판단이다.

확신도 0.72는 1순위가 다른 보기보다 얼마나 앞서 있는지를 0\~1로 나타낸 값이다. 보기가 셋이면 고르게 나눴을 때 하나당 0.33인데, 1순위가 이 0.33에서 1까지 가는 길의 어디쯤에 있는지를 재면 (0.81 − 0.33) ÷ (1 − 0.33), 약 0.72가 나온다.

1순위만 보면 놓치는 답도 있다. 같은 이력서로 장애 대응을 얼마나 깊이 다뤘는지 물었을 때는 깊음이 1순위였지만 확률은 0.55 대 0.45로 보통과 거의 반반이었고, 확신도는 0.33이었다. 깊음만 저장하면 Jev가 망설였다는 정보가 사라진다. 앞에서 나눈 구간으로 보면 이 답은 바로 처리하지 말고 확인으로 넘겨야 한다.

### score에서 0.99는 무슨 의미일까

score의 단계는 보낸 배열 순서대로 0, 1, 2다. `scope`의 0.99는 단계 하나를 고른 값이 아니라 단계마다 확률을 곱해 더한 위치다. 0 × 0.14 + 1 × 0.73 + 2 × 0.13 = 0.99이니, 팀 단위 과제 한가운데에 있고 양옆으로 비슷하게 조금씩 퍼져 있다는 뜻이다.

확신도 0.59는 확률이 한 단계에 다 모이지 않고 양옆에도 실려 있다는 뜻이다. score의 확신도는 가장 그럴듯한 단계에서 먼 단계에 확률이 실릴수록 더 깎인다. 위치는 그대로 다른 점수와 합쳐 써도 되고, 반올림해 단계로 바꿀 때는 확신도를 함께 봐야 한다.

### noul에서 0.53은 얼마나 확실할까

`stack_kafka`의 0.53은 이력서에 Kafka를 실무에서 쓴 경험이 적혀 있을 확률이다. 0.5에 붙어 있으니 Jev는 모르겠다고 답한 셈이다. 실제로 이력서의 기술 목록에는 Kafka가 있지만, 경력 설명에는 메시지 큐를 도입했다고만 적혀 있어서 실무에서 Kafka를 썼는지는 이력서만으로 알 수 없다.

같은 이력서에서 Kotlin은 0.97이었다. 요약에 Kotlin을 주로 쓴다고 분명히 적혀 있기 때문이다. noul에는 확신도가 따로 없고, 이렇게 확률이 0.5에서 멀수록 확실한 답이다. 앞의 표대로라면 판독기는 Kotlin에는 태그를 붙이고, Kafka는 태그 없이 확인할 점으로 남긴다.

### 다시 물어도 같은 답이 나올까

같은 요청을 다섯 번 보냈다. choice 질문 일곱 개 가운데 1순위가 바뀐 질문은 하나도 없었지만, 확률은 소수 둘째 자리에서 조금씩 흔들렸다. 장애 대응의 깊음은 0.54\~0.58 사이를 오갔고, Kafka 질문은 0.53, 0.44, 0.51, 0.51, 0.58로 0.5를 사이에 두고 오갔다.

비교 삼아 Haiku에도 같은 요청을 열 번 보냈는데, 데이터베이스 설계 질문에서는 얕음을 두 번, 보통을 여덟 번 골랐다. Jev는 같은 질문에 다섯 번 모두 얕음을 골랐고, 그 확률도 0.78\~0.81 안에 있었다.

문턱 바로 위아래에 걸친 답은 이 흔들림 때문에 보낼 때마다 다른 쪽으로 갈 수 있다. 그런 자리에서는 같은 요청을 몇 번 보내 평균을 내면 된다.

## 같은 판단, 다른 비용과 시간

이제 들어가며에서 말한 숫자가 어떻게 나왔는지 보자. 측정 조건은 다음과 같다.

- 지어낸 이력서 한 장에 choice 7개, score 7개, noul 6개, 모두 20개의 질문을 물었다. 이력서와 질문 전체는 이 절 끝에 붙였다.
- Jev는 지금 1.14를 가리키는 `jev-latest`로 불렀고, 20개를 한 요청에 묶어 다섯 번 보냈다.
- Haiku 5.5는 Claude Code의 비대화 모드인 `claude -p`로 불렀다. 시간은 Claude Code가 잰 API 시간으로, 명령이 뜨는 시간은 뺐다. Jev는 요청을 보내고 답을 받을 때까지 잰 시간이라 네트워크 왕복이 들어 있다.
- 비용은 캐시 할인 없이 정가로 계산했다.

| 방식 | 시간 | 출력 토큰 | 비용 | Jev와 비교 |
| --- | --- | --- | --- | --- |
| Jev, 한 요청에 20개 | 0.19초 (0.18\~0.24) | 없음 | $0.000116 | 기준 |
| Haiku 5.5, 한 번에 20개, 생각 안 함 | 2.9초 (2.3\~3.4) | 492\~493 | $0.00070 | 16배 느리고 6배 비싸다 |
| Haiku 5.5, 한 번에 20개, 생각 함 | 11.4초 (10.6\~13.7) | 2,246\~2,909 | $0.00165 | 61배 느리고 14배 비싸다 |
| Haiku 5.5, 문항마다 따로 20번, 차례로 | 54.7초 | 5,188 | $0.0073 | 약 290배 느리고 62배 비싸다 |
| Haiku 5.5, 문항마다 따로 20번, 동시에 | 4.0\~5.2초 | 4,292\~4,720 | $0.0068\~0.0070 | 21\~27배 느리고 59\~60배 비싸다 |

시간은 중앙값이고 괄호 안은 가장 빠른 값과 가장 느린 값이다. 한 번에 묻는 방식은 열 번 불렀는데, 그중 일곱 번은 Haiku가 생각을 했고 세 번은 생각 없이 답했다.

같은 판단 20개를 놓고 보면 Jev는 생각하는 Haiku보다 61배 빠르고 14배 쌌다. 생각을 하지 않는 Haiku와 비교해도 16배 빠르고 6배 쌌다.

### 그래도 Haiku에 한 번에 물으면 되지 않을까

생각을 하지 않는 Haiku에 한 번에 물으면 이력서 한 장에 $0.0007이니 충분히 싸다고 볼 수도 있다. 그래도 Jev를 고른 데는 세 가지 이유가 있다.

우선 조건을 맞추면 차이가 훨씬 커진다. 한 번에 묻는 방식은 앞에 쓴 답이 뒤의 답에 영향을 줄 수 있어서, 질문끼리 섞이지 않게 하려면 문항마다 따로 물어야 한다. 그러면 비용이 Jev의 60배 안팎이 되고, 동시에 보내도 가장 느린 호출을 기다리느라 4\~5초가 걸린다. 그렇게 해도 확률은 여전히 모델이 써 넣은 글자다.

규모가 커지면 차이도 커진다. 이력서 3만 장을 처리하면 Jev는 약 $3.5, 생각을 하지 않는 Haiku는 약 $21, 생각하는 Haiku는 약 $50, 문항마다 따로 묻는 Haiku는 약 $218이 든다. 에이전트가 한 작업 안에서 이런 판단을 여러 번 한다면 그만큼 곱해진다.

마지막으로 시간을 예측하기 어렵다. Haiku 5.5는 생각을 할지 말지를 요청마다 스스로 정한다. 기본 설정에서는 다섯 번 모두 생각했고, 생각의 양을 정하는 effort를 가장 낮은 low로 내려도 다섯 번 중 두 번은 생각했다. 그래서 같은 설정으로 보낸 같은 요청이 2\~3초에 끝나기도 하고 11초 가까이 걸리기도 했다. 에이전트의 한 단계가 이렇게 들쭉날쭉하면 전체 작업 시간도 가늠하기 어렵다. 느린 것보다 예측할 수 없는 것이 더 큰 문제다.

### 답의 형식도 흔들린다

문항마다 따로 물었을 때는 답의 형식도 흔들렸다. 질문 이름을 키로 쓰라고 지시했는데도, 질문이 하나뿐일 때는 20건 중 7\~11건이 키 없이 답만 돌려줬다. 프롬프트를 더 다듬으면 줄어들 수 있으니 이 숫자를 Haiku의 한계로 볼 수는 없다. 다만 생성 모델을 쓰면 형식을 지키는 일까지 모델에 맡기게 되고, 형식이 어긋났을 때 다시 부르는 비용은 코드가 떠안는다. Jev는 다섯 번 모두 20개 답이 정해진 모양으로 왔다.

### 이 측정의 한계

이번 측정에는 분명한 한계가 있다.

- 횟수가 적다. Jev는 5번 불렀고, Haiku는 한 번에 묻는 방식을 10번, 문항마다 따로 묻는 방식을 차례로 1번과 동시에 2번 불렀다.
- Haiku는 Claude Code를 거쳐 불렀고 답 형식 지시가 입력에 더 붙었다. 그래서 같은 이력서인데도 입력이 Haiku는 4,584 토큰, Jev는 2,768 토큰이었다. 두 회사의 토크나이저가 다른 것도 이 차이에 섞여 있다.
- 정답을 정해 두고 정확도를 잰 실험이 아니다. 이 절의 숫자는 시간과 비용만 말해 준다.

### 실험에 쓴 이력서와 질문

실험에 쓴 이력서는 지어낸 것이고, 회사 이름도 모두 가상이다. Jev와 Haiku에는 아래 이력서를 `state.resume`에, 「Jev에게 묻는 법」 예시의 공고 내용을 `state.job`에 넣어 똑같이 보냈다.

```text

- 사내 관리자 도구를 만들었다. 운영팀이 엑셀로 하던 일을 화면으로 옮겼다.

[기술]
Kotlin, Java, Spring Boot, TypeScript, Node.js, MySQL, PostgreSQL, Redis, Kafka, AWS(ECS, RDS, SQS), Docker, Kubernetes 기초

[프로젝트]
- 사이드 프로젝트: 오픈소스 결제 테스트 도구 기여(문서 번역, 작은 버그 수정 2건)
- 사내 기술 블로그에 "정산 배치를 40분으로 줄인 이야기" 기고

[자기소개]
저는 문제를 끝까지 파고드는 개발자입니다. 결제는 한 건의 실수도 허용되지 않는 도메인이라, 테스트와 모니터링을 먼저 생각합니다. 새로운 기술을 배우는 것을 좋아하며, 팀과 함께 성장하는 것을 중요하게 생각합니다. 귀사의 비전에 깊이 공감하며, 제 경험이 귀사의 성장에 기여할 수 있다고 확신합니다. 끊임없이 배우고 도전하는 자세로 최선을 다하겠습니다.
```

| 이름 | 단계 |
| --- | --- |
| `scope` | 혼자 맡은 기능 → 팀 단위 과제 → 여러 팀에 걸친 과제 |
| `depth` | 도구를 쓰는 수준 → 원리를 알고 고치는 수준 → 구조를 새로 설계하는 수준 |
| `impact` | 영향이 보이지 않는다 → 팀 지표가 좋아졌다 → 서비스 지표가 크게 좋아졌다 |
| `scale` | 작은 내부 도구 → 서비스의 한 기능 → 서비스 핵심 경로 |
| `growth` | 비슷한 일을 반복 → 조금씩 커짐 → 뚜렷하게 커짐 |
| `helping` | 보이지 않는다 → 코드 리뷰·온보딩 정도 → 다른 사람의 성장을 이끌었다 |
| `specific` | 거의 안 보인다 → 일부 보인다 → 대부분 보인다 |

Haiku에는 같은 state와 질문을 JSON으로 붙이고, 다음 시스템 프롬프트로 답 형식을 정했다.

```text
너는 채용 서류 평가 보조다. 사용자가 이력서(state)와 질문들을 준다.
각 질문에 JSON 으로만 답한다. 설명·코드 펜스 없이 JSON 객체 하나만 출력한다.
- type 이 noul 이면 {"p": 예일 확률 0~1}
- type 이 choice 면 {"answer": 고른 보기 키, "p": 그 보기일 확률 0~1}
- type 이 score 면 {"level": 고른 단계 문장, "p": 그 단계일 확률 0~1}
키는 질문 id 를 그대로 쓴다.
```

## 예시: 이력서 판독기

지금까지 살펴본 방법을 가상의 이력서 판독기 하나로 묶어 보자. 공고의 요건과 이력서를 맞대어 보고, 사람이 먼저 읽을 이력서의 순서와 확인할 점을 정리해 주는 도구다. 판독기는 이력서를 떨어뜨리지 않는다. 떨어뜨리는 결정은 되돌리기 어려우니 사람이 한다. 학력이나 출신 회사처럼 사람을 등급 매기는 항목도 넣지 않는다.

판독기가 이력서마다 판단하는 기준은 다음과 같다. 가상의 백엔드 개발자 공고를 기준으로 했고, 앞에서 잰 질문 20개가 바로 이것이다.

| 묶음 | 판단 | 질문 |
| --- | --- | --- |
| 직무 관련성 | 공고 직무와 관련 있는 이력서인가 | noul 1개 |
| 필수 요건 | API 설계, 대용량 트래픽 처리, 데이터베이스 설계, 장애 대응을 얼마나 깊이 다뤘나 | choice 4개 |
| 우대 조건 | 팀을 이끈 경험, 결제·정산 일 경험, 쿠버네티스 운영 경험을 채웠나 | choice 3개 |
| 이력의 면 | 주도한 범위, 전문성의 깊이, 성과의 영향, 다룬 시스템의 규모, 맡은 일의 성장, 동료를 도운 경험 | score 6개 |
| 기록 | 상황과 본인 행동, 결과가 구체적으로 적혀 있나 | score 1개 |
| 기술 스택 | Kotlin, Spring Boot, Kafka, AWS를 실무에서 쓴 경험이 적혀 있나 | noul 4개 |
| 기록 | 프로젝트마다 본인이 한 일이 팀이 한 일과 구분돼 적혀 있나 | noul 1개 |

### 비싼 모델은 애매할 때만 부른다

판독기에서 이력서 한 건은 다음 순서로 흐른다.

1. 마감 뒤에 들어온 지원이나 빠진 서류처럼 규칙으로 가릴 수 있는 것은 코드가 먼저 처리한다.
2. 위의 기준을 Jev에 한 요청으로 묻는다.
3. 답이 모두 확실하면 코드가 바로 읽는 순서를 매긴다. 확신도가 낮은 답이 섞여 있으면 그 이력서만 큰 모델이 다시 읽고, 왜 애매한지 짧게 적어 둔다.
4. 사람은 정해진 순서대로 이력서를 읽고, 표시된 확인 사항을 보면서 결정한다.

이렇게 하면 큰 모델은 애매한 이력서에만 쓰인다. 다만 처음부터 이 구조로 바꾸기보다는 그림자 시험부터 해 보는 것이 좋다. 지금의 흐름은 그대로 두고 Jev로 끝냈다면 어떻게 판단했을지 계산만 해서, 큰 모델의 판단과 비교해 보는 것이다. 둘이 많이 겹칠수록 큰 모델을 부를 일이 줄어든다.

### 질문은 쪼개고, 합치는 건 코드가 한다

읽는 순서를 Jev에게 바로 묻지는 않는다. 순서를 매기는 규칙은 코드가 갖고, Jev는 그 재료가 되는 항목만 판단한다. 예를 들면 이런 규칙이다.

- 필수 요건의 깊이를 얕음 0, 보통 1, 깊음 2로 바꾸고, 요건마다 가중치를 곱해 더한다.
- 우대 조건은 충족이면 조금 더하고, 모름이면 더하지도 빼지도 않는다.
- 필수 요건 가운데 하나라도 얕음이 확실하면 합계와 상관없이 뒤로 보낸다.

마지막 규칙처럼 하나만 어긋나도 안 되는 조건은 가중 합에 섞지 말고 따로 둔다. 가중 합은 한 항목이 모자라도 다른 항목으로 메워지기 때문이다.

Jev의 답은 확률까지 그대로 저장해 둔다. 그러면 가중치나 화면에서 거르는 조건을 바꿀 때 Jev를 다시 부르지 않고 계산만 새로 하면 된다. 다시 물어야 하는 것은 질문의 뜻이 바뀌었을 때뿐이다.

### 1순위 대신 확률로 정한다

앞에서 본 장애 대응 질문을 다시 보자. 깊음이 1순위였지만 확률은 0.55 대 0.45였고 확신도는 0.33이었다. 판독기가 1순위만 저장했다면 이 이력서는 장애 대응을 깊이 다룬 이력서로 분류됐을 것이다. 확신도까지 보면 이 답은 큰 모델이나 사람에게 넘길 답이다.

문턱은 남이 쓰는 숫자를 그대로 가져오지 말고 내 데이터로 정한다. 사람이 미리 판단해 둔 이력서 몇십 장을 Jev의 답과 맞대어 보고, 확신도가 얼마일 때부터 사람과 맞는지 보면 된다. 이 확인은 질문을 고칠 때마다 다시 한다. 질문 문장이 조금만 바뀌어도 확률이 달라지기 때문이다.

## LiteLLM 게이트웨이로 Jev 부르기

[연재 첫 글](/ko/blog/llm-gateway/)에서는 서비스가 모델 제공자를 직접 부르지 않고 게이트웨이 하나를 거치게 했다. Jev도 같은 길로 부를 수 있다. LiteLLM은 [v1.103.0-rc부터](https://docs.litellm.ai/blog/typesafe_jev) Jev를 지원하는데, Jev는 글이 아니라 판단을 돌려주는 모델이라 `/chat/completions`가 아닌 자기 경로로 받는다.

가장 간단한 방법은 `/typesafe/` 아래로 들어온 요청을 TypeSafe API에 그대로 넘기는 패스스루다. TypeSafe 키는 프록시의 환경 변수에만 두고, 서비스는 LiteLLM 가상 키만 들고 다닌다.

```bash
# 프록시 쪽에만 둔다
export TYPESAFE_API_KEY="..."
```

서비스 쪽에서는 앞의 curl에서 주소와 키만 바꾸면 된다. 요청 본문은 그대로다.

```bash
curl https://<게이트웨이 주소>/typesafe/v1/systemone \
  -H "Authorization: Bearer $LITELLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "model": "jev-latest", "state": { ... }, "questions": { ... } }'
```

게이트웨이를 거치면 다른 모델과 같은 자리에서 비용과 로그가 쌓인다. 비용은 응답에 실린 토큰 수로 계산하고, `jev-latest`로 불러도 기록에는 실제로 응답한 판의 이름이 남는다. 다만 스트리밍과 최종 사용자별 사용량 추적은 지원하지 않는다. 배포를 여러 개 두고 부하를 나누거나 대체 모델로 넘기고 싶다면, 패스스루 대신 `model_list`에 Jev를 올리고 통합 경로 `/v1/systemone`을 쓰라고 [LiteLLM 문서](https://docs.litellm.ai/docs/pass_through/typesafe)는 권한다.

LiteLLM은 Jev를 게이트웨이 안의 판단에도 쓴다. 자동 라우터는 Jev를 분류기로 두고 choice 질문 하나로 요청을 어느 모델에 보낼지 고른다. 이 글에서 말한 비싼 모델 앞에 작은 판단을 세우는 일을 게이트웨이가 대신 해 주는 셈이다. [v1.104.3](https://docs.litellm.ai/release_notes/v1.104.3/v1-104-3)에서는 관리자가 적어 둔 예/아니오 질문으로 메시지와 도구 인자를 검사해 막거나 기록하는 가드레일도 들어왔다.

## Jev는 언제 사용해야 하는가

Jev는 판단만 한다. 그래서 언제 쓰지 말아야 하는지부터 정해 두면 나머지가 쉬워진다.

- <strong>계산하는 일</strong> — 합산, 숫자 비교, 날짜 비교, 개수 세기는 코드가 한다. Jev는 숫자를 다루는 데 약하고, 코드는 이런 일을 틀리지 않는다.
- <strong>글을 써야 하는 일</strong> — 요약이나 답장, 판단의 이유를 설명하는 글은 생성 모델이 쓴다. 판독기에서도 애매한 이력서의 이유를 적는 일은 큰 모델에게 맡겼다.
- <strong>값을 새로 뽑아내는 일</strong> — Jev는 정해 준 보기 안에서만 고른다. 이력서에서 경력 기간 같은 값을 꺼내는 일은 코드나 생성 모델이 하고, 코드가 후보를 뽑아 오면 그중 맞는 것을 고르는 일은 Jev가 할 수 있다.
- <strong>되돌리기 어려운 결정</strong> — Jev의 확률은 사람이나 큰 모델에게 넘길지 정하는 데 쓴다. 판독기가 이력서를 떨어뜨리지 않은 것도 이 때문이다.
- <strong>글이 아닌 입력</strong> — Jev는 지금 글만 받는다. 이미지나 음성은 다른 모델로 먼저 글로 바꿔야 한다. [모델 페이지](https://docs.typesafe.ai/models) 기준으로 한 요청에 state와 질문을 합쳐 6만 4천 토큰, 질문 하나당 3만 2천 토큰까지 들어간다.

반대로 이런 자리에서는 생성 모델보다 Jev를 먼저 떠올려 볼 만하다.

- 항목마다 예/아니오나 보기, 단계를 매기는 반복 판단이다. 분류, 태그 붙이기, 라우팅이 여기에 든다.
- 비싼 모델을 부르기 전에 거르거나 나눠 보내는 자리다.
- 코드나 검색이 뽑아 온 후보가 정말 맞는지 의미로 다시 확인하는 자리다.
- 큰 모델이 낸 결과가 그 근거와 맞는지 점검하는 자리다.

## 정리

작은 판단을 Haiku에 맡겨도 비싼 이유는 단가가 아니라 답의 모양에 있었다. 생성 모델은 답을 글로 쓰느라 출력과 시간을 쓰고, 확률도 글자로만 준다. 질문끼리 섞이지 않게 하려면 질문마다 따로 불러야 해서 비용이 더 늘어난다.

Jev는 판단만 하고, 흐름은 코드가 맡는다. 판단을 좁은 질문으로 쪼개 한 요청에 묶고, 돌아온 확률로 구간을 나눠 확실한 답은 코드가 처리하고 애매한 답은 사람이나 큰 모델에게 넘긴다. 지어낸 이력서 한 장에 같은 판단 20개를 시켜 보니 생각하는 Haiku보다 61배 빠르고 14배 쌌고, 생각을 하지 않는 Haiku와 비교해도 16배 빠르고 6배 쌌다.

처음부터 구조를 바꿀 필요는 없다. 지금 LLM에게 예/아니오를 묻고 있는 자리 하나를 골라, 기존 흐름은 그대로 둔 채 같은 질문을 Jev에도 물어 보자. 두 답을 나란히 놓고 보면 어디에 Jev를 세울 수 있는지가 보인다.
