이 글에서는 Aurora Serverless v2의 용량 단위인 ACU가 왜 생겼고 무엇인지, CloudWatch에서는 ACU를 어떻게 읽고 무엇과 함께 봐야 하는지 살펴본다. 그런 다음 큰 쓰기 작업을 ACU에 맞춰 조절하는 방법을 다룬다.

## ACU가 생긴 이유

프로비저닝 방식의 Aurora를 쓸 때는 `db.r6g.xlarge` 같은 인스턴스 클래스를 고른다. 클래스마다 메모리와 CPU가 정해져 있고, 요금은 실제로 얼마나 썼는지와 상관없이 고른 클래스의 크기와 켜 둔 시간으로 정해진다. 그래서 바쁠 때를 버티려고 큰 클래스를 골라 두면, 한가한 시간에도 그 크기만큼 요금을 낸다. 반대로 작게 골라 두면 바쁠 때 모자란다. 둘 다 피하려면 부하가 바뀔 때마다 사람이 클래스를 바꿔야 하고, 바꾸는 동안 연결이 잠깐 끊기는 것도 감수해야 한다.

Serverless v2에서는 클래스 대신 범위를 고른다. 최소 몇 ACU부터 최대 몇 ACU까지로 정해 두면, Aurora가 그 안에서 부하에 맞춰 용량을 늘리고 줄인다. 요금은 실제로 쓴 용량만큼만 낸다. 같은 하루를 두 방식으로 견줘 보면 이렇다.

<ProvisionedVsServerlessDiagram />

AWS 서비스는 대부분 쓴 만큼 내는 종량제다. 프로비저닝 인스턴스도 켜 둔 시간만큼만 요금을 내지만, 시간당 요금은 고른 크기로 정해진다. Serverless v2는 이 기준을 실제로 쓴 크기로 바꿨다. 쓴 크기만큼 요금을 매기려면 지금 얼마나 쓰고 있는지 잴 단위가 필요하다. 전기 요금을 쓴 만큼 매기려면 kWh라는 단위가 필요한 것과 같다. Aurora에서는 그 단위가 ACU다.

그래서 Serverless v2는 부하가 들쭉날쭉하거나 미리 가늠하기 어려운 데이터베이스에 잘 맞는다. AWS 문서도 쓰임새로 갑자기 일이 몰리는 서비스, 고객마다 데이터베이스를 따로 두는 서비스, 필요한 크기를 아직 모르는 새 서비스, 개발과 테스트 환경을 든다.

## ACU

### ACU란

ACU(Aurora Capacity Unit)는 Serverless v2의 용량을 세는 단위다. 1 ACU는 메모리 약 2GiB와 그에 맞는 CPU, 네트워크를 묶은 것이다. 메모리를 기준으로 떠올리면 쉽다. 4 ACU는 메모리가 약 8GiB인 서버, 12 ACU는 약 24GiB인 서버쯤 된다.

ACU 하나에 무엇이 들어 있고 여러 개를 쌓으면 어떻게 되는지 그려 보면 다음과 같다.

ACU는 1, 2, 3처럼 딱 떨어지는 수로만 세지 않는다. 3.5 ACU처럼 소수점이 붙은 값도 되고, 3.5 ACU는 메모리가 약 7GiB인 크기다.

### 계산과 저장소

ACU로 세는 것은 CPU와 메모리 같은 계산 용량뿐이다. 데이터를 담는 저장소는 계산과 따로 떨어져 있어서, 계산 용량이 바닥까지 내려가도 테라바이트 단위의 데이터를 그대로 담아 둘 수 있다. Aurora에서 저장소라고 부르는 곳은 두 군데다.

<StorageLayoutDiagram />

클러스터 저장소는 테이블과 인덱스처럼 계속 남아 있어야 할 데이터를 두는 곳이다. 인스턴스 바깥에 따로 있고, 한 클러스터의 writer와 reader가 이 저장소 하나를 함께 쓴다. AWS는 이 데이터를 세 가용 영역에 두 벌씩, 모두 여섯 벌로 보관한다. 메모리에 없는 데이터는 여기서 읽어 오고, writer가 데이터를 고치면 고친 내용을 로그 레코드로 만들어 여기로 보낸다.

로컬 저장소는 인스턴스마다 하나씩 붙은 작업용 디스크다. 쿼리를 처리하다가 정렬이나 해시가 메모리에 다 들어가지 않으면 그 임시 파일이 여기에 놓이고, 로그 파일도 여기에 쌓인다. Aurora MySQL은 인덱스를 만들거나 S3에서 데이터를 불러올 때도 이곳을 쓴다. 작업하는 동안 잠깐 쓰는 공간이라 계속 남겨야 할 데이터는 두지 않는다.

### 최소와 최대

범위는 클러스터마다 하나만 정한다. writer와 reader가 같은 범위를 쓰지만 용량은 인스턴스마다 따로 움직이므로, writer가 바쁠 때도 reader는 바닥에 머물 수 있다.

최소는 바닥이다. 한가할 때는 용량이 여기까지 내려가므로 바닥이 낮을수록 요금이 덜 나오고, 0으로 두면 일이 없을 때 인스턴스가 아예 멈춘다. 다만 이 자동 일시 중지는 Aurora PostgreSQL 16.3, 15.7, 14.12, 13.15 이상과 Aurora MySQL 3.08.0 이상에서만 쓸 수 있다. 그렇다고 무조건 낮게 잡을 일은 아니다. 바닥이 낮으면 두 가지를 잃는다. 하나는 속도다. 용량이 작을 때는 조금씩 늘어나서, 바닥에서 출발하면 필요한 만큼 올라가는 데 오래 걸린다. 다른 하나는 캐시다. Aurora는 자주 읽는 데이터를 버퍼 캐시라는 메모리 공간에 올려 두는데, 용량이 줄면 이 데이터가 밀려난다. 그러면 다시 바빠졌을 때 클러스터 저장소에서 새로 읽어 와야 한다.

최소만 다르게 정한 두 인스턴스에 같은 일을 맡겨 보자. 위는 최소가 0.5 ACU, 아래는 4 ACU다.

<FloorTradeoffDemo client:visible />

결국 최소는 한가할 때의 요금과 바빠졌을 때의 속도를 맞바꾸는 값이다. 처음에는 평소에 쓰는 용량보다 조금 낮게 잡고 시작하면 된다.

최대는 천장이다. 쿼리를 잘못 짜서 부하가 치솟아도 용량과 요금은 여기서 더 오르지 않는다. 대신 천장이 낮으면 정말 필요할 때 더 커지지 못해 모든 쿼리가 느려진다. 천장은 인스턴스마다 따로 걸리므로, 인스턴스가 셋이면 클러스터 전체로는 최대의 세 배까지 쓸 수 있다.

### 스케일링

Aurora는 인스턴스마다 CPU, 메모리, 네트워크 사용량을 계속 지켜본다. AWS 문서는 이 셋을 묶어 부하라고 부른다. 부하에는 애플리케이션이 보낸 쿼리뿐 아니라 데이터베이스의 백그라운드 작업과 Aurora의 관리 작업도 들어간다. 셋 가운데 하나라도 지금 용량으로 모자라기 시작하면 Aurora는 용량을 늘린다.

한 번에 늘리는 폭은 지금 용량에 따라 다르다. 용량이 작을 때는 0.5 ACU씩 늘리고, 용량이 클수록 폭도 커진다. 그래서 용량이 클수록 빨리 늘어난다.

최소를 1 ACU, 최대를 20 ACU로 정한 클러스터에 최대보다 많은 용량이 필요한 작업이 들어왔다고 하자. 파란 선은 용량, 주황 선은 그 작업에 필요한 용량이다.

<ScalingDemo client:visible />

용량이 낮을 때는 계단도 낮아서 필요한 용량을 따라잡는 데 시간이 걸린다. 그동안 모자란 몫이 빨갛게 칠해지고, 최대에 닿은 뒤로는 이 몫이 더 줄어들지 않는다.

용량을 바꾸는 동안 연결은 끊기지 않는다. 트랜잭션이 돌고 있거나 테이블이 잠겨 있어도, 한가한 틈을 기다리지 않고 바로 바꾼다.

> <strong>reader는 writer를 따라갈 수도 있다</strong>  
> reader의 승격 우선순위(promotion tier)를 0이나 1로 두면 writer의 지금 용량이 곧 reader의 최소 용량이 된다. 장애가 났을 때 writer 자리를 바로 넘겨받을 수 있도록 writer만큼 미리 커져 있는 것이다. 2\~15로 두면 reader는 writer와 따로 움직인다.

## ACU 읽기

### 두 지표

ACU는 CloudWatch에서 두 지표로 본다.

| 지표 | 뜻 |
| --- | --- |
| `ServerlessDatabaseCapacity` | 지금 용량(ACU) |
| `ACUUtilization` | 지금 용량을 최대 ACU로 나눈 비율(%) |

`ACUUtilization`이 100%에 가까우면 그 인스턴스는 더 커질 수 없는 데까지 올라간 것이다.

`ServerlessDatabaseCapacity`는 인스턴스 단위로도 클러스터 단위로도 볼 수 있다. 다만 클러스터 단위 값은 조심해서 읽어야 한다. 이 값은 인스턴스들의 평균이라서, writer가 최대에 붙어 있어도 reader가 바닥에 있으면 그 중간쯤으로 나온다. writer가 20 ACU, reader가 2 ACU라고 하자.

<ClusterAverageDiagram />

클러스터 단위 값은 11 ACU다. 최대의 절반을 조금 넘을 뿐이라 여유가 있어 보이지만, writer는 이미 최대에 닿아 있다. 그래서 쓰기 작업의 영향을 보려면 writer의 값을 따로 읽어야 한다. 장애 조치로 writer 인스턴스가 바뀌어도 계속 writer의 값을 읽으려면, 인스턴스 이름 대신 `DBClusterIdentifier`와 `Role=WRITER`를 함께 지정한다.

### 1분 값과 Average, Maximum

Aurora는 용량을 1초마다 재지만 CloudWatch에는 1분 단위로 보낸다. 1분 값 하나에는 그 1분 동안 잰 값들이 묶여 있고, 이 묶음을 무엇으로 요약할지는 통계로 고른다. Average는 그 1분의 평균이고, Maximum은 그 1분 동안 가장 높았던 값이다.

둘의 차이는 짧은 봉우리에서 드러난다. 어느 1분 동안 50초는 4 ACU였고 10초만 20 ACU로 튀었다고 하자. 이 1분의 Average는 (4×50 + 20×10) ÷ 60으로 약 6.7 ACU이고, Maximum은 20 ACU다.

1초마다 잰 값 60개가 1분 값 하나로 줄어드는 과정을 따라가 보자.

<AverageMaxDemo client:visible />

Maximum은 몇 초짜리 봉우리에도 반응한다. 그래서 Maximum만 보면 늘 위험해 보이고, Average만 보면 짧은 봉우리를 놓친다. 오래 이어지는 부담은 Average로, 잠깐이라도 최대에 닿았는지는 Maximum으로 보는 편이 낫다.

### 방금 끝난 1분의 값

1분 값은 그 1분이 지난 뒤에야 다 모인다. 방금 끝난 1분을 곧바로 읽으면 값이 아직 없거나 덜 모인 채로 나올 수 있다. 그러니 최근 몇 분을 함께 읽고, 다 모인 값 가운데 가장 최근 것으로 판단하는 편이 안전하다. 이렇게 읽은 값은 적어도 1분 전의 상태다. ACU를 보고 움직이는 장치는 늘 그만큼 늦게 반응한다는 뜻이다.

### CPUUtilization과 FreeableMemory의 기준

Serverless v2에서는 익숙한 두 지표의 뜻이 달라진다.

`CPUUtilization`은 지금 쓰는 CPU를, 지금 용량이 아니라 <strong>최대 ACU에서 쓸 수 있는 CPU</strong>로 나눈 값이다. 최대를 20 ACU로 정한 클러스터의 인스턴스가 지금 4 ACU 몫의 CPU를 다 쓰고 있어도 `CPUUtilization`은 20% 근처로 나온다.

`FreeableMemory`도 최대 용량을 기준으로 한다. 인스턴스가 최대까지 커졌을 때 남을 메모리를 보여 주기 때문에, 지금 용량이 최대보다 1 ACU 낮을 때마다 약 2GiB씩 더 크게 나온다. 그래서 최대에 닿기 전에는 0 근처로 내려가지 않는다.

같은 인스턴스를 두 기준으로 나란히 놓고 보면 차이가 드러난다.

<CpuBaselineDiagram />

두 지표가 넉넉해 보여도 지금 인스턴스에 여유가 있다는 뜻은 아니다. Serverless v2 인스턴스가 얼마나 바쁜지는 `ServerlessDatabaseCapacity`와 `ACUUtilization`으로 읽는다.

## ACU가 오를 때 볼 지표

Aurora는 CPU, 메모리, 네트워크를 함께 지켜보다가 그중 하나라도 모자라면 용량을 늘린다. 그래서 ACU 그래프만 봐서는 ACU가 왜 올랐는지 알 수 없다. 데이터베이스가 바쁜지 볼 때 흔히 보는 CPU 하나만으로도 모자란다. 범위를 늘려야 하는지, 쿼리를 고쳐야 하는지, 켜 둔 기능을 꺼야 하는지 판단하려면 원인이 되는 지표를 ACU 옆에 함께 띄워 두어야 한다.

흔한 경우 몇 가지를 모아, 무엇이 ACU를 끌어올리고 그때 어떤 지표를 함께 봐야 하는지 정리하면 이렇다.

| 이런 일이 있으면 | ACU를 끌어올리는 자원 | ACU와 함께 볼 지표 |
| --- | --- | --- |
| 무거운 쿼리가 몰리거나 동시 연결이 많다 | CPU | `CPUUtilization`, `DatabaseConnections` |
| 많은 행을 한꺼번에 고쳐 쓴다 | 메모리, 저장소 쓰기 | `WriteIOPS`, `StorageNetworkTransmitThroughput` |
| 메모리에 다 들어가지 않는 정렬이나 집계를 한다 | 로컬 저장소와 오가는 네트워크 | `TempStorageIOPS`, `TempStorageThroughput` |
| 요청이 없는데도 최소까지 내려오지 않는다 | 켜 둔 기능과 백그라운드 작업 | `DatabaseConnections`, `CommitThroughput` |

### CPU가 끌어올릴 때

가장 익숙한 경우다. AWS 문서는 CPU를 많이 쓰는 원인으로 무겁거나 비효율적인 작업과 많은 동시 연결을 든다. 이때는 `CPUUtilization`이 ACU와 함께 오른다. 다만 앞에서 본 것처럼 `CPUUtilization`은 최대 ACU를 기준으로 계산해서 낮게 나오므로, 값이 얼마나 큰지보다 ACU와 같은 때 오르는지를 본다. 무거운 쿼리가 몰리는 동안 세 지표를 시간축을 맞춰 나란히 띄웠다고 하자.

### 메모리와 쓰기가 끌어올릴 때

CPU는 잔잔한데 ACU만 크게 오르는 경우다. AWS 문서는 용량이 늘어나는 원인이 대부분 메모리 사용과 CPU 활동이라고 설명한다. CPU가 잔잔하다면 메모리를 먼저 의심해 볼 만하다.

많은 행을 한꺼번에 고쳐 쓰는 작업을 떠올려 보자. 행을 고치려면 그 행이 든 페이지를 버퍼 캐시로 읽어 와서 고쳐야 하고, 고친 내용은 로그 레코드로 만들어 클러스터 저장소로 보내야 한다. 행마다 하는 계산은 단순해서 CPU는 많이 쓰지 않는다. 하지만 캐시에 올릴 페이지가 많아 메모리를 많이 쓰고, 저장소로 나가는 쓰기도 많다. 그래서 CPU 그래프는 잔잔한데 ACU는 크게 오른다.

writer 안에서 일어나는 일을 단계별로 그리면 이렇다. 위는 클러스터 저장소와 writer의 버퍼 캐시이고, 아래는 메모리, CPU, 저장소 쓰기, ACU 막대다. 메모리 막대는 최대 20 ACU에 해당하는 40GiB를 끝으로 잡았다. 그래서 1 ACU가 메모리 약 2GiB라는 관계대로 ACU 막대와 같은 길이로 움직인다. 막대의 숫자는 흐름을 보여 주려고 가정한 값이다.

<BulkRewriteDemo client:visible />

여기에 `CPUUtilization`이 최대 ACU를 기준으로 한다는 점까지 겹치면 CPU 그래프는 더 낮게 나온다. 큰 쓰기 작업이 데이터베이스에 얼마나 부담을 주는지는 CPU가 아니라 ACU로 재야 한다.

ACU가 쓰기 때문에 오르는지 확인하려면 writer의 `WriteIOPS`와 `StorageNetworkTransmitThroughput`을 함께 띄워 두면 좋다. `WriteIOPS`는 클러스터 저장소로 보내는 초당 로그 레코드 수이고, `StorageNetworkTransmitThroughput`은 클러스터 저장소로 보내는 초당 바이트 수다. 큰 쓰기 작업이 도는 동안 네 지표를 시간축을 맞춰 한 화면에 띄웠다고 하자. 그래프 모양은 설명을 위해 가정한 것이다.

<MetricRowsDiagram scenario="write" />

CPU는 작업 내내 잔잔한데, ACU와 두 쓰기 지표는 작업이 시작될 때 함께 오르고 끝날 때 함께 내려온다. 이렇게 같은 때 움직였다면 ACU를 끌어올린 것은 쓰기라고 짐작할 수 있다. 쓰기 지표는 작업이 시작되자마자 오르는데 ACU는 계단을 밟으며 조금 늦게 따라 오른다. 앞의 스케일링 그림에서 본 그대로다.

### 임시 파일이 끌어올릴 때

CPU로도 메모리로도 설명되지 않는데 ACU가 오를 때도 드물게 있다. AWS 문서는 이럴 때 의심해 볼 곳으로 로컬 저장소를 꼽는다.

정렬이나 해시는 정해진 메모리 안에서 처리하다가, 메모리가 모자라면 넘친 몫을 임시 파일로 덜어 내며 마저 처리한다. 책상이 좁으면 서류 일부를 바닥에 펼쳐 놓고 정리하는 것과 같다. 이 임시 파일이 놓이는 곳이 앞에서 본 로컬 저장소다.

DB 인스턴스에서 데이터가 드나드는 길은 셋이다. 애플리케이션과 오가는 길, 클러스터 저장소와 오가는 길, 그리고 로컬 저장소와 오가는 길이다. 메모리를 넘치는 정렬 쿼리 하나가 돌 때 세 길로 무엇이 오가는지 따라가 보자. 상자마다 그 길을 재는 지표 이름과, 그 값이 지금까지 움직인 모양을 작게 그려 두었다.

<TempSpillDemo client:visible />

애플리케이션과 오가는 양은 `NetworkThroughput`이, 클러스터 저장소와 오가는 양은 `StorageNetworkThroughput`이 잰다. 로컬 저장소와 오가는 임시 파일은 Serverless v2에만 있는 `TempStorageIOPS`와 `TempStorageThroughput`이 따로 잰다. 이 두 지표가 ACU와 함께 오른다면 메모리를 넘친 정렬이나 집계 쿼리부터 찾아본다.

### 요청이 없는데도 내려오지 않을 때

반대로 애플리케이션이 조용한데도 ACU가 최소까지 내려오지 않을 때가 있다. AWS 문서는 그 원인으로 먼저 켜 둔 기능을 든다. Performance Insights, Enhanced Monitoring, CloudWatch Logs 내보내기, global database 같은 기능은 그 자체로 자원을 쓴다. `max_connections`처럼 공유 메모리 크기를 정하는 파라미터를 기본값보다 크게 잡아도 최소까지 내려오지 않는다. purge 같은 백그라운드 작업이나, 데이터가 많을수록 커지는 클러스터 관리 부담도 원인이 된다.

이때는 연결 수인 `DatabaseConnections`와 초당 커밋 수인 `CommitThroughput`을 함께 본다. Aurora MySQL이라면 초당 쿼리 수인 `Queries`도 쓸 수 있다. 연결과 커밋이 바닥인데 ACU만 높다면, 원인은 애플리케이션이 아니라 켜 둔 기능이나 데이터베이스 안의 작업에 있다.

<MetricRowsDiagram scenario="idle" />

정리하면 ACU는 결과이고, 원인은 CPU, 메모리, 네트워크, 데이터베이스 안의 작업 가운데 어딘가에 있다. 원인을 찾을 때는 이 지표들을 ACU 옆에 띄워 놓고 함께 본다. 반대로 큰 쓰기 작업을 언제 멈출지 정할 때는, 이 원인이 모두 합쳐진 결과인 ACU 하나만 보면 된다. 뒤에서 배치를 ACU로 조절하는 것도 이 때문이다.

## 최대에 닿으면

### 모든 쿼리가 느려진다

최대에 닿은 인스턴스는 더 커질 수 없다. 부하는 그대로인데 CPU와 메모리는 더 늘지 않으니, 그 인스턴스로 들어오는 쿼리들이 한정된 자원을 나눠 쓰며 모두 느려진다. 큰 쓰기 작업이 용량을 최대까지 끌어올렸다면 그 작업과 상관없는 화면 조회까지 함께 느려진다. 애플리케이션에 쿼리 시간 제한을 걸어 두었다면 그 제한에 걸려 실패하는 요청도 생긴다.

최대에 닿는 일이 잦으면 상황은 더 나빠진다. 메모리나 CPU가 모자라 인스턴스가 자꾸 재시작되면 Aurora는 그 인스턴스를 `incompatible-parameters` 상태로 바꾸고, 재시작한 이유가 메모리 부족인지 CPU 부족인지를 이벤트로 남긴다. 이 상태에서는 엔진 버전 업그레이드 같은 작업이 막힌다.

### 늘어나는 속도에도 한계가 있다

최대에 닿지 않아도 느려질 수 있다. 용량은 한 번에 뛰어오르지 않고 계단을 밟아 늘어나기 때문이다. 앞의 계단 그림에서 최대에 닿기 전에 칠해진 빨간 몫이 바로 이것이다.

AWS 문서는 몇 초에 몇 ACU씩 늘어난다는 숫자를 주지 않는다. 대신 늘어나는 속도가 지금 용량에 달려 있다고 설명한다. 용량이 작을수록 한 번에 늘리는 폭도 작으므로, 최소와 최대 사이가 멀수록 최소에서 최대까지 오르는 데 오래 걸린다.

바닥에서 쉬던 인스턴스에 갑자기 큰 작업이 들어오면, 용량이 따라 올라오는 동안 그 작업도 다른 쿼리도 모자란 용량으로 버텨야 한다. 앞에서 최소를 너무 낮게 잡지 말라고 한 것도 이 때문이다. AWS 문서도 지금 용량과 필요한 용량의 차이가 작을수록 Aurora가 늘릴 폭과 속도를 더 정확하게 정한다고 설명한다.

## 요금

### ACU-시간

Serverless v2는 ACU-시간으로 요금을 매긴다. 1 ACU를 1시간 쓰면 1 ACU-시간이다. 용량 그래프에서는 선 아래 넓이가 곧 ACU-시간이다.

평소 2 ACU에 머물다가 한 시간 동안만 20 ACU까지 오르는 하루를 그려 보자.

<AcuHoursDiagram />

봉우리는 한 시간뿐인데 그 넓이는 평소 하루치의 3분의 1이 넘는다.

단가는 2026년 11월 서울 리전 기준으로 다음과 같다.

| 클러스터 저장소 설정 | ACU-시간당 요금 |
| --- | --- |
| Aurora Standard | $0.20 |
| Aurora I/O-Optimized | $0.26 |

MySQL과 PostgreSQL의 단가는 같다. 저장 용량 요금은 따로 붙고, Standard에서는 I/O 요청에도 요금이 붙는다. 청구 금액은 앞에서 본 `ServerlessDatabaseCapacity`를 기준으로 계산한다. 다만 한 시간 가운데 일부만 쓴 경우처럼, 지표 평균으로 직접 계산한 값과 조금 다를 때가 있다.

### 계산해 보기

writer 하나가 평소 2 ACU에 머물다가, 매일 한 시간씩 도는 배치 작업 때 20 ACU까지 오른다고 하자. 한 달은 730시간, 배치는 한 달에 30번 돈다고 잡으면 이렇다.

| 구분 | 계산 | ACU-시간 |
| --- | --- | --- |
| 평소 | 2 ACU × 730시간 | 1,460 |
| 배치로 늘어난 몫 | (20 − 2) ACU × 1시간 × 30일 | 540 |
| 합계 | | 2,000 |

Standard 단가로 계산하면 2,000 × $0.20 = $400이다. 하루 한 시간짜리 배치가 한 달 요금의 4분의 1 넘게 차지한다.

여기에 승격 우선순위가 0이나 1인 reader가 하나 있다면, 이 reader는 배치를 돌리지 않는데도 writer 크기를 따라 20 ACU까지 올라간다. 그러면 클러스터 전체의 ACU-시간은 두 배가 된다.

## 큰 쓰기 작업을 ACU에 맞춰 조절하기

### 묶음 사이에 ACU를 읽는다

writer를 쓰는 것은 배치만이 아니다. 사용자가 화면을 열거나 버튼을 누를 때마다 서비스도 같은 writer에 쿼리를 보낸다. 이 글에서는 이런 평소 쿼리를 서비스 요청이라고 부르겠다. 큰 쓰기 작업을 한꺼번에 몰아서 하면 용량이 최대까지 오르고, 앞에서 본 것처럼 서비스 요청까지 모두 느려진다. 그래서 작업을 묶음으로 나누고, 묶음 사이마다 ACU를 읽어 속도를 정한다.

1. writer의 ACU를 읽는다.
2. 문턱보다 높으면 쉬었다가 다시 읽는다. 내려올 때까지 다음 묶음을 쓰지 않는다.
3. 문턱보다 낮으면 한 묶음을 쓴다.
4. 짧게 쉬고 1로 돌아간다.

멈췄다가 이어서 하려면 어디까지 했는지 기록이 남아 있어야 한다. 묶음마다 마지막으로 처리한 키를 저장해 두면, 쉬었다가 이어 갈 때는 물론 작업이 죽었다가 다시 떠도 처음부터 다시 하지 않아도 된다.

### 문턱은 낮게 잡는다

문턱을 최대 근처에 두면 안 된다. 배치가 최대 직전까지 용량을 쓰고 나면 서비스 요청이 쓸 여유가 남지 않는다. 그래서 최대까지의 용량을 배치가 쓸 몫과 서비스 요청이 쓸 여유로 나누고, 배치의 문턱은 최대보다 한참 아래에 둔다. 최대를 20 ACU로 정한 클러스터에서 배치 문턱을 `ACUUtilization` 50%로 잡았다고 하자. 배치는 10 ACU 근처에서 멈추고, 나머지 10 ACU는 서비스 요청이 쓸 여유로 남는다.

지표가 늦게 도착한다는 점도 감안해야 한다. 지금 읽은 값은 적어도 1분 전의 상태라서, 묶음 하나가 그사이에 용량을 최대까지 밀어 올릴 만큼 크면 문턱을 둔 의미가 없다. 그래서 묶음은 늦게 알아차려도 버틸 만큼 작게 잡는다.

어떤 통계로 읽을지도 정해야 한다. Maximum으로 읽으면 서비스 요청이 만든 짧은 봉우리에도 걸려 배치가 자꾸 멈춘다. 배치가 만드는 것처럼 오래 이어지는 부담을 보려면 Average가 맞다.

지금까지의 규칙을 모두 적용하면 배치는 이렇게 움직인다. 주황 동그라미는 배치가 읽는 1분 전의 값이다.

<ThrottleDemo client:visible />

읽는 값이 늦기 때문에 ACU는 문턱을 조금 넘었다가 내려온다. 그래도 묶음이 작아서 그사이에 최대까지 닿지는 않는다.

### 값을 못 읽을 때

CloudWatch 호출이 실패하거나 최근 1분 값이 비어 있을 때가 있다. 이때 고를 수 있는 길은 둘이다.

| 선택 | 값이 없을 때 | 맞는 때 |
| --- | --- | --- |
| 진행(fail-open) | 그대로 쓴다 | 작업에 마감이 있고, 데이터베이스가 잠깐 느려져도 피해가 작을 때 |
| 멈춤(fail-closed) | 쉰다 | 작업은 늦어져도 되고, 데이터베이스가 막히면 사용자가 피해를 볼 때 |

조절 장치를 단 목적이 서비스 요청을 지키는 것이라면 멈춤을 기본으로 둔다. 지표를 읽지 못하는 동안에는 데이터베이스가 괜찮은지 알 수 없기 때문이다. 대신 그대로 두면 아무도 모르는 사이에 작업이 오래 서 있을 수 있으니, 이유가 무엇이든 일정 시간 넘게 멈춰 있으면 알림을 보낸다.

어느 쪽을 고르든 값이 없는 것을 0으로 읽어서는 안 된다. 0 ACU는 한가하다는 뜻이라, 값이 없을 때마다 0으로 읽으면 고른 적도 없는 진행이 기본 동작이 되어 버린다. 값이 없는 경우는 따로 다뤄야 한다.

### 코드로 옮기기

앞의 순서를 코드로 옮기면 이렇다. 묶음 쓰기와 지표 읽기, 알림 함수는 생략했다.

```ts
type AcuReading = { kind: 'value'; utilization: number } | { kind: 'missing' }

const PAUSE_AT_UTILIZATION = 50 // 최대 ACU의 50%라고 가정한 값
const SHORT_REST_MS = 2_000
const LONG_REST_MS = 60_000
const ALERT_AFTER_MS = 30 * 60_000

async function runBatch(): Promise<void> {
  for (;;) {
    await waitUntilAcuIsLow()
    const { done } = await writeNextChunk() // 저장해 둔 위치부터 한 묶음을 쓰고 위치를 갱신한다
    if (done) return
    await sleep(SHORT_REST_MS)
  }
}

async function waitUntilAcuIsLow(): Promise<void> {
  const startedAt = Date.now()
  for (;;) {
    // Role=WRITER, 1분 Average, 다 모인 가장 최근 값
    const reading: AcuReading = await readWriterAcuUtilization()
    if (reading.kind === 'value' && reading.utilization < PAUSE_AT_UTILIZATION) return
    // 값이 없으면 진행하지 않는다(fail-closed)
    if (Date.now() - startedAt > ALERT_AFTER_MS) await notifyOnce('배치가 오래 멈춰 있다')
    await sleep(LONG_REST_MS)
  }
}
```

`AcuReading`은 값이 있을 때와 없을 때를 서로 다른 타입으로 나눠 두었다. 그래서 값이 없는 경우를 0과 섞어 읽을 틈이 없다.

## 정리

1 ACU는 메모리 약 2GiB와 그에 맞는 CPU, 네트워크를 묶은 단위다. Aurora는 CPU만이 아니라 메모리와 네트워크까지 보고 용량을 늘리고, 지금 용량이 작을수록 천천히 늘린다. 용량이 최대에 닿으면 그 인스턴스를 쓰는 모든 쿼리가 함께 느려진다.

그래서 큰 쓰기 작업은 CPU가 아니라 writer의 ACU를 보고 조절한다. 문턱은 서비스 요청이 쓸 여유를 남길 만큼 낮게, 묶음은 늦게 알아차려도 버틸 만큼 작게 잡는다. 값을 못 읽을 때 어떻게 할지도 미리 정해 둔다.
