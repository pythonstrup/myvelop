## 들어가며

LLM 게이트웨이에 시맨틱 캐싱을 적용하는 기법이 있다고 들었다. 뜻이 비슷한 질문이 오면 모델을 부르지 않고 저장해 둔 답을 돌려주는 캐시다.

[AI 캐시가 제값을 하려면](/ko/blog/llm-prompt-caching/)에서 본 응답 캐시는 요청이 통째로 같아야 적중했다. 사람은 같은 것을 물어도 매번 다르게 쓰니, 이런 캐시는 좀처럼 적중하지 않는다. 글자가 아니라 뜻으로 맞추면 이 문제가 풀릴 것 같았다. 그런데 뜻이 비슷하다는 것을 무엇으로 판단하는지, 비슷해 보이지만 답이 다른 질문이 오면 어떻게 되는지 알 수 없었다.

알고 싶은 것은 세 가지였다.

1. 두 질문의 뜻이 같다는 것을 무엇으로 판단하는가.
2. 얼마나 비슷해야 같은 질문으로 볼 것인가.
3. 어떤 요청에는 쓰면 안 되는가.

## 글자가 같아야 맞는 캐시

쇼핑몰 상담 챗봇이 있다고 하자. 한 사람은 「환불은 어떻게 하나요?」라고 묻고, 다른 사람은 「환불하려면 어떻게 해야 하나요?」라고 묻는다. 답은 같은데 응답 캐시는 두 번째 질문을 놓친다.

응답 캐시는 요청을 해시해서 키로 쓴다. Cloudflare AI Gateway는 제공자, 경로, 모델, 인증 헤더, 요청 본문 전체를 이어 붙여 SHA-256으로 해시한다. 해시는 입력이 한 글자만 달라도 전혀 다른 값이 된다. 두 질문을 글자만 따로 해시해 보면 이렇다.

<ExactKeyDiagram />

그래서 이 캐시는 보내는 글자가 정해져 있을 때 잘 맞는다. Cloudflare 문서도 정해진 선택지 가운데 하나를 고르게 하는 상담 봇을 예로 들고, 시맨틱 검색은 앞으로 넣을 계획이라고 적는다.

## 뜻이 가까우면 맞는 캐시

### 질문을 벡터로 바꿔 찾는다

시맨틱 캐시는 해시 대신 임베딩을 쓴다. 임베딩 모델은 글을 수백에서 수천 개의 숫자로 이루어진 벡터로 바꾼다. 뜻이 가까운 글끼리 벡터의 방향도 가까워지도록 학습된 모델이다. 두 벡터가 얼마나 같은 방향을 가리키는지는 코사인 유사도로 잰다. 방향이 똑같으면 1이고, 벌어질수록 작아진다.

공개 임베딩 모델인 bge-m3로 두 쌍을 재 보았다. 이 모델의 벡터는 숫자가 1,024개라 그대로 그릴 수 없어서, 두 벡터 사이의 각도만 평면에 옮겼다.

<AngleDiagram variant="basic" />

요청이 오면 게이트웨이는 이 순서로 움직인다.

1. 질문을 임베딩 모델에 보내 벡터를 얻는다.
2. 저장해 둔 질문 벡터 가운데 가장 가까운 것을 찾는다.
3. 유사도가 문턱값 이상이면 그 질문에 딸린 답을 돌려준다. 모델은 부르지 않는다.
4. 문턱값에 못 미치면 모델을 부르고, 질문 벡터와 답을 저장한다.

문턱값을 0.9로 정하고 질문 셋을 저장해 두었다고 하자. 적중하는 질문과 놓치는 질문이 차례로 들어온다.

<LookupFlowDemo client:visible />

여기서 눈여겨볼 것은 적중했을 때 돌려주는 답이다. 사용자는 자기 질문의 답이 아니라, 자기 질문과 가장 가까운 <strong>다른 질문의 답</strong>을 받는다. 응답 캐시는 요청이 똑같을 때만 적중하므로 이런 일이 없다.

LiteLLM에서는 설정 파일에 캐시 종류, 문턱값, 임베딩 모델을 적으면 켜진다.

```yaml
litellm_settings:
  cache: true
  cache_params:
    type: redis-semantic
    similarity_threshold: 0.8
    redis_semantic_cache_embedding_model: my-embedding-model
```

캐시에서 나간 응답에는 `x-litellm-semantic-similarity` 헤더가 붙어서, 얼마나 비슷한 질문의 답이 나갔는지 알 수 있다.

### 본전은 쉽게 넘는다

적중하면 모델을 아예 부르지 않으므로 입력과 출력 토큰 요금, 답을 만드는 시간을 모두 아낀다. 대신 모든 요청 앞에 임베딩 호출과 벡터 검색이 붙는다. 놓친 요청은 캐시가 없을 때보다 그만큼 늦게 끝난다.

임베딩과 검색에 50ms, 모델이 답을 만드는 데 2초가 걸린다고 하자. 요청마다 50ms를 더 쓰고 적중할 때마다 2초를 아끼므로, 적중률이 2.5%만 넘으면 평균 시간은 줄어든다.

임베딩 서버가 느려지면 이 계산이 깨진다. 임베딩이 끝나야 모델을 부를 수 있기 때문이다. 그래서 LiteLLM은 임베딩을 5초까지만 기다리고, 넘으면 놓친 것으로 치고 모델을 부른다.

본전이 이렇게 낮다면 문턱값을 내려 적중률을 올리는 편이 이득일 것 같다. 그런데 시맨틱 캐시의 적중에는 틀린 적중이 섞인다.

## 문턱값은 적중과 오답을 맞바꾼다

### 질문 14쌍을 재 보았다

쇼핑몰 상담에서 나올 법한 질문을 14쌍 만들고, bge-m3로 유사도를 쟀다. 앞 질문이 저장되어 있을 때 뒤 질문이 들어왔다고 보면 된다. 질문은 재기 전에 정해 두었고, 결과를 보고 빼거나 바꾸지 않았다.

| 무리 | 저장된 질문 | 들어온 질문 | 유사도 |
| --- | --- | --- | --- |
| 뜻이 같다 | 환불은 어떻게 하나요? | 환불하려면 어떻게 해야 하나요? | 0.959 |
| | 배송은 며칠 걸려요? | 주문하면 언제 받을 수 있어요? | 0.881 |
| | 비밀번호를 잊어버렸어요 | 로그인 암호가 기억나지 않아요 | 0.849 |
| | 영수증은 어디서 받나요? | 결제 영수증 발급 방법 알려 주세요 | 0.827 |
| | 회원 탈퇴는 어떻게 하나요? | 계정을 지우고 싶어요 | 0.699 |
| | 포인트는 언제 적립되나요? | 적립금은 언제 들어와요? | 0.849 |
| 답이 다르다 | 반품이 되는 상품은 무엇인가요? | 반품이 안 되는 상품은 무엇인가요? | 0.921 |
| | 3일 안에 취소하면 수수료가 얼마인가요? | 30일 안에 취소하면 수수료가 얼마인가요? | 0.931 |
| | 서울 매장 영업시간이 어떻게 되나요? | 부산 매장 영업시간이 어떻게 되나요? | 0.822 |
| | 달러를 원화로 바꾸려면 어떻게 하나요? | 원화를 달러로 바꾸려면 어떻게 하나요? | 0.970 |
| | 지난달 결제 금액 알려 주세요 | 이번 달 결제 금액 알려 주세요 | 0.944 |
| | 자동 결제를 켜는 방법 알려 주세요 | 자동 결제를 끄는 방법 알려 주세요 | 0.898 |
| 상관없다 | 환불은 어떻게 하나요? | 서울 매장 영업시간이 어떻게 되나요? | 0.560 |
| | 비밀번호를 잊어버렸어요 | 배송은 며칠 걸려요? | 0.479 |

답이 다른 6쌍은 글자가 닮도록 일부러 까다롭게 골랐다. 그러니 이 비율을 실제 서비스의 오답률로 읽으면 안 된다. 여기서 볼 것은 어떤 질문이 문턱값을 넘는지다. 막대를 움직이면 엉뚱한 답을 받는 질문이 아래 목록에서 진해진다.

<ThresholdDemo client:visible />

0.80에서는 뜻이 같은 6쌍 가운데 5쌍이 적중하지만, 답이 다른 6쌍도 모두 적중해 엉뚱한 답을 받는다. 0.95로 올리면 엉뚱한 답은 1쌍으로 줄고, 제대로 적중하는 쌍도 1쌍만 남는다. 0.98에서는 엉뚱한 답이 사라지지만 적중도 사라진다. 이 질문들에서는 오답을 모두 걸러 내면서 적중을 남기는 문턱값이 없다.

### 닮은 글자가 같은 뜻보다 가깝다

유사도가 가장 높은 쌍은 「달러를 원화로」와 「원화를 달러로」다. 쓰인 낱말이 같고 자리만 바뀌었다. 뜻이 같은 쌍 가운데 가장 낮은 것은 「회원 탈퇴는 어떻게 하나요?」와 「계정을 지우고 싶어요」다. 뜻은 같은데 겹치는 낱말이 없다.

<AngleDiagram variant="trap" />

임베딩은 무엇에 관한 질문인지는 잘 잡아낸다. 상관없는 질문은 0.6을 넘지 않았다. 하지만 되는지 안 되는지, 3일인지 30일인지, 켜는지 끄는지는 유사도에 작게만 나타난다. 정작 답을 가르는 것은 이 작은 차이다.

[vCache 논문](https://arxiv.org/abs/2502.03771)도 같은 문제를 짚는다. 맞는 적중과 틀린 적중의 유사도 분포가 크게 겹치므로, 모든 요청에 문턱값 하나를 쓰면 정확도를 보장할 수 없다는 것이다. 그래서 저장된 질문마다 문턱값을 따로 학습한다. 사용자는 문턱값 대신 허용할 오류율을 정한다.

### 0.8의 뜻은 모델마다 다르다

LiteLLM 문서의 예시 문턱값은 0.8이다. 이 값을 그대로 가져다 쓰면 어떻게 될까. 같은 14쌍을 다른 공개 모델 둘로도 재 보았다.

<SimilarityRowsDiagram variant="models" />

| 모델 | 뜻이 같다 | 답이 다르다 | 상관없다 |
| --- | --- | --- | --- |
| paraphrase-multilingual-MiniLM-L12-v2 | 0.466\~0.890 | 0.900\~0.991 | 0.244\~0.375 |
| multilingual-e5-small | 0.835\~0.972 | 0.935\~0.994 | 0.799\~0.810 |
| bge-m3 | 0.699\~0.959 | 0.822\~0.970 | 0.479\~0.560 |

> <strong>잰 방법</strong>  
> Transformers.js 4.3.2로 로컬에서 돌렸다. bge-m3는 8비트로 줄인 모델을 썼고, 나머지 둘은 줄이지 않았다. e5-small에는 모델 카드의 안내대로 질문 앞에 `query: `를 붙였다. 벡터는 모두 길이를 1로 맞췄다.

MiniLM에서는 답이 다른 쌍이 모두 뜻이 같은 쌍보다 위에 있다. 0.8을 쓰면 뜻이 같은 쌍은 2쌍만 적중하고, 답이 다른 쌍은 6쌍 모두 적중한다. e5-small에서는 「비밀번호를 잊어버렸어요」와 「배송은 며칠 걸려요?」까지 0.810으로 적중한다. 비밀번호를 잊은 사람이 배송 안내를 받는 셈이다. e5-small의 [모델 카드](https://huggingface.co/intfloat/multilingual-e5-small)는 유사도가 0.7에서 1.0 사이에 몰리는 것이 학습 방식 때문에 생기는 예상된 결과라고 설명한다.

그러니 문턱값은 다른 곳에서 옮겨 올 수 없다. 임베딩 모델을 바꾸면 처음부터 다시 정해야 한다. 방향도 확인해야 한다. 같은 자리에 적는 숫자인데 도구에 따라 뜻이 반대다.

| 도구 | 설정 | 재는 값 | 엄격해지는 방향 |
| --- | --- | --- | --- |
| LiteLLM | `similarity_threshold` | 코사인 유사도 | 높일수록 |
| Portkey | `SEMANTIC_CACHE_SIMILARITY_THRESHOLD` | 코사인 유사도 | 높일수록 |
| Azure API Management | `score-threshold` | 0.0\~1.0 점수 | 낮출수록 |
| Kong AI Gateway | `vectordb.threshold` | 설정한 거리 기준 | 낮출수록 |
| RedisVL | `distance_threshold` | 코사인 거리 0\~2 | 낮출수록 |

Azure 문서는 0.05 같은 낮은 값에서 시작하라고 권하고, 0.2를 넘으면 엉뚱한 답이 나갈 수 있다고 경고한다. LiteLLM에서 쓰던 0.8을 여기에 그대로 적으면 경고하는 값의 네 배가 된다. 방향이 같아도 값은 다르다. 똑같이 코사인 유사도를 쓰는데 LiteLLM 문서의 예시는 0.8이고 Portkey의 기본값은 0.95다.

## 임베딩에는 질문만 들어가야 한다

지금까지는 질문 한 문장만 임베딩했다. 실제 요청에는 시스템 프롬프트와 앞선 대화가 함께 들어 있다. [LiteLLM 문서](https://docs.litellm.ai/docs/proxy/caching_semantic)에 따르면 시맨틱 캐시는 시스템 프롬프트를 포함한 `messages` 전체의 글을 임베딩한다.

### 시스템 프롬프트가 질문을 덮는다

같은 14쌍의 앞에 같은 시스템 프롬프트를 붙이고 bge-m3로 다시 쟀다. 하나는 37토큰, 하나는 261토큰이다. 토큰 수는 bge-m3의 토크나이저로 셌다.

<SimilarityRowsDiagram variant="system" />

시스템 프롬프트가 길어질수록 모든 점이 오른쪽으로 몰린다. 두 글의 대부분이 같은 문장이니 벡터도 거의 같은 방향을 가리킨다. 261토큰에서는 상관없는 두 질문의 유사도가 0.974와 0.976까지 올라, 문턱값을 0.95로 높여도 14쌍이 모두 적중한다. 비밀번호를 잊었다고 말한 사람이 여기서도 배송 안내를 받는다. 261토큰은 지시문 열 줄 분량이다.

그래서 시스템 프롬프트를 빼고 비교하게 해 주는 도구도 있다. 다만 기본값은 도구마다 다르다.

| 도구 | 시스템 프롬프트 | 앞선 대화 |
| --- | --- | --- |
| LiteLLM | 넣는다. 빼는 설정은 문서에서 찾지 못했다 | `messages` 전체를 넣는다 |
| Azure API Management | `ignore-system-messages`로 뺀다. 문서는 `true`를 권하지만 기본값은 `false`다 | 메시지 수가 `max-message-count`를 넘으면 캐시를 건너뛴다 |
| Kong AI Gateway | `ignore_system_prompts`로 뺀다. 기본값은 `false`다 | `message_countback`으로 넣을 메시지 수를 정한다. 기본값은 1이다 |
| Portkey | 뺀다 | 메시지가 4개 이하인 요청에만 쓴다 |

시스템 프롬프트를 빼면 반대쪽 문제가 생긴다. Portkey 문서는 시스템 프롬프트를 바꿔도 적중에 영향이 없다고 적는다. 프롬프트가 다른 두 기능이 캐시를 함께 쓰면, 한 기능의 답이 다른 기능에서 나갈 수 있다는 뜻이다. 그래서 기능마다 캐시를 나눠야 한다. Portkey에서는 네임스페이스로, Azure에서는 `vary-by`로 나눈다.

### 대화가 길어지면 직전 요청과 같아진다

대화형 요청은 매번 앞선 대화를 전부 다시 보낸다. 새로 붙는 것은 마지막 질문뿐이다. 시스템 프롬프트 37토큰으로 시작하는 상담 대화를 만들어, 이어진 요청끼리의 유사도를 쟀다.

<TurnSimilarityDiagram />

대화가 길어질수록 새 질문이 차지하는 몫이 작아져 유사도가 1에 가까워진다. 이 대화를 캐시에 붙여 처음부터 이어 가 보았다. 사용자의 말은 정해 두고, 적중하면 저장된 답을, 놓치면 제대로 된 답을 대화에 넣었다. 먼저 문턱값 0.8이다.

<TurnReplayDemo client:visible />

첫 요청만 모델이 답하고, 그 뒤로는 무엇을 말해도 첫 답이 되풀이된다. 되풀이된 답도 대화에 쌓이지만 첫 요청과의 유사도는 0.8 밑으로 내려가지 않는다.

문턱값을 0.95로 올려도 절반만 고쳐진다. 첫째, 둘째, 넷째 요청은 새 답을 받지만 셋째는 둘째의 답을, 다섯째는 넷째의 답을 받는다. 「그럼 그냥 환불해 주세요」라고 말한 사람이 교환 배송비 안내를 다시 받는다.

LiteLLM 문서는 에이전트에서 이 문제가 더 심하다고 설명한다. 에이전트가 같은 도구 호출을 되풀이하는 모습으로 드러나는데, 어시스턴트의 `tool_calls`는 임베딩에 들어가지도 않아 이어진 턴을 가르기가 더 어렵다. 문턱값을 올려도 확실히 고쳐지지 않으니 에이전트 트래픽은 캐시에서 빼라고 권한다. 에이전트가 쓰는 키의 메타데이터에 `"cache": {"no-cache": true}`를 넣으면 된다. 그래도 캐시가 필요하면 요청 전체를 해시하는 응답 캐시를 쓴다.

## 같은 질문인데 답이 다를 때

지금까지 본 오답은 질문이 달라서 생겼다. 질문이 글자까지 같아도 답이 달라야 할 때가 있다. 이때는 유사도가 1이므로 문턱값으로는 막을 수 없다.

### 사람마다 답이 다른 질문

「이번 달 결제 금액 알려 주세요」는 누가 묻느냐에 따라 답이 다르다. 한 사람의 답을 저장해 두면 다음 사람이 남의 결제 금액을 본다. 오답을 넘어 정보 유출이다. A의 금액이 42,000원, B의 금액이 15,000원이라고 하자.

<CacheScopeDiagram />

LiteLLM은 기본으로 가상 키, 팀, 조직 단위로만 캐시를 나눈다. 서비스 하나가 키 하나로 모든 사용자의 요청을 보낸다면, 그 사용자들은 캐시를 함께 쓴다. 사용자마다 나누려면 `semantic_cache_scope: end_user`를 적는다. 요청에 사용자 ID가 없으면 다시 키 단위로 돌아가므로, 사용자 ID를 빠짐없이 보내는지도 확인해야 한다. Azure에서는 `vary-by`에 사용자나 그룹을 가르는 식을 적는다.

사용자마다 나누면 남의 답을 받을 일은 없지만, 여러 사람이 같은 것을 물어도 서로의 답을 쓰지 못한다. 시맨틱 캐시의 이득은 여러 사람이 같은 것을 묻는 데서 나온다. 그래서 사람마다 답이 다른 기능이라면 캐시를 나누기보다 아예 쓰지 않는 편이 낫다.

### 시간이 지나면 바뀌는 답

재고, 가격, 배송 상황, 공지는 어제의 답이 오늘은 틀린다. 저장할 때 유효 시간을 정해 두어야 한다. LiteLLM은 `ttl`로, Azure는 저장 정책의 `duration`으로 초 단위 시간을 정한다. 환불 규정 같은 안내 문서를 바꿨다면 유효 시간을 기다리지 말고 캐시를 비운다.

## 세 캐시는 서로를 대신하지 않는다

### 셋의 차이

이름이 비슷한 세 캐시를 나란히 놓으면 이렇다.

| | 응답 캐시 | 시맨틱 캐시 | 프롬프트 캐싱 |
| --- | --- | --- | --- |
| 저장하는 것 | 요청과 답 | 질문 벡터와 답 | 입력 앞부분의 KV |
| 적중 조건 | 요청이 통째로 같다 | 유사도가 문턱값 이상이다 | 앞부분이 같다 |
| 답 | 저장된 답 | 가장 가까운 질문의 답 | 매번 새로 만든다 |
| 아끼는 것 | 모델 호출 전체 | 모델 호출 전체 | 입력 앞부분의 계산 |
| 놓쳤을 때 | 거의 그대로다 | 임베딩과 검색만큼 늦다 | 쓰기 요금이 더 붙을 수 있다 |
| 다른 질문의 답이 나갈 위험 | 없다 | 있다 | 없다 |
| 잘 맞는 곳 | 정해진 문구가 반복되는 곳 | 여러 사람이 같은 것을 다르게 묻는 곳 | 긴 지시문과 대화 이력 |

### 함께 쓸 때의 순서

함께 쓸 때는 틀릴 위험이 없는 쪽부터 본다. 앞의 흐름 그림처럼 문턱값을 0.9로 정하고, 「환불은 어떻게 하나요?」가 저장되어 있다고 하자.

<CachePathDemo client:visible />

글자까지 같은 요청은 응답 캐시에서 끝나므로 임베딩을 부를 필요가 없다. 응답 캐시가 놓친 요청만 시맨틱 캐시로 가고, 둘 다 놓친 요청만 모델까지 간다. 이때 입력 앞부분이 프롬프트 캐시에 남아 있으면 모델 제공자는 그 계산을 다시 쓴다.

Portkey의 시맨틱 캐시는 정확히 같은 요청을 먼저 찾고, 놓쳤을 때만 시맨틱 검색을 한다. Kong도 `exact_caching`을 켜면 정확히 같은 질문을 먼저 찾지만 기본은 꺼져 있다. LiteLLM은 캐시 종류를 `type` 하나로 고른다. 두 캐시를 함께 켜는 설정은 문서에서 찾지 못했다.

### 나머지 둘로 충분한지부터 본다

셋 가운데 다른 질문의 답을 내보낼 수 있는 것은 시맨틱 캐시 하나다. 적중률이 낮아 아쉽다면 시맨틱 캐시를 떠올리기 전에 나머지 둘로 충분한지부터 본다. 입력이 길어 비싼 것이라면 프롬프트 캐싱이 답을 바꾸지 않고 줄여 준다. 질문이 몇 가지로 정해져 있다면 버튼으로 고르게 하고 응답 캐시를 쓰는 편이 안전하다.

## 켜기 전에 재 본다

시맨틱 캐시가 맞는 자리라고 판단했다면, 켜기 전에 이 순서로 확인한다.

1. 실제로 들어온 질문을 모아 두 개씩 짝짓고, 같은 답을 줘도 되는 쌍과 안 되는 쌍으로 나눈다. 글자는 닮았는데 답이 다른 쌍을 꼭 넣는다.
2. 쓸 임베딩 모델로 유사도를 잰다. 게이트웨이가 시스템 프롬프트까지 임베딩한다면 그것도 붙여서 잰다.
3. 두 무리를 가르는 문턱값이 있는지 본다. 없으면 켜지 않는다.
4. 처음에는 저장된 답을 내보내지 않고 기록만 한다. 적중했을 답과 새로 만든 답을 견줘 오답률을 센다.
5. 켠 뒤에는 유사도를 로그에 남긴다. 문턱값 바로 위에서 적중한 요청부터 골라 읽는다.

3번에서 멈추더라도 손해는 아니다. 앞의 14쌍처럼 두 무리가 겹친다면, 켜기 전에 알게 된 것이 다행이다.

## 정리

서문의 세 질문으로 돌아가자.

- <strong>무엇으로 판단하는가</strong> — 질문을 벡터로 바꿔 코사인 유사도를 잰다. 무엇에 관한 질문인지는 잘 잡지만, 되는지 안 되는지처럼 답을 가르는 차이는 작게 나타난다.
- <strong>얼마나 비슷해야 하는가</strong> — 정해진 값이 없다. 문턱값을 내리면 오답이 늘고 올리면 적중이 준다. 임베딩 모델이 바뀌면 같은 숫자의 뜻도 바뀐다.
- <strong>쓰면 안 되는 요청</strong> — 이어지는 대화와 에이전트, 사람마다 답이 다른 질문, 시간이 지나면 바뀌는 답이다.

시맨틱 캐싱을 켤지 정할 때는 다섯 가지를 기준으로 삼으면 된다.

1. <strong>틀린 답이 나가도 괜찮은 자리인지 본다.</strong> 시맨틱 캐시는 가장 가까운 다른 질문의 답을 돌려준다. 틀렸을 때 되돌릴 수 없는 안내라면 쓰지 않는다.
2. <strong>적중률보다 오답률을 먼저 정한다.</strong> 앞의 가정대로면 본전은 적중률 2.5%로 넘는다. 얼마나 틀려도 되는지를 먼저 정하고, 그 안에서 적중률을 올린다.
3. <strong>문턱값은 내 질문과 내 모델로 잰다.</strong> 문서의 예시 값은 내 질문으로 잰 값이 아니다. 높여야 엄격한지 낮춰야 엄격한지도 확인한다.
4. <strong>임베딩에 무엇이 들어가는지 확인한다.</strong> 시스템 프롬프트와 앞선 대화가 들어가면 질문이 묻힌다. 질문만 비교하게 만들 수 없다면 쓰지 않는다. 시스템 프롬프트를 뺐다면 기능마다 캐시를 나눈다.
5. <strong>캐시를 누구와 나눠 쓰는지 확인한다.</strong> 기본 설정이 사용자를 가르지 않을 수 있다. 사람마다 답이 다른 기능은 캐시에서 뺀다.
